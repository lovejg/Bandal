# 개발 일지

실제로 겪은 문제와 해결 과정. 포트폴리오의 "가장 어려웠던 문제" 항목에 쓸 재료다.

## 쓰는 규칙

1. **겪는 즉시 쓴다.** 나중에 몰아서 쓰면 에러 메시지도 시행착오 순서도 기억이 안 난다.
2. **에러 메시지를 그대로 붙인다.** 요약하지 말 것. 포트폴리오에서 신뢰를 만드는 건
   "동시성 문제가 있었습니다"가 아니라 실제 스택 트레이스와 재현 조건이다.
3. **재현한 것만 쓴다.** 일어날 것 같았던 문제는 쓰지 않는다. 피해 간 문제는
   "피해 갔다"고 적는다.
4. **틀렸던 시도도 남긴다.** 한 번에 맞힌 것처럼 쓰면 읽는 사람이 얻을 게 없다.
   막다른 길이 왜 막다른 길이었는지가 이해의 증거다.

```markdown

(재현 조건도 같이 — 동시 요청 N개, 데이터 M건 등)

**원인** 왜 그랬나.

**시도한 것** 안 통한 것부터. 왜 안 통했는지.

**해결** 최종적으로 어떻게 고쳤나. 코드가 있으면 diff나 핵심 부분만.

**배운 것** 다음에 비슷한 걸 만나면 뭘 먼저 볼까.

**포트폴리오 각도** 이걸 면접에서 어떻게 한 문단으로 설명할까.
```

## 2026-09-15. User 테이블이 안 만들어졌는데 앱은 정상적으로 떴다

**상황** Phase 1 들어가기 전 도메인 엔티티 작업. `User` 엔티티를 매핑하고
`UserRepositoryTest`(@DataJpaTest, Testcontainers Postgres 17)를 돌렸다.
`ddl-auto: create-drop`.

**증상** 테스트 10개가 전부 실패했다. 컨텍스트 로딩은 성공했고, 테이블 생성 에러는
ERROR가 아니라 WARN으로 찍혔다.

```
WARN ... o.h.t.s.i.ExceptionHandlerLoggedImpl : GenerationTarget encountered exception accepting command : Error executing DDL "
    create table user (
        trust_score integer not null,
        email_verified_at timestamp(6) with time zone,
        id bigint generated by default as identity,
        university_id bigint not null,
        email varchar(255) not null unique,
        nickname varchar(255) not null unique,
        password varchar(255) not null,
        primary key (id)
    )" via JDBC [ERROR: syntax error at or near "user"
  Position: 19]
```

저장하는 테스트 6개는 INSERT에서 터졌다.

```
org.springframework.dao.InvalidDataAccessResourceUsageException: could not execute statement
[ERROR: syntax error at or near "user"  Position: 13]
[insert into user (email,email_verified_at,nickname,password,trust_score,university_id) values (?,?,?,?,?,?)]
```

not null 제약을 확인하는 테스트 4개는 예외 종류가 달라서 실패했다.

```
Expecting actual throwable to be an instance of:
  org.springframework.dao.DataIntegrityViolationException
but was:
  org.springframework.dao.InvalidDataAccessResourceUsageException
```

**원인** 엔티티 이름 `User`를 따라 테이블 이름이 `user`가 됐는데, `user`는 PostgreSQL
예약어다(`SELECT user;`가 현재 접속 계정을 돌려준다). 테이블 이름 자리에 오면 문법 오류다.
Hibernate는 기본 설정에서 DDL 실패를 로그로만 남기고 계속 진행하기 때문에, 테이블이 없는
채로 컨텍스트가 떴고 문제는 첫 INSERT에서야 드러났다.

not null 테스트 4개는 제약 위반까지 가지도 못하고 SQL 문법 오류에서 먼저 막혔다. 테스트가
"예외가 난다"가 아니라 "`DataIntegrityViolationException`이 난다"까지 확인하고 있어서
엉뚱한 이유로 통과하지 않았다.

**시도한 것** 따로 헛발질한 시도는 없다. 두 방법을 놓고 골랐다.
- `@Table(name = "\"user\"")`로 따옴표를 씌운다: 이름은 유지되지만 SQL을 직접 쓸 때마다
  따옴표가 필요하고, 빠뜨리면 같은 에러가 난다. 버렸다.

**해결**

```java
@Entity
@Table(name = "users")
public class User {
```

전체 테스트 24개 통과.

**배운 것**
- 엔티티 이름이 흔한 단어(`User`, `Order`, `Group`)면 DB 예약어인지 먼저 본다.
  `order`와 `group`도 SQL 예약어다. 앞으로 만들 `GroupOrder`는 `group_order`라서 괜찮다.
- 테스트 로그의 WARN도 읽는다. DDL 실패는 WARN으로 조용히 지나간다.
- 예외 테스트는 예외 종류까지 확인해야 엉뚱한 실패를 통과로 착각하지 않는다.

**포트폴리오 각도** "User 엔티티를 만들었는데 앱은 정상적으로 뜨고 저장만 실패했다.
로그를 보니 `user`가 PostgreSQL 예약어라 테이블 생성이 실패했는데, Hibernate가 이걸
WARN으로만 남기고 넘어간 것이었다. 테이블 이름을 `users`로 지정해서 고쳤고, 이후로는
테스트 로그의 WARN도 확인한다. 제약조건 테스트가 예외 타입까지 검사하고 있어서, 제약 때문이
아니라 문법 오류로 실패한 것을 구분할 수 있었다."

## 2026-09-18. 방장 확인을 `Long !=`로 했는데 테스트가 통과했다

**상황** GroupOrder 상태 전이 1단계(모집중 → 마감). `closeByHost`에서 요청자가 방장인지
확인하는 코드. DB 없는 단위 테스트 `GroupOrderTest`, 테스트 id는 1000.

**증상** 처음 구현은 이랬고, 방장 관련 테스트 6개가 전부 통과했다.

```java
|| requesterId != host.getId() // 요청자가 방장이 아닌 경우
```

`requesterId`도 `host.getId()`도 `Long`이라 `!=`는 값이 아니라 객체 주소를 비교한다.
그런데도 통과한 건 테스트가 같은 상수 `HOST_ID` 객체를 방장 id에도 넣고 요청자 id로도
넘겼기 때문이다. 우연히 같은 객체라 주소 비교가 맞아떨어졌다.

테스트를 실제 상황처럼 바꿨다. 엔티티 id는 DB에서, 요청자 id는 요청에서 읽으니 값만 같은
서로 다른 객체다.

```java
ReflectionTestUtils.setField(host, "id", Long.valueOf(HOST_ID.longValue()));
```

그러자 방장이 자기 방을 마감하는 테스트가 거절당했다.

```
GroupOrderTest > 방장의 수동 마감 > 2명 이상이고 메뉴 합계가 최소주문금액 이상이면 마감된다 FAILED
java.lang.IllegalStateException: 에러 발생
```

**원인** Java에는 연산자 오버로딩이 없어서 객체에 쓴 `==`, `!=`는 항상 주소 비교다.
`Long`은 -128~127만 캐시해서 같은 객체를 돌려주므로, id가 작을 때는 우연히 맞는다.
운영에서 id가 128을 넘으면 방장이 자기 방을 못 닫는다. 테스트 id를 1000으로 잡아 캐시
범위는 피했지만, 같은 객체를 재사용해서 그것만으로는 못 잡았다.

**시도한 것** `Objects.equals`로 바꾸면서 `!`를 빠뜨렸다. 결과가 정확히 뒤집혔다.

```java
|| Objects.equals(requesterId, host.getId()) // 요청자가 방장이 아닌 경우
```

```
방장의 수동 마감 > 2명 이상이고 ... 마감된다 FAILED   java.lang.IllegalStateException: 에러 발생
방장의 수동 마감 > 방장이 아닌 사람은 마감할 수 없다 FAILED   Expecting code to raise a throwable.
```

테스트가 방장이 마감하는 경우와 남이 마감하는 경우를 둘 다 보고 있어서 바로 드러났다.

**해결**

```java
|| !Objects.equals(requesterId, host.getId()) // 요청자가 방장이 아닌 경우
```

전체 테스트 53개 통과.

**배운 것**
- 대문자 타입(`Long`, `String`, 엔티티)끼리는 `Objects.equals`. 예외는 enum뿐이다.
  C++로 치면 대문자 타입 변수는 포인터이고, `==`는 `p1 == p2`, `equals`는 `*p1 == *p2`다.
- null일 일이 없으면 기본형 `long`을 쓴다. 비교 고민이 사라진다.
- 테스트에 쓰는 값이 운영과 같은 모양인지 본다. 작은 id, 같은 객체 재사용은 이 버그를 숨긴다.
- `!=`를 `equals`로 바꾸는 변환은 부호가 뒤집히기 쉽다. 양쪽 경우를 다 보는 테스트가 잡아준다.

**포트폴리오 각도** "방장 확인을 `Long`끼리 `!=`로 비교했는데 테스트가 통과했다. 테스트가
같은 `Long` 객체를 재사용해서 주소 비교가 우연히 맞았던 것이다. 운영처럼 값만 같은 다른
객체를 넣자 방장이 자기 방을 못 닫는 버그가 드러났다. `Long`은 -128~127만 캐시하기 때문에
개발 초기의 작은 id로는 절대 안 보이고, id가 128을 넘는 순간 터지는 종류의 버그다."

## 2026-09-22. 지연로딩 프록시를 `==`로 비교할 뻔했다 (피해 감)

**이 항목은 재현하지 않았다.** 코드를 쓰기 직전에 지적을 받아서 다른 방식으로 짰다.
겪은 게 아니라 피해 간 것이라 증상 칸에 붙일 에러 메시지가 없다. 그래도 남기는 이유는
`Long !=`(2026-09-18)와 실패 방식이 같은데, 그때보다 더 안 보이는 자리이기 때문이다.

**상황** Phase 1, 메뉴 담기/빼기. `Participation.removeItem(requesterId, item)`에서 "이 메뉴가
정말 이 참여의 것인가"를 확인해야 했다. 남의 메뉴를 뺄 수 있으면 안 되니까.

**쓰려던 코드**

```java
if (item.getParticipation() != this) { // 다른 참여의 메뉴
    throw new IllegalStateException("에러 발생");
}
```

**왜 위험한가** `OrderItem.participation`은 `FetchType.LAZY`다. Hibernate는 메뉴를 읽을 때
참여 테이블을 같이 읽지 않고, `Participation`을 상속한 프록시 객체를 대신 넣는다. 안에는
id만 있고, 다른 getter를 처음 부를 때 SELECT가 나간다.

```java
found.getParticipation().getClass()  // Participation$HibernateProxy$...
```

`==`는 주소 비교라서, 실체와 프록시를 비교하면 값이 같아도 다르다고 나올 수 있다.
`equals`를 재정의하지 않았으므로 `equals`도 결과가 같다.

**더 고약한 점** 같은 영속성 컨텍스트 안에서 그 참여를 이미 꺼내 썼다면 Hibernate가 같은
객체를 돌려주므로 `==`가 맞아떨어진다. 즉 **되는 경우가 있다.** 한 트랜잭션 안에서
`findById`로 참여를 먼저 꺼내는 테스트만 짜면 통과하고, 메뉴부터 꺼내는 경로에서만 틀린다.
`Long !=`가 작은 id에서만 우연히 맞았던 것과 똑같은 구조다. 조건이 "숫자 크기"에서
"어떤 순서로 로딩했는가"로 바뀌었을 뿐이고, 이쪽이 훨씬 눈에 안 띈다.

**대신 쓴 방법**

```java
Long ownerId = item.getParticipation().getId();      // 프록시도 id는 알고 있어서 SELECT가 안 나간다
if (!Objects.equals(ownerId, this.id)) {
    throw new IllegalStateException("에러 발생");
}
```

`getParticipation()`을 안 쓰는 게 아니라, 꺼낸 것을 **객체로 비교하지 않는다.** id만 꺼내면
프록시가 초기화되지도 않아서 쿼리도 늘지 않는다.

**배운 것**
- 엔티티끼리 같은 행인지 볼 때는 객체가 아니라 id를 비교한다. 지연로딩이 걸려 있으면
  한쪽이 프록시일 수 있다.
- 프록시에서 `getId()`는 공짜다. 다른 getter는 SELECT를 부른다. 이 차이가 "id로 비교"가
  성능상으로도 맞는 이유다.
- "될 때도 있고 안 될 때도 있는 비교"가 제일 위험하다. 되는 쪽만 보는 테스트를 짜면
  통과해버린다. 자바에서 대문자 타입을 `==`로 비교하고 있으면 일단 의심한다.

**포트폴리오 각도** "지연로딩 연관을 `==`로 비교하려다 멈췄다. `@ManyToOne(LAZY)`는 프록시를
넣기 때문에 실체와 주소가 다를 수 있고, 같은 영속성 컨텍스트에서 이미 로딩됐을 때만 우연히
맞는다. 로딩 순서에 따라 결과가 달라지는 비교라 테스트로도 잘 안 잡힌다. 엔티티 동일성은
id로 비교하도록 했고, 프록시는 id를 이미 갖고 있어 추가 쿼리도 나가지 않는다."

## 2026-09-22. 메뉴가 하나도 없는 방의 합계를 구하니 SUM이 NULL을 돌려줬다

**상황** Phase 1, 메뉴 담기(OrderItem). 방의 메뉴 합계를 `OrderItemRepository`의 JPQL로
구한다. 마감 조건(최소주문금액을 채웠나) 판정에 쓸 숫자다.

```java
@Query("""
    SELECT SUM(oi.unitPrice * oi.quantity) from OrderItem oi
    WHERE oi.participation.groupOrder.id = :groupOrderId
    """)
long sumAmountByGroupOrderId(@Param("groupOrderId") Long groupOrderId);
```

**증상** 메뉴가 있는 방을 더하는 테스트는 전부 통과했고, 아무도 메뉴를 담지 않은 방
하나만 터졌다. 85개 중 1개 실패.

```
OrderItemRepositoryTest > 아무도 메뉴를 담지 않은 방의 합계는 0이다 FAILED

org.springframework.aop.AopInvocationException: Null return value from advice
does not match primitive return type for:
public abstract long com.bandal.participation.OrderItemRepository.sumAmountByGroupOrderId(java.lang.Long)
```

**원인** SQL에서 `COUNT`와 `SUM`은 빈 결과를 다르게 다룬다. `COUNT`는 행을 세므로 행이
없으면 0이다. `SUM`은 값을 더하므로 더할 값이 없으면 "합계가 없다"는 뜻의 NULL이다.
SQL의 NULL은 "값이 0"이 아니라 "값이 없다"라서, 0으로 대신 채워주지 않는다.

그 NULL이 자바로 넘어오는데 반환 타입이 기본형 `long`이라 담을 자리가 없다. 스프링이
프록시에서 언박싱하려다 위 예외를 냈다.

**해결** DB 쪽에서 0으로 바꾼다.

```java
SELECT COALESCE(SUM(oi.unitPrice * oi.quantity), 0) from OrderItem oi
WHERE oi.participation.groupOrder.id = :groupOrderId
```

85개 전부 통과.

**시도하지 않은 대안** 반환 타입을 `Long`으로 바꾸고 자바에서 null을 처리할 수도 있다.
그러면 이 메서드를 부르는 모든 곳이 null을 신경 써야 하고, `closeByHost(..., total)`에
그대로 넘기면 더 늦게, 더 엉뚱한 자리에서 NPE가 난다. 한 군데서 막는 쪽을 택했다.

**배운 것**
- 집계 함수의 빈 결과를 먼저 생각한다. `COUNT`는 0, `SUM`/`AVG`/`MAX`/`MIN`은 NULL이다.
- 반환 타입이 기본형인데 NULL이 올 수 있으면 언박싱에서 터진다. 쿼리에서 `COALESCE`로
  막거나, 막을 수 없으면 `Optional`이나 래퍼 타입으로 받아 호출부에서 처리한다.
- 실제로 터지는 시점은 "방장이 방만 만들고 아직 아무도 메뉴를 안 담은 상태"다. 개발 중에는
  항상 데이터를 채워놓고 보기 때문에 잘 안 보이고, 배포하면 가장 흔한 상태에서 나온다.
  빈 상태를 확인하는 테스트가 없었으면 그대로 나갔다.

**같이 나온 것들** (같은 단계에서 겪었고, 한 줄씩 고친 것)

- `@Query` 안에 자바처럼 `==`를 썼다. JPQL은 SQL 계열이라 `=` 하나다.
  `BadJpqlGrammarException: token '=', extraneous input '='`. 더 인상적이었던 건 이 한 줄
  때문에 `orderItemRepository` 빈 생성이 실패하면서 **`@DataJpaTest` 44개가 전부 죽었다**는
  점이다. 개별 테스트만 보면 원인이 안 보이고 `Caused by`를 끝까지 따라가야 나온다.
  쿼리 오타를 런타임이 아니라 뜨는 순간 잡아준다는 점에서는 좋은 성질이다.
- `oi.participation.groupOrder = :groupOrderId`로 엔티티와 `Long`을 비교했다.
  `InvalidDataAccessApiUsageException: argument [1] is not assignable to GroupOrder`.
  JPQL은 테이블이 아니라 객체 그래프를 타는 언어여서 `.groupOrder`는 컬럼이 아니라 객체다.
  `.groupOrder.id`로 한 칸 더 내려가면 되고, participation 테이블에 group_order_id가 이미
  있으므로 조인도 늘지 않는다.
- 예외를 `new`만 하고 `throw`를 빼먹었다(세 군데). 자바에서 예외도 그냥 객체라서 문법상
  멀쩡하고 경고도 없다. 검사가 통째로 무력화됐고 `Expecting code to raise a throwable.`로
  드러났다.
- 주인 확인을 참여 행의 id(`this.id`)와 요청자 id로 했다. 서로 다른 테이블의 번호다.
  이때 **거절을 확인하는 테스트는 전부 통과했다.** 항상 거절하고 있었기 때문이다. 성공하는
  경우를 보는 테스트가 없었으면 멀쩡해 보였을 것이다. 2026-09-18 항목과 같은 교훈이다.

**포트폴리오 각도** "메뉴 합계를 SUM으로 구했는데, 메뉴가 하나도 없는 방에서만 실패했다.
SQL의 SUM은 대상 행이 없으면 0이 아니라 NULL을 돌려주고, 반환 타입이 기본형 `long`이라
언박싱에서 터진 것이다. COUNT는 0을 주기 때문에 같은 모양이라고 생각하기 쉽다. 쿼리에
COALESCE를 넣어 DB 경계에서 막았고, 자바 쪽으로 null을 흘려보내 호출부마다 처리하게 하는
방식은 택하지 않았다. 빈 상태를 확인하는 테스트가 없었다면 '방을 막 만들었을 때'라는 가장
흔한 상황에서 났을 버그다."

## 2026-09-22. 테스트 12개가 다 통과했는데 로그아웃이 로그아웃이 아니었다

**상황** Phase 1-2, 로그인(JWT 액세스 + Redis 리프레시, ADR-024). 로그인, 토큰 갱신,
로그아웃을 만들고 테스트 12개를 붙였다. 전부 통과했다.

- 로그인하면 토큰 두 개가 나온다 — 통과
- 리프레시 토큰으로 새 액세스 토큰을 받는다 — 통과
- 로그아웃하면 그 리프레시 토큰으로 더 갱신할 수 없다 — 통과

**증상** 세 기능을 순서대로 엮는 테스트를 하나 더 붙이자 바로 깨졌다.

```
LoginApiTest > 갱신한 뒤 로그아웃하면 갱신 전 토큰으로도 더 갱신할 수 없다 FAILED
    java.lang.AssertionError: Status expected:<401> but was:<200>
```

재현 순서는 로그인 → 갱신 → (새 토큰으로) 로그아웃 → **갱신 전 토큰으로 갱신 시도**다.

**원인** 갱신할 때 새 리프레시 토큰을 발급하면서 옛 토큰을 지우지 않았다.

```java
public TokenResponse refresh(String refreshToken) {
    Long userId = refreshTokenStore.findUserId(refreshToken);
    ...
    return new TokenResponse(..., refreshTokenStore.issue(userId));   // 새 키만 추가된다
}
```

```
로그인        → refresh:AAA 생성              유효: AAA
갱신          → refresh:BBB 생성              유효: AAA, BBB
로그아웃(BBB) → refresh:BBB 삭제              유효: AAA   ← 아직 로그인 상태
```

클라이언트는 최신 토큰만 들고 있으므로 그걸로 로그아웃한다. 옛 토큰들은 TTL 2주 동안
그대로 살아남는다. 갱신을 열 번 했으면 살아 있는 토큰이 열 개다. 폰을 잃어버려서 로그아웃한
사용자가 실제로는 끊기지 않는다.

**해결** 리프레시 토큰 회전. 갱신에 쓴 토큰을 폐기하고 새로 발급한다.

```java
Long userId = refreshTokenStore.findUserId(refreshToken);   // 찾고
if (userId == null) throw new UnauthorizedException("다시 로그인해주세요");
refreshTokenStore.revoke(refreshToken);                     // 폐기하고
return new TokenResponse(jwtProvider.createAccessToken(userId),
                         refreshTokenStore.issue(userId));  // 발급한다
```

순서가 중요하다. 폐기를 먼저 하면 누구 토큰인지 알 수 없고, 발급을 먼저 하면 잠깐이지만
유효한 토큰이 둘이 된다. 전체 153개 통과.

**배운 것**
- **기능 하나씩 보는 테스트는 기능 사이의 구멍을 못 본다.** 로그인도 갱신도 로그아웃도
  각각은 맞게 동작했다. 깨진 건 셋을 실제 사용 순서대로 엮었을 때뿐이었다. 상태를 남기는
  기능(저장소에 무언가 쌓이는 기능)은 "여러 번 반복한 뒤"를 확인하는 테스트가 따로 필요하다.
- 설계 문서에 "회전은 하지 않는다"라고 적어뒀는데, 구현은 새 토큰을 발급하는 쪽으로 갔다.
  **둘 중 어느 쪽이든 안전한데 반반 섞여서 위험해졌다.** 문서와 코드가 어긋나면 각각은
  말이 되는데 합쳐서 구멍이 생긴다. ADR-024를 고치고 왜 바꿨는지도 같이 적었다.
- Redis에 TTL을 걸어두면 "언젠가 사라진다"는 안심이 생기는데, 보안에서 2주는 영원에 가깝다.

**포트폴리오 각도** "JWT 리프레시 토큰을 Redis에 두고 로그아웃 시 삭제하도록 만들었다.
단위 기능 테스트는 모두 통과했지만, 로그인 → 갱신 → 로그아웃 순서로 엮은 테스트에서
로그아웃이 동작하지 않는 것을 발견했다. 갱신할 때 새 토큰만 발급하고 이전 토큰을 폐기하지
않아 유효한 리프레시 토큰이 계속 쌓이고 있었다. 토큰 회전을 도입해 어느 시점에도 유효한
리프레시 토큰이 기기당 하나만 존재하도록 고쳤다. 상태를 축적하는 기능은 단건 테스트가 아니라
시나리오 테스트가 필요하다는 걸 배운 사례다."

## 2026-09-23. 메일 서버를 껐더니 가입이 통째로 사라졌다

**상황** Phase 1, 이메일 인증(B단계). 가입하면 인증 토큰을 발급하고 메일을 보낸다.
처음에는 발송을 `AuthService.signUp()` 안에 그대로 두었다. 이 메서드에는
`@Transactional`이 붙어 있다.

```java
@Transactional
public SignUpResponse signUp(SignUpRequest request) {
    ...
    userRepository.save(user);
    emailVerificationService.send(user.getId(), user.getEmail());   // 트랜잭션 안
    return new SignUpResponse(SIGN_UP_MESSAGE);
}
```

테스트는 전부 통과했다. 테스트에서는 `JavaMailSender`를 가짜로 바꿔 끼워서 발송이 절대
실패하지 않았기 때문이다.

**증상** Mailpit 컨테이너를 내리고 가입을 시도했다.

```
$ docker compose stop mailpit
$ curl -i -X POST localhost:8080/api/auth/signup -d '{"email":"shin@hankuk.ac.kr",...}'

HTTP/1.1 500
{"status":500,"message":"서버에서 문제가 생겼습니다"}
```

```
ERROR ... com.bandal.common.ApiExceptionHandler : 처리하지 못한 예외

org.springframework.mail.MailSendException: Mail server connection failed.
Failed messages: org.eclipse.angus.mail.util.MailConnectException:
Couldn't connect to host, port: localhost, 1025; timeout -1;
```

DB를 보니 계정이 아예 없었다.

```
bandal=# select count(*) from users;
3        -- 가입 시도 전과 같다
```

**원인** 되돌릴 수 있는 일(DB 저장)과 되돌릴 수 없는 일(메일 발송)을 한 트랜잭션에
묶었다. 발송이 예외를 던지자 트랜잭션이 롤백되면서 방금 만든 계정까지 같이 사라졌다.
메일을 못 보낸 것은 사실이지만, 그게 계정을 만들지 말아야 할 이유는 아니다. 재전송
기능까지 만들어 놓고 정작 재전송할 계정이 없어지는 상황이었다.

반대 방향도 같은 뿌리다. 발송이 성공하고 그 뒤에 커밋이 실패하면 롤백은 DB만 되돌린다.
**이미 나간 메일은 되돌릴 수 없다.** 존재하지 않는 계정의 인증 링크가 남의 메일함에
도착해 있게 된다.

**시도하지 않은 것** 발송을 `try/catch`로 감싸는 방법이 먼저 떠올랐다. 예외는 막히지만
메일이 여전히 커밋 전에 나간다. 위의 반대 방향 문제가 그대로 남아서 버렸다.

`signUp()`을 트랜잭션 있는 메서드와 없는 메서드로 쪼개는 방법도 생각했다. 같은 빈 안에서
부르면 프록시를 거치지 않아 `@Transactional`이 아예 안 먹는다(self-invocation). 피하려면
빈을 하나 더 만들어야 한다.

**해결** 서비스는 사건만 발행하고, 발송은 커밋된 뒤에 실행되는 리스너가 맡는다.

```java
// AuthService
userRepository.save(user);
eventPublisher.publishEvent(new SignUpEvents.UserRegistered(user.getId(), user.getEmail()));
```

```java
// SignUpMailListener
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onUserRegistered(SignUpEvents.UserRegistered event) {
    try {
        emailVerificationService.send(event.userId(), event.email());
    } catch (Exception e) {
        // 여기서 던지면 커밋을 끝낸 호출자에게 올라가 500이 나간다.
        // 계정은 이미 만들어졌으니 가입은 성공으로 두고 로그만 남긴다
        log.error("인증 메일을 보내지 못했다. userId={}", event.userId(), e);
    }
}
```

`AFTER_COMMIT`은 커밋에 성공했을 때만 실행되고 롤백되면 아예 실행되지 않는다. 그래서
"없는 계정의 인증 메일"이 나갈 수 없다. 반대로 발송이 실패해도 커밋은 이미 끝났으니
계정은 남는다.

같은 조건으로 다시 해봤다.

```
### 1. 메일 서버를 내린 채로 가입한다
HTTP/1.1 202
{"message":"가입 확인 메일을 보냈습니다. 메일함을 확인해주세요"}

### 2. 계정은 만들어졌나
4|shin@hankuk.ac.kr|      -- 만들어졌고, 인증 시각은 비어 있다
```

메일 서버를 다시 올리고 재전송을 누르니 메일이 도착했고, 링크를 눌러 인증까지 이어졌다.

**배운 것** 트랜잭션은 DB만 되돌린다. 메일, 결제, 외부 API 호출처럼 밖으로 나가는 일은
트랜잭션이 책임질 수 없으므로 커밋 경계 밖으로 빼야 한다. 그리고 이 문제는 **가짜 객체로
바꿔 끼운 테스트가 끝까지 초록불이었다.** 실패하지 않는 가짜를 쓰면 실패했을 때의 동작은
검증되지 않는다. 지금은 "메일 서버가 죽어 있어도 가입은 성공한다" 테스트를 따로 두었다.

**한 줄 요약** "가입 트랜잭션 안에서 인증 메일을 보내다가, 메일 서버 장애 시 가입 자체가
롤백되는 문제를 발견했다. 되돌릴 수 없는 외부 호출을 커밋 경계 안에 둔 것이 원인이었다.
`@TransactionalEventListener(AFTER_COMMIT)`로 발송을 커밋 이후로 옮기고, 발송 실패는
로그로 남기되 가입은 성공 처리하도록 바꿨다. 가짜 객체가 항상 성공하는 탓에 테스트가
이 문제를 잡지 못했다는 것도 같이 배웠다."

## 2026-09-23. `Long.parseLong(null)`이 400으로 나가고 있었다

**상황** Phase 1, 이메일 인증. Redis에서 인증 토큰을 꺼내면서 지우는 코드다.

```java
public Long consume(String token) {
    if (token != null) {
        return Long.parseLong(redisTemplate.opsForValue().getAndDelete(TOKEN_PREFIX + token));
    }
    return null;
}
```

**증상** 테스트가 전부 통과했다. "같은 링크를 두 번 누르면 400이다"도, "지어낸 토큰,
이미 쓴 토큰, 만료된 토큰은 응답이 모두 같다"도 초록불이었다.

응답 본문을 확인하는 단언을 한 줄 넣자 정체가 드러났다.

```
Expecting actual:
  "{"status":400,"message":"Cannot parse null string"}"
to contain:
  "만료되었거나 이미 사용된 링크입니다"
```

**원인** `getAndDelete`는 키가 없으면 `null`을 돌려준다. 만료됐거나, 이미 썼거나,
지어낸 토큰이면 전부 이 경우다. 그 `null`이 `Long.parseLong`으로 들어가
`NumberFormatException`이 났다.

그런데 **`NumberFormatException`은 `IllegalArgumentException`의 자식**이다.
`ApiExceptionHandler`의 `handleIllegalArgument`가 이걸 덥석 잡아서 400을 만들어 줬다.
상태 코드가 우연히 맞아떨어진 것이다. 세 경우가 똑같이 터지니 "응답이 모두 같다"는
조건까지 만족했다.

**해결** `RefreshTokenStore.findUserId`와 같은 모양으로 맞췄다.

```java
public Long consume(String token) {
    if (token == null) return null;
    String userId = redisTemplate.opsForValue().getAndDelete(TOKEN_PREFIX + token);
    return userId == null ? null : Long.valueOf(userId);
}
```

**배운 것** 상태 코드만 보는 테스트는 "우연히 맞은 정답"을 잡지 못한다. 실패 응답은
메시지까지 확인해야 한다. 그리고 예외를 상속 관계로 잡는 핸들러는 의도하지 않은 예외까지
같이 삼킨다. 자바 표준 예외(`NumberFormatException`, `IllegalArgumentException`)를
API 응답 규칙에 직접 연결해 둔 대가다.

**한 줄 요약** "만료된 인증 토큰의 응답 메시지가 'Cannot parse null string'으로 나가고
있었는데, `NumberFormatException`이 `IllegalArgumentException`을 상속해 전역 예외

## 2026-09-29. `this.` 하나 때문에 테스트 80개가 엉뚱한 곳을 가리켰다

**상황** Phase 1, 컨트롤러·서비스를 다시 짜는 중(방 만들기). "계좌가 없으면 방을 만들 수
없다"(ADR-031)를 `GroupOrder` 생성자에 넣고, `User.registerAccount`에 null 방어를 넣었다.
같은 날 같은 종류의 실수가 두 번 나왔다.

**첫 번째 — 생성자에서 필드를 검사했다**

```java
public GroupOrder(User host, PickupSpot pickupSpot, ...) {
    if(!this.host.hasAccount()) throw new IllegalStateException("방장의 계좌 정보가 없습니다");
    this.host = host;
```

```
java.lang.NullPointerException:
  Cannot invoke "com.bandal.user.User.hasAccount()" because "this.host" is null
```

`this.host`는 바로 다음 줄에서 대입된다. 검사하는 시점에는 아직 `null`이다. 인자 `host`를
봐야 했다. 바로 터져서 원인을 찾기는 쉬웠다.

**두 번째 — 등록 메서드에서 필드를 검사했다**

```java
public void registerAccount(String bankName, String accountNumber, String accountHolder) {
    if(this.bankName == null || this.accountNumber == null || this.accountHolder == null) return;
    this.bankName = bankName;
    ...
```

**증상** 전체 테스트를 돌리니 224개 중 134개가 실패했다. 그중 80개가 같은 메시지였다.

```
GroupOrderTest               27 / 27  java.lang.IllegalStateException: 방장의 계좌 정보가 없습니다
OrderItemTest                16 / 16  java.lang.IllegalStateException: 방장의 계좌 정보가 없습니다
SettlementTest               12 / 12  java.lang.IllegalStateException: 방장의 계좌 정보가 없습니다
GroupOrderRepositoryTest      8 /  9  java.lang.IllegalStateException: 방장의 계좌 정보가 없습니다
ParticipationRepositoryTest   9 /  9  java.lang.IllegalStateException: 방장의 계좌 정보가 없습니다
OrderItemRepositoryTest       7 /  7  java.lang.IllegalStateException: 방장의 계좌 정보가 없습니다
```

메시지는 전부 `GroupOrder` 생성자를 가리켰다.

**시도한 것** 테스트 준비물에서 방장이 계좌 없이 만들어지고 있었다. 생성자에 새 규칙이
들어왔으니 당연한 실패라고 보고, 여섯 파일에 방장을 만든 직후
`host.registerAccount("한국은행", "110-123-456789", "김민수")`를 한 줄씩 넣었다.

다시 돌렸다. **결과가 한 글자도 바뀌지 않았다.** 여전히 134개, 같은 메시지.

**원인** 등록 메서드가 조용히 아무것도 안 하고 있었다. 처음 계좌를 등록하는 사용자는
필드가 전부 `null`이라 첫 줄에서 바로 `return`한다. 예외도 없고 로그도 없다.

```
host.registerAccount(...)   → this.bankName == null → return  (조용히 끝남)
host.hasAccount()           → false
new GroupOrder(host, ...)   → "방장의 계좌 정보가 없습니다"   ← 여기서 터짐
```

**에러가 난 곳과 원인이 있는 곳이 달랐다.** 80개 테스트가 전부 멀쩡한 생성자를
가리켰고, 진짜 원인은 `User`에 있었다. 조치를 했는데 결과가 그대로라는 게 유일한 단서였다.

**해결** 두 곳 모두 인자를 검사하도록 바꿨다. 등록 메서드는 인자에 `null`이 있을 때만
`return`한다(조용히 끝나는 건 그대로다). 생성자 맨 앞에는 `host == null` 검사를 추가해 NPE 대신
`IllegalArgumentException`으로 거절한다. 134개에서 55개로 줄었고, 남은 55개는 아직 다시
만들지 않은 엔드포인트다.

그러면서 "방장 없이 방을 저장하면 DB가 거부한다"는 테스트의 의미가 바뀌었다. 예전에는
DB의 NOT NULL 제약이 막았는데, 이제 생성자가 먼저 막는다. 테스트를 "방장 없이는 방을
만들 수조차 없다"로 고쳤다. DB 제약은 두 번째 방어선으로 남는다.

**배운 것**
- **들어온 값을 검사할 때는 인자를, 이미 가진 값을 검사할 때는 필드를 본다.** 생성자와
  등록 메서드는 앞쪽이고, 상태 전이 메서드는 뒤쪽이다.
- **조용한 실패는 원인을 멀리 숨긴다.** 첫 번째는 NPE로 그 자리에서 터져서 한 번에 찾았다.
  두 번째는 아무 일도 없이 끝나서 증상이 다른 클래스에서 나타났다. 정산의 `markPaid`가
  남의 요청을 조용히 통과시켰던 것(2026-09-26)과 같은 계열이다.
- **고쳤는데 아무것도 안 바뀌면, 고친 코드가 실행되지 않고 있는 것이다.** 결과가 그대로라는
  사실 자체가 가장 강한 단서였다.
- 엔티티 생성자에 불변식을 하나 넣으면, 그 엔티티를 만드는 **모든 테스트 준비물**이
  영향받는다. 서비스에 두었다면 서비스를 거치는 테스트만 영향받았을 것이다. 불변식을
  엔티티에 두는 대가다.

**한 줄 요약** "생성자와 등록 메서드에서 인자 대신 `this.` 필드를 검사하는 실수를 같은 날
두 번 했다. 두 번째는 조용히 `return`해서, 80개 테스트가 멀쩡한 `GroupOrder` 생성자를
가리키는 동안 진짜 원인은 `User`에 숨어 있었다. 준비물을 고쳤는데 결과가 한 글자도 안
바뀐 게 단서였다."

**덧붙임 (2026-10-01)** 이틀 뒤 같은 생성자에서 같은 실수가 또 나왔다. "방장 학교 == 거점 학교"
검사(ADR-036)를 넣으면서 인자 `pickupSpot` 대신 `this.pickupSpot`을 비교했다.

```
java.lang.NullPointerException:
  Cannot invoke "com.bandal.pickupspot.PickupSpot.getUniversity()" because "this.pickupSpot" is null
```

처음에는 설명(description)이 null일 때 나는 NPE가 먼저 터져서 이 에러가 가려져 있었다. 그걸
고치고 다시 돌리자 드러났다. 생성자 안에서 `this.`는 "아직 비어 있는 칸"이라는 걸 습관으로
만들어야 한다.

## 2026-10-01. Postgres가 한글 거점 이름을 가나다 거꾸로 정렬했다

**상황** Phase 1, 거점 목록(ADR-036). 리포지토리에 메서드 이름 쿼리
`findByUniversityIdOrderByNameAsc`를 만들고, 일부러 순서를 섞어 넣은 뒤 가나다순으로
나오는지 확인하는 테스트를 썼다.

**증상**

```
Expecting actual:
  ["중앙도서관 앞", "제1기숙사 로비", "공대 7호관 앞"]
to contain exactly (and in same order):
  ["공대 7호관 앞", "제1기숙사 로비", "중앙도서관 앞"]
```

넣은 순서(중앙, 공대, 민국대, 제1)도 아니고, 정확히 **가나다의 반대**였다. `Asc`를 썼는데.

**확인한 것** 테스트와 같은 `postgres:17` 이미지를 따로 띄워서 SQL로 직접 정렬해봤다.

```
DB 기본 정렬 규칙(collation): en_US.utf8, provider = libc

ORDER BY x                        → 중앙도서관 앞 / 제1기숙사 로비 / 공대 7호관 앞
ORDER BY x COLLATE "C"            → 공대 7호관 앞 / 제1기숙사 로비 / 중앙도서관 앞
ORDER BY x COLLATE "ko-KR-x-icu"  → 공대 7호관 앞 / 제1기숙사 로비 / 중앙도서관 앞
```

쿼리도 JPA도 문제가 아니었다. **DB의 문자열 정렬 규칙**이 한글을 이렇게 줄 세우고 있었다.
`ORDER BY`의 결과는 SQL만 보고 정해지지 않는다. 그 DB가 어떤 collation으로 만들어졌는지에
달려 있다. 공식 이미지는 기본값이 `en_US.utf8`이고, 이 규칙은 한글을 위한 것이 아니다.

**해결** DB에 정렬을 맡기지 않기로 했다. 거점 목록은 페이징이 없어서(ADR-036) 한 학교 거점을
전부 받은 뒤 서비스에서 `Collator.getInstance(Locale.KOREAN)`으로 정렬한다. 리포지토리 메서드는
`OrderByNameAsc`를 뺀 `findByUniversityId`로 바꿨다. DB 설정을 바꾸는 방법, COLLATE를 붙이는
방법은 ADR-036 버린 대안에 남겼다.

**배운 것**
- `ORDER BY` 결과는 SQL만으로 정해지지 않는다. DB가 어떤 정렬 규칙(collation)으로 만들어졌는지에
  달려 있다. 같은 쿼리도 환경이 다르면 다른 순서가 나올 수 있다.
- 일부러 순서를 섞어 넣고 정렬을 확인하는 테스트가 아니었으면 몰랐다. 데이터를 가나다순으로
  넣었으면 DB가 넣은 순서대로 돌려줘서 우연히 통과했을 수도 있다.
- 자바 정렬이 가능했던 건 페이징이 없어서다. 페이지를 나누는 목록이었다면 DB에서 정렬해야 한다.

**한 줄 요약** "`OrderByNameAsc`로 거점을 가나다순 정렬했는데 정확히 반대로 나왔다. 같은
Postgres 이미지를 띄워 SQL로 비교해보니 기본 정렬 규칙 en_US.utf8이 한글을 그렇게 세우고
있었다. 페이징이 없는 목록이라 DB 대신 자바에서 한국어 Collator로 정렬했다."

## 2026-10-01. 메뉴를 담아둔 채로 방을 나가니 500이 났다

**상황** Phase 1, 방 나가기(ADR-037). 담아둔 메뉴도 같이 지워야 한다는 건 알고 있었다. 방법을
고르기 전에 **일부러 참여 행만 지우는 순진한 버전**을 먼저 짜고 테스트를 돌렸다.

```java
participation.checkLeavable(userId, Instant.now());
participationRepository.delete(participation);
```

**증상** 메뉴가 없는 참여자는 잘 나갔다. 메뉴를 담아둔 참여자만 500이 났다.

```
Status expected:<204> but was:<500>

ERROR: update or delete on table "participation" violates foreign key constraint
       "fkobc8amtcss9cb2e8jm1qt0njm" on table "order_item"
  Detail: Key (id)=(68) is still referenced from table "order_item".
[delete from participation where id=?]
```

**원인** `order_item.participation_id`는 `participation.id`를 가리키는 외래 키다. DB는 아직 누가
가리키고 있는 행을 지우게 두지 않는다. 지우면 메뉴가 "없는 참여"를 가리키게 되니까.
JPA는 `delete from participation`만 보냈고, 메뉴에 대해서는 아무것도 하지 않았다. 참여가
단방향이라(ADR-019) `Participation`은 자기 메뉴가 있다는 것조차 모른다.

이 예외(`DataIntegrityViolationException`)는 핸들러가 따로 처리하지 않아서 마지막 `Exception`
핸들러로 떨어져 500이 됐다. 사용자 잘못이 아니라 우리 코드의 빈틈이니 500 자체는 맞는 신호다.

**해결** 세 방법(JPA cascade, 서비스에서 일괄 삭제, DB의 ON DELETE CASCADE)을 비교해서 서비스에서
지우기로 했다(ADR-037). `OrderItemRepository`에 `@Modifying` + `@Query`로
`DELETE FROM OrderItem oi WHERE oi.participation.id = :participationId`를 두고, 서비스가 참여 행보다
먼저 부른다. 메뉴가 몇 개든 DELETE 한 번이고, 지우는 일이 코드에 보이고, 단방향 구조를 안 건드린다.

**고치다가 하나 더: 벌크 DELETE와 영속성 컨텍스트** 리포지토리 테스트에서 "메뉴를 먼저 지우면 참여
행도 지울 수 있다"가 실패했다. 순서를 지켰는데도.

```
TransientPropertyValueException: Persistent instance of 'OrderItem' references an unsaved
transient instance of 'Participation' (persist the transient instance before flushing)
[OrderItem.participation -> Participation]
```

테스트는 같은 트랜잭션 안에서 메뉴를 `save`한 다음 지웠다. `@Query` DELETE는 영속성 컨텍스트를
거치지 않고 DB로 바로 간다. DB에서 메뉴는 사라졌지만 **컨텍스트에는 메뉴 객체가 그대로 살아 있었다.**
그 상태로 참여 행을 지우자, 컨텍스트에 남은 메뉴 객체가 "지워진 참여"를 가리키게 됐고, flush 때
Hibernate가 이걸 거부했다. 메시지의 `Persistent instance of 'OrderItem'`이 "컨텍스트가 아직 들고
있는 메뉴"다.

`@Modifying(flushAutomatically = true, clearAutomatically = true)`로 고쳤다. DELETE 전에 쌓인
변경을 먼저 보내고, DELETE 뒤에 컨텍스트를 비운다.

실제 나가기 요청에서는 이 문제가 안 났을 것이다. 그 트랜잭션은 메뉴를 불러오지 않으니까. 하지만
나중에 누가 같은 트랜잭션에서 메뉴를 먼저 읽으면(예: "나가면 이만큼 빠집니다"를 보여주려고) 그때
터진다. 테스트가 그 상황을 먼저 만들어 줬다.

**덤으로 걸린 것: 마감 정각** 같은 실행에서 "마감 시각 정각에는 이미 늦었다"도 실패했다.

```java
now.isAfter(this.groupOrder.getDeadlineAt())   // 정각이면 false → 통과해 버린다
```

`isAfter`는 "엄밀히 뒤"라서 정각에는 거짓이다. `checkJoinable`은 `!now.isBefore(deadlineAt)`
("앞이 아니면 늦었다")로 정각을 막고 있었다. 같은 경계를 두 메서드가 다르게 그었다.
`!now.isBefore(...)`로 맞췄다.

**배운 것**
- 외래 키는 "가리키는 쪽이 남아 있으면 가리켜지는 쪽을 못 지운다". 메뉴 없는 참여자만 테스트했으면
  못 봤을 버그다. 자식 행이 있는 경우를 따로 테스트해야 한다.
- `@Query`로 쓴 DELETE·UPDATE는 영속성 컨텍스트를 건너뛴다. DB와 컨텍스트가 어긋날 수 있어서
  `clearAutomatically`(와 그 전에 `flushAutomatically`)로 맞춘다.
- 시각 경계는 한 번 정했으면 모든 메서드가 같은 식으로 써야 한다. `isAfter`와 `!isBefore`는 정각에서 갈린다.

**한 줄 요약** "방 나가기를 참여 행만 지우는 순진한 버전으로 먼저 짰더니, 메뉴를 담은 사람만
외래 키 에러로 500이 났다. 서비스가 메뉴를 `@Modifying` DELETE 한 번으로 먼저 지우게 고쳤는데,
이번엔 그 벌크 DELETE가 영속성 컨텍스트를 건너뛰어서 남은 메뉴 객체가 flush 때 터졌다.
`clearAutomatically`로 컨텍스트를 비워 맞췄다."

## 2026-10-02. 메뉴 고치기 권한을 시각으로 나눴더니 손으로 마감한 방에서 거꾸로 동작했다

**상황** Phase 1, 메뉴 담기·고치기·빼기(ADR-038). 규칙은 "모집중이고 마감 시각 전에는 주인만,
마감(CLOSED)에는 방장만 고친다". `OrderItem.update`를 처음엔 시각으로 나눠서 짰다.

```java
if(!now.isBefore(groupOrder.getDeadlineAt())) {   // 마감 시각이 지났으면
    // 방장만
} else {
    // 주인만
}
this.editedByHost = true;
```

**증상** `OrderItemTest`의 고치기 14개 중 6개가 실패했다.
- 마감 시각(19:30) 전인 19:10에 방장이 손으로 마감한 방에서 **주인은 고쳐지고 방장은 거절됐다.** 규칙과 정반대다.
- 시각만 지나고 아직 모집중인 방에서 방장이 고칠 수 있었다.
- 취소된 방, 정산중인 방에서도 고쳐졌다.
- 주인이 자기 메뉴를 고쳐도 "방장이 수정함" 표시가 켜졌다.

**원인** "마감"이라는 말이 두 가지를 가리킨다. 마감 **시각**(deadlineAt)과 마감 **상태**(CLOSED).
둘은 늘 같이 움직이지 않는다. 최소주문금액이 일찍 차면 방장이 시각 전에 손으로 마감하고,
스케줄러가 없어서 시각이 지나도 상태는 모집중으로 남는다. 시각만 보면 상태가 무엇이든 같은
쪽으로 갈라진다. 표시는 조건 없이 켜고 있었다.

**해결** 상태로 먼저 나누고, 모집중일 때만 시각을 본다. 표시는 "고친 사람이 주인이 아닐 때"만 켠다.

```java
if(status == RECRUITING) { 시각 전이어야 하고 주인만 }
else if(status == CLOSED) { 방장만 }
else { 거절 }
```

**하나 더: 방 합계 자리에 내 합계** 서비스를 붙이자 API 테스트 3개가 실패했다.

```
JSON path "$.groupOrderTotal" expected:<32000> but was:<24000>
```

응답의 방 합계 자리에 `sumAmountByParticipationId`(그 사람 합계)를 넘기고 있었다. 나머지 테스트가
통과한 건 방 전체에서 한 사람만 메뉴를 담아서 두 값이 같았기 때문이다. 다른 사람 메뉴를 미리 넣어둔
테스트만 차이를 잡았다. `sumAmountByGroupOrderId`로 고쳤다.

**배운 것**
- 상태와 시각은 따로 움직인다. 권한을 상태로 나누고, 시각은 "상태가 아직 안 바뀐 경우"를 막는 보조로 쓴다.
- 두 값이 같아지는 데이터로는 둘을 헷갈린 버그를 못 잡는다. 테스트 데이터를 일부러 다르게 깔아야 한다.

**한 줄 요약** "메뉴 고치기 권한을 마감 시각으로 나눴더니, 방장이 시각 전에 손으로 마감한 방에서
주인은 고쳐지고 방장은 막혔다. 마감 시각과 마감 상태가 따로 움직인다는 걸 보고, 상태로 먼저 나누고
시각은 모집중일 때만 보게 고쳤다."

## 2026-10-06. 방장 검수 목록이 참여자 한 명당 쿼리를 두 번씩 더 날렸다 (N+1)

**상황** Phase 1, 방장 검수 목록(ADR-039). 참여자마다 메뉴와 닉네임을 붙여 돌려준다. 순진한 버전으로 먼저 짰다.

```java
List<Participation> participations = participationRepository.findByGroupOrderIdOrderByJoinedAtAscIdAsc(groupOrderId);
participations.stream()
    .map(p -> ParticipantItemsResponse.of(p,
        orderItemRepository.findByParticipationId(p.getId()),   // 사람마다 메뉴 조회
        groupOrder.isHost(p.getUser().getId())))                // of() 안에서 닉네임을 읽는다
```

**증상** 테스트에서 Hibernate 통계(`getPrepareStatementCount`)로 요청 하나의 SQL 수를 셌다.
참여자 2명일 때 7번, 5명일 때 13번. 사람이 늘수록 쿼리가 는다.

```
[2명일 때 쿼리 7번, 5명일 때 13번]
```

**원인** 3 + 2N으로 나뉜다.
- 고정 3번: 인증 필터의 사용자 조회, 방 조회, 명단 조회.
- 사람당 1번: 반복문 안의 `findByParticipationId`.
- 사람당 1번: 명단의 user가 지연 로딩 프록시라서, 닉네임을 읽는 순간 user를 따로 가져온다.
  필터가 방장 user를 이미 읽었지만 그건 다른 영속성 컨텍스트라 여기서는 다시 읽는다.
- `isHost(...)`의 `getUser().getId()`와 `getHost().getId()`는 0번. 프록시는 자기 id를 알고 있다.

**해결** 한 번에 하나씩 고치며 다시 셌다.
1. 명단을 `JOIN FETCH p.user` 쿼리(`findRosterWithUser`)로 바꿨다. 2명 5번, 5명 8번(3 + N). 닉네임 쪽 N이 사라졌다.
2. 반복문 밖에서 방의 메뉴 전부를 한 번에 받고(`findByGroupOrderId`), `groupingBy`로 참여 id별로 묶어
   반복문에서는 Map에서 꺼냈다. 메뉴 없는 사람은 `getOrDefault(id, List.of())`. 2명 4번, 5명 4번.

**배운 것**
- 지연 로딩 프록시는 id만 꺼낼 때는 쿼리가 안 나가고, 다른 필드를 읽는 순간 나간다. 어느 줄이
  쿼리를 부르는지는 코드만 봐서는 안 보이고, 세어 봐야 보인다.
- "쿼리 수가 인원과 무관한가"는 2명과 5명의 쿼리 수가 같은지로 테스트할 수 있다. 숫자를 박지 않아서
  필터 쿼리 같은 고정분이 바뀌어도 깨지지 않는다.
- 반복문 안의 리포지토리 호출은 반복문 밖으로 꺼내 한 번에 받고, 메모리에서 나누면 된다.

**한 줄 요약** "방장 검수 목록을 순진하게 짰더니 참여자 2명에 7번, 5명에 13번 쿼리가 나갔다.
닉네임 지연 로딩과 사람마다 메뉴 조회가 각각 N번이었다. 명단을 JOIN FETCH로, 메뉴를 방 단위로 한 번에
받아 groupingBy로 나눠서 인원과 상관없이 4번으로 고정했다."

## 2026-10-06. 마감 시각이 지난 방의 마감을 자동 규칙에 맡겼는데, 맡긴 뒤에도 메서드가 계속 흘러내려갔다

**상황** Phase 1, 방장 마감 API(ADR-040). 마감 시각이 지난 뒤 누른 마감 버튼은 거절하지 않고 자동 마감
규칙(`closeAtDeadline`)으로 처리하기로 했다. `closeByHost`에 `now`를 받게 하고, 모집중·방장 검사 다음에
시각을 보게 고쳤다.

**첫 번째 시도와 증상** `GroupOrderTest` 41개 중 18개 실패. 마감 시각 전의 평범한 마감까지 전부 같은 예외였다.

```java
if(!Instant.now().isBefore(now)) {
    throw new IllegalStateException("마감 시각이 지났으므로 마감 처리 됩니다");
}
```

```
IllegalStateException: 마감 시각이 지났으므로 마감 처리 됩니다
```

**원인** 두 가지가 겹쳤다.
- 비교 대상이 `deadlineAt`이 아니라 실제 시계(`Instant.now()`)였다. 테스트가 넘긴 `now`(2026-09-17)는 실제
  현재보다 늘 과거라 조건이 항상 참이었다. 엔티티 안에서 시계를 보면 시각을 인자로 받는 의미(ADR-016)도 사라진다.
- 시각이 지나면 처리하지 않고 예외를 던졌다. 서비스에서는 롤백되니 방은 그대로 모집중, 고치기 전과 같다.

**두 번째 시도와 증상** `now.isBefore(deadlineAt)`으로 비교를 고치고 `closeAtDeadline`을 부르게 했다.
3개가 남았다.

```
금액이 모자라면 거절하지 않고 자동 취소된다   → AssertionError (예외가 났다)
방장 혼자면 자동 취소된다                    → 방장을 포함해 2명 이상이어야 마감할 수 있습니다
정확히 마감 시각이면 이미 지난 것으로 본다    → 최소주문금액에 1원 모자랍니다
```

**원인** `closeAtDeadline`을 부른 뒤 `return`이 없었다. 자동 규칙이 상태를 `CANCELED`로 바꾼 다음,
아래의 수동 규칙까지 흘러내려가 인원·금액 예외를 던졌다. 서비스였다면 이 예외로 롤백돼 취소가 저장되지 않는다.
조건을 채운 방은 통과했는데, 자동 규칙이 `CLOSED`로 바꾸고 흘러내려가 수동 규칙도 통과해 `CLOSED`를 한 번 더
넣었을 뿐이다. 결과가 우연히 같아서 버그가 가려졌다.

**해결** `closeAtDeadline(...)` 다음에 `return;`. 특별한 경우를 먼저 처리하고 일찍 빠져나간다(early return).

**배운 것**
- 시각 비교는 "무엇과 무엇을" 비교하는지가 전부다. 같은 클래스의 `checkJoinable`, `closeAtDeadline`이
  이미 `now`와 `deadlineAt`을 비교하고 있었다. 같은 모양으로 쓰면 틀릴 일이 없다.
- 다른 메서드에 처리를 맡겼으면 거기서 끝내야 한다. 끝내지 않으면 아래 코드가 맡긴 결과를 덮거나 예외로 되돌린다.
- 조건을 채운 경우만 테스트했다면 두 번째 버그는 안 보였다. 실패해야 할 경로(모자란 금액, 혼자, 정각)를 따로 테스트해야 한다.

**한 줄 요약** "마감 시각이 지난 방의 마감 버튼을 자동 마감 규칙에 맡기도록 고쳤는데, 맡긴 뒤 return이 없어서
아래의 수동 규칙까지 흘러내려가 예외가 났다. 서비스였다면 롤백돼 취소가 저장되지 않았을 것이다. 조건을 채운 방은
우연히 결과가 같아 통과해서, 실패 경로 테스트만 이걸 잡았다."

## 2026-10-06. 계좌 등록이 거절됐는데 은행 이름만 바뀐 채로 남았다

**상황** 계좌 등록(`User.registerAccount`)이 null을 받으면 조용히 return하던 걸 예외로 바꿨다(ADR-041).
계좌번호는 숫자만 남긴 뒤에 비어 있는지도 보기로 했다(`"---"`는 DTO 형식 검사를 통과하지만 숫자가 없다).

**증상** `UserTest` 7개 중 2개 실패.

```
거절되면 원래 계좌가 그대로 남는다  → UserTest.java:93
expected: "한국은행"  but was: "우리은행"
```

한국은행 계좌가 있는 사람이 `("우리은행", "", "이영희")`로 다시 등록했다. 예외는 났는데 은행만 우리은행으로 바뀌어
있었다. 계좌번호는 한국은행 것 그대로다.

**원인** 대입과 검사가 섞여 있었다.

```java
this.bankName = bankName;                           // 먼저 바꾸고
String tempNumber = accountNumber.replaceAll(...);
if (tempNumber.isBlank()) throw ...;                // 그다음에 거절
```

예외가 나도 이미 바뀐 필드는 되돌아가지 않는다. 남은 객체는 "우리은행 + 한국은행 계좌번호"라는 존재하지 않는
계좌다. 참여자가 이걸 보고 송금하면 엉뚱한 계좌로 가거나 실패한다.

나머지 하나는 예금주 `"   "`가 통과한 것이다. null만 보고 공백은 보지 않았다. API에서는 DTO의 `@NotBlank`가
먼저 막아서 엔티티를 직접 부를 때만 드러난다.

**해결** 세 값을 지역 변수로 전부 검사하고(계좌번호는 숫자만 남긴 값으로), 다 통과한 뒤에 세 필드를 한꺼번에
대입했다. 은행과 예금주에는 `isBlank()` 검사를 더했다.

**배운 것**
- 서비스에서 불렸다면 예외로 트랜잭션이 롤백돼 DB에는 안 남는다. 그래서 API 테스트만 있었으면 안 보였을 것이다.
  롤백은 DB를 되돌리지 메모리의 객체를 되돌리지 않는다. 엔티티는 롤백에 기대지 말고 스스로 "전부 바뀌거나 하나도
  안 바뀌거나"를 지켜야 한다.
- 검사 다 하고 나서 대입한다. 변환(숫자만 남기기)이 검사에 필요하면 지역 변수로 먼저 만든다.

**한 줄 요약** "계좌 등록 검사를 고치면서 은행을 먼저 대입하고 계좌번호를 나중에 검사했더니, 거절된 요청이
은행만 바꿔놓아 존재하지 않는 계좌가 남았다. 롤백은 DB만 되돌린다. 검사를 전부 끝낸 뒤 한꺼번에 대입해서 고쳤다."

## 2026-10-07. 배달비 입력이 500으로 끝났는데, 그 뒤에서 정산표만 저장되고 방은 마감으로 남아 있었다

**상황** 배달비를 입력하면 방이 `정산중`으로 넘어가고 정산표가 생기는 `SettlementService.start`를 짰다(ADR-042).
방을 찾고, `startSettlement`로 전이하고, 사람별 메뉴 합계로 계산기를 돌리고, `Settlement` 행을 `saveAll`로 저장하고,
`SettlementResponse.of`로 응답을 만든다. 메서드에 `@Transactional`이 없었다.

**증상** `SettlementApiTest` 배달비 입력 테스트 중 성공해야 하는 7개가 전부 500. 거절 케이스(방장 아님, 음수, 401 등)는
통과했다. 서비스 앞부분에서 끝나서 문제 지점까지 가지 않았기 때문이다.

```
org.hibernate.LazyInitializationException: Could not initialize proxy [com.bandal.user.User#1] - no session
    at com.bandal.user.User$HibernateProxy.getBankName(Unknown Source)
    at com.bandal.settlement.dto.HostAccountResponse.of(HostAccountResponse.java:14)
    at com.bandal.settlement.dto.SettlementResponse.of(SettlementResponse.java:28)
    at com.bandal.settlement.SettlementService.start(SettlementService.java:62)
```

**원인** 트랜잭션이 없으니 리포지토리 호출마다 짧은 트랜잭션이 따로 열리고 닫혔다. `open-in-view: false`라 컨트롤러까지
세션을 열어두지도 않는다.

- `findById`가 끝나는 순간 방은 영속성 컨텍스트 밖으로 나갔다. 방의 `host`는 LAZY라 id만 아는 프록시다.
  응답을 만들며 `getBankName()`을 부르자 프록시가 DB에 가려 했고, 세션이 없어 터졌다. `isHost`는 `getId()`만 써서
  무사했다. 프록시는 id만은 세션 없이 알려준다.

500보다 나쁜 게 로그에 숨어 있었다.

- **방 상태 UPDATE는 한 번도 나가지 않았다.** 로그의 `update group_order`는 11번이었는데, 테스트가 `closedRoom()`으로
  마감시킬 때 나간 수와 정확히 같았다. `status = SETTLING`은 관리 밖의 객체에 적혀서 변경 감지가 보지 못했다.
- **정산표 INSERT는 나갔다.** `saveAll`은 자기 트랜잭션을 열고 커밋한다. 참여자 줄의 `9000`, `10750`이 바인딩된 게 보였다.

DB에는 "마감 상태인데 정산표가 있는 방"이 남았다. 방장이 다시 입력하면 엔티티는 아직 마감이라 통과시키고, 정산표가
한 벌 더 쌓인다.

**해결** `start`에 `@Transactional`을 붙였다. 조회, 전이, 저장, 응답 변환이 한 세션 안에서 일어나서 프록시가 읽히고,
끝날 때 방 UPDATE와 정산표 INSERT가 같이 커밋된다. 중간에 하나가 터지면 같이 롤백된다. 배달비 입력 13개 통과.

**배운 것**
- `@Transactional`이 빠지면 단순히 "저장이 안 된다"로 끝나지 않는다. `save`를 직접 부른 것은 저장되고, 변경 감지에
  기댄 것은 사라진다. 반만 저장된다.
- 이번엔 응답 변환의 LAZY 로딩이 우연히 500을 내줘서 알아챘다. 응답에 계좌가 없었다면 200이 나가고, 방은 마감인데
  정산표가 있는 상태로 조용히 쌓였을 것이다. 상태 전이 테스트는 응답만 보지 말고 DB의 상태도 확인해야 한다.
- 로그에 찍힌 SQL을 세어보는 게 원인을 찾는 가장 빠른 길이었다. "나갔어야 할 UPDATE가 없다"는 예외 메시지에는 안 나온다.

**한 줄 요약** "정산 시작 서비스에 `@Transactional`을 빠뜨렸더니 LAZY 프록시 때문에 500이 났는데, 로그를 세어보니
방 상태 UPDATE는 안 나가고 정산표 INSERT만 커밋돼 있었다. 변경 감지는 트랜잭션 안의 객체만 본다. 메서드 전체를 한
트랜잭션으로 묶어서 고쳤다."

## 2026-10-12. 방 취소가 200에 CANCELED를 돌려줬는데 DB의 방은 그대로였다

**상황** 방장 취소 API(`POST /api/group-orders/{id}/cancel`, ADR-048)의 서비스 `GroupOrderService.cancel`을 짰다. 방을 찾고,
`cancelByHost`로 상태를 바꾸고, 마감과 같은 방 상세 응답을 만든다. 바로 위 `close`를 보고 짰는데 `@Transactional`이 빠졌다.
10-07에 같은 이유로 500을 겪었고, 사흘 전에는 "DB를 고치는 함수도 아닌데 왜 붙나"를 같이 이야기한 직후였다.

**증상** 전체 516개 중 취소 테스트 9개 실패. 이번엔 500이 아니었다.

```
모집중인 방은 사유 없이 취소하면 200이고 취소 종류가 남는다
expected: CANCELED
 but was: RECRUITING
    at GroupOrderApiTest.cancelsRecruitingWithoutReason(GroupOrderApiTest.java:590)
```

- 응답 검사(`$.status`가 `CANCELED`, `$.cancelType`이 `HOST_WHILE_RECRUITING`)는 전부 통과했다. 590줄은 DB에서 방을 다시
  읽어 확인하는 줄이다.
- 같은 방을 다시 취소하면 409가 아니라 200. 취소한 뒤에도 "보냈어요", 확인 취소, 주문완료가 200으로 통과했다.
  정산 조회의 `status`는 `SETTLING`이었다.

**원인** 10-07과 같다. 트랜잭션이 없으니 `findById`가 끝나는 순간 방은 관리 밖의 객체가 됐고, `status = CANCELED`는 그
자바 객체에만 적혔다. 변경 감지가 보지 못해 UPDATE가 나가지 않았다.

10-07과 다른 점은 터지지 않았다는 것이다. 10-07은 응답을 만들며 방장 계좌(`getBankName()`)를 읽다가 LAZY 프록시가
세션 없이 DB에 가려 해서 500이 났다. 이번 `GroupOrderResponse`는 방장과 수령지에서 `getId()`만 읽는다. 프록시는 id를 세션
없이 알려준다. 그래서 메모리의 객체로 그럴듯한 응답이 만들어져 200으로 나갔다. 10-07에 "응답에 계좌가 없었다면 200이
나가고 조용히 쌓였을 것"이라고 적어둔 경우가 그대로 일어났다.

**해결** `cancel`에 `@Transactional`을 붙였다. 516개 전부 통과.

**배운 것**
- `@Transactional`이 빠졌을 때 가장 나쁜 결과는 500이 아니라 거짓 200이다. 화면은 "취소됐습니다"를 띄우고, 참여자는
  계속 송금할 수 있고, 방장은 같은 방을 몇 번이고 다시 취소할 수 있다.
- 500이 나느냐 마느냐는 응답 DTO가 LAZY 필드를 얼마나 읽느냐라는, 버그와 상관없는 우연에 달려 있다.
- 이번에 잡은 건 테스트가 응답 다음에 DB를 다시 읽어서다. 상태 전이 테스트에 DB 확인을 넣은 10-07의 교훈이 그대로
  쓰였다.
- 옆 메서드를 보고 따라 쓸 때는 본문만이 아니라 어노테이션까지 같이 봐야 한다.

**한 줄 요약** "방 취소 서비스에 `@Transactional`을 빠뜨렸더니 응답은 200에 CANCELED였는데 DB는 그대로였다. 응답 DTO가
프록시의 id만 읽어서 500조차 나지 않았다. 응답 뒤에 DB를 다시 읽는 테스트가 잡아냈다."

## 2026-10-13. 자동 취소된 정산중 방에서 송금한 사람이 자기 정산 정보를 못 봤다

**상황** 스케줄러가 24시간 동안 주문하지 않은 정산중 방을 자동 취소하게 했다(ADR-051, 052). 새 취소 종류 `SETTLING_TIMEOUT`도
정산중 취소로 봐야 환불 흐름이 열린다. 그래서 `GroupOrder.isCanceledWhileSettling()`을 고쳤다.

```java
return this.cancelType == CancelType.HOST_AFTER_SETTLING || this.cancelType == CancelType.SETTLING_TIMEOUT;
```

**증상** 엔티티 테스트 하나가 실패했다. 환불 버튼 테스트는 전부 통과했는데 정산 조회만 막혔다.

```
자동 만료 | 자동 취소된 정산중 방은 정산 정보를 볼 수 있다 | AssertionError
```

API로 치면 B가 10,750원을 보내고 방장이 사라져 방이 자동 취소됐는데, B가 정산 정보를 열면 409 "정산이 시작된 방만 정산
정보를 볼 수 있습니다"가 나온다. 환불 대기 표시도, 돌려받았어요를 누를 줄 id도 볼 수 없다.

**원인** 같은 조건이 두 곳에 있었다. 10-12에 환불 대상을 판단하려고 `isCanceledWhileSettling()`을 만들었는데, 그보다 먼저
있던 `checkSettlementVisible()`은 같은 판단을 자기 안의 지역 변수로 따로 하고 있었다.

```java
boolean canceledWhileSettling = this.cancelType == CancelType.HOST_AFTER_SETTLING;
```

그날 "새 메서드로 바꿀지는 정해"라고 남겨두고 그대로 뒀다. 이번에 메서드 쪽만 고쳤으니 환불 버튼 다섯 개(메서드를 부른다)는
새 종류를 받았고, 조회(복사본을 쓴다)는 받지 못했다.

**해결** `checkSettlementVisible()`이 `isCanceledWhileSettling()`을 부르게 바꿨다. 조건은 이제 한 곳에만 있다.

**배운 것**
- 같은 규칙을 두 곳에 적어 두면 지금은 맞아도 다음에 규칙이 바뀔 때 한쪽만 고쳐진다. 그날은 둘이 같아서 아무 문제가
  없었고, 문제는 사흘 뒤 규칙이 늘어나는 순간에 생겼다.
- 깨진 쪽은 버튼이 아니라 조회였다. 돈을 보낸 사람이 "내 돈이 어떻게 됐는지"를 못 보는 쪽이라 더 나쁘다.
- 새 상태 값(enum)을 추가할 때는 그 값을 비교하는 곳을 전부 찾아봐야 한다. `cancelType ==`로 검색했으면 바로 보였다.

**한 줄 요약** "정산중 취소를 판단하는 조건이 메서드와 지역 변수 두 곳에 있었는데, 새 취소 종류를 추가하면서 메서드만
고쳐 자동 취소된 방의 정산 조회가 409로 막혔다. 조건을 한 곳으로 모아 고쳤다."
## 2026-10-13. 스케줄러가 방 하나에서 터지자 뒤의 방을 아무도 처리하지 않았다

**상황** 1분마다 멈춘 방을 넘기는 스케줄러(ADR-051, 052)를 일부러 가장 단순하게 먼저 짰다. 후보 id를 받아 방마다 서비스를
부르는 `for` 루프 하나다. 서비스 `expire`는 방마다 `@Transactional`이다.

```java
for (Long id : ids) {
    groupOrderService.expire(id, now);
}
```

**증상** 마감된 지 3시간이 넘은 방 셋 중 가운데 방에서만 예외가 나게 한 테스트(DB 연결이 잠깐 끊긴 상황 흉내)가 실패했다.

```
방 하나를 넘기다 실패해도 나머지 방은 넘어간다
Expecting code not to raise a throwable but caught
  "java.lang.IllegalStateException: 이 방만 실패한다
	at com.bandal.grouporder.GroupOrderService.expire(GroupOrderService.java:140)
	...
	at org.springframework.transaction.interceptor.TransactionInterceptor.invoke(TransactionInterceptor.java:130)
```

**원인** 방 1은 자기 트랜잭션에서 커밋됐다. 방 2의 예외는 트랜잭션을 롤백시키고 그대로 `for` 밖으로 올라가 `runAt` 전체를
끝냈다. 방 3은 차례가 오지 않았다. 트랜잭션은 롤백할 뿐 예외를 삼키지 않는다.

실제로 돌면 더 나쁘다. 스프링 스케줄러는 예외를 로그로 남기고 1분 뒤에 다시 부르지만, 쿼리가 `ORDER BY id`라 다음에도 방 2가
방 3보다 먼저 나온다. 방 2가 계속 실패하는 한 그 뒤의 방은 영원히 처리되지 않는다. 방 하나가 스케줄러 전체를 막는다.

**해결** 루프 안에서 방마다 `try-catch`로 잡고, 실패한 방의 id를 `log.error`로 남긴 뒤 다음 방으로 간다. 실패한 방은 다음
1분에 다시 시도된다. 618개 전부 통과. 로그에 `멈춘 방을 넘기지 못했습니다. groupOrderId=13`이 찍히는 것도 확인했다.

이게 되는 건 `expire`가 방마다 자기 트랜잭션이기 때문이다. 예외가 루프까지 올라왔을 때 그 방은 이미 롤백이 끝났고, 다른 방의
커밋에는 영향이 없다. `runAt` 전체에 `@Transactional`을 걸었다면 방들이 한 트랜잭션에 묶여서, 예외를 잡아도 이미 처리한 방까지
같이 롤백 대상이 된다.

**배운 것**
- "방들은 서로 독립적"이라는 건 요구사항이고, 코드가 저절로 그렇게 되지는 않는다. 독립성은 트랜잭션 경계(방마다)와 예외
  경계(방마다) 둘 다로 만들어야 한다.
- 순서가 정해진 배치에서 계속 실패하는 항목 하나는 뒤의 모든 항목을 막는다.
- 잡아서 넘기되 반드시 남긴다. 조용히 삼키면 방 2가 영원히 멈춰 있어도 아무도 모른다.

**한 줄 요약** "스케줄러 루프에서 방 하나가 예외를 던지자 뒤의 방이 처리되지 않았고, 순서가 고정이라 매분 같은 방에서 막힐
구조였다. 방마다 트랜잭션과 try-catch를 두고 실패한 id를 로그로 남겨 고쳤다."

## 2026-10-14. 쿼리 하나의 패키지 이름 오타로 상관없는 테스트 394개가 같이 쓰러졌다

**상황** 내 방 목록(ADR-053)의 진행 중 탭 쿼리를 `@Query`로 직접 짰다. 상태 비교에 enum 상수를 JPQL 안에 전체 이름으로
적는 쿼리다.

**증상** 전체 테스트 652개 중 394개가 실패했다. 내 방 목록과 상관없는 회원가입, 로그인 테스트까지 쓰러졌다. 실패한 테스트는
전부 스프링을 띄우는 테스트였고, 스프링 없이 도는 엔티티 테스트(`GroupOrderTest`, `SettlementTest` 등)는 통과했다.
맨 아래 원인부터 위로 읽으면 이렇다.

```
Caused by: org.hibernate.query.SemanticException: Could not interpret path expression 'com.bandal.groupOrder.GroupOrderStatus.RECRUITING'
Caused by: org.springframework.beans.factory.BeanCreationException: Error creating bean with name 'groupOrderRepository'
  ... Query validation failed for 'SELECT go FROM Participation p JOIN p.groupOrder go WHERE p.user.id = :userId
  AND (go.status IN (com.bandal.groupOrder.GroupOrderStatus.RECRUITING, ...'
Caused by: org.springframework.beans.factory.UnsatisfiedDependencyException: Error creating bean with name 'groupOrderController'
  ... Error creating bean with name 'groupOrderService' ...
```

**원인** 패키지 이름을 `com.bandal.grouporder`가 아니라 `com.bandal.groupOrder`로 적었다. 같은 쿼리 바로 앞의
`p.groupOrder`는 엔티티 필드 이름이라 카멜케이스가 맞고, 패키지 이름은 폴더 이름이라 전부 소문자다. 둘이 똑같이 생겨서
섞였다. 같은 쿼리 안에서도 참고본을 복사한 줄(`com.bandal.grouporder.CancelType.HOST_WHILE_SETTLING`)은 맞고 손으로 친
줄은 틀려 있었다.

하이버네이트는 먼저 `com.bandal.groupOrder.GroupOrderStatus`라는 클래스를 찾는다. 대소문자가 달라 없으니, `go.status` 같은
엔티티 필드 경로로 보고 다시 해석한다. `com`이라는 별칭도 필드도 없으니 "경로 표현식을 해석할 수 없다"가 된다. 메시지가
오타 자리를 짚어 주지 않는다.

테스트가 394개나 쓰러진 건 `@Query`가 앱이 뜰 때 미리 검사되기 때문이다. 검사에 실패하면 `GroupOrderRepository` 빈이
만들어지지 않고, 그 리포지토리를 받는 서비스, 그 서비스를 받는 컨트롤러가 줄줄이 만들어지지 않아서 스프링 컨텍스트 전체가
뜨지 못한다. 그 컨텍스트를 쓰는 테스트는 무엇을 검사하든 다 실패한다.

**시도한 것** 처음 돌렸을 때는 쿼리가 아직 짜는 중이라(`go.cancelType IN ()`이 비어 있었다) 그 탓으로 보일 수 있었다. 다 짠
뒤에 다시 돌려도 같은 `SemanticException`이 남아서 빈 괄호가 아니라 경로가 원인이라는 게 드러났다.

**해결** 따옴표 안에 찍힌 경로를 참고본과 한 글자씩 비교해 `groupOrder`를 `grouporder`로 고쳤다(다섯 군데). 652개 전부 통과.

**배운 것**
- 테스트 수백 개가 한꺼번에 깨지면 테스트 하나하나를 보지 말고 맨 아래 `Caused by`부터 본다. 대개 원인은 하나다.
- `@Query`(그리고 메서드 이름으로 만드는 쿼리)는 앱이 뜰 때 검사된다. 답답하지만 덕분에 배포 전에 잡힌다. 문자열 쿼리인데도
  런타임 첫 호출까지 기다리지 않는다.
- `SemanticException: Could not interpret path expression '...'`은 오타 자리를 알려 주지 않는다. 따옴표 안의 문자열을
  정답과 나란히 놓고 비교하는 게 가장 빠르다.
- JPQL 안의 enum 상수는 패키지 경로까지 적어야 해서 오타가 나기 쉽다. 파라미터로 넘기면(`:statuses`) 문자열 안의 경로가
  사라진다.

**한 줄 요약** "JPQL에 적은 enum 경로의 패키지 이름 대소문자 하나 때문에 리포지토리 빈이 만들어지지 않았고, 스프링 컨텍스트가
통째로 뜨지 못해 상관없는 테스트 394개가 같이 실패했다. `@Query`가 기동 시점에 검사된다는 걸 이때 실제로 봤다."

**상황** CI(ADR-057)를 붙인 첫 PR(#1)을 열고 바로 merge했다. 기록을 보면 PR 검사는 02:00:37에 시작했고 merge는 02:00:40,
백엔드 테스트가 끝난 건 02:03:47이다. 테스트 결과를 보기 전에 main에 들어갔다. 이번에는 초록이었지만 빨간불이었어도
그대로 들어갔을 것이다. 이때 main은 `protected: false`였다.

**원인** 워크플로를 만드는 것과 그 결과로 merge를 막는 것은 별개다. CI는 검사를 돌리고 결과를 표시할 뿐이고, 막는 건
브랜치 보호 규칙이 한다. 규칙이 없으면 PR 화면의 merge 버튼은 검사가 도는 중에도 눌린다.

**해결** main에 보호 규칙을 걸었다. PR 필수(승인 수는 0. 혼자라 자기 PR을 승인할 수 없다), 필수 검사 `backend`와
`frontend`, 브랜치가 최신 main이어야 함, 관리자도 예외 없음. 필수 검사 목록은 그 검사가 최근 7일 안에 한 번은 돌아야 검색된다.

그다음 일부러 실패하는 테스트(`1 + 1`이 `3`)를 넣은 PR(#2)을 열었다. `backend`가 ❌(failure), 화면 폴더는 안 건드려서
`frontend`는 건너뜀(skipped)이었다. 실패 테스트를 지운 커밋을 같은 PR에 올려 ✅가 된 뒤(02:36:47) merge했다(02:37:12).
main에 들어온 뒤의 실행도 ✅였다.

같은 실패 실행에 경고가 같이 붙었다. 쓰던 Actions 버전(checkout, setup-java 등 v4)이 Node.js 20 기반이라 낡았다는 것,
`ubuntu-latest`가 10월 19일부터 Ubuntu 26으로 바뀐다는 것. 버전을 올리고 서버 OS를 `ubuntu-24.04`로 고정했다. 다음
실행에서 경고가 사라졌다.

**배운 것**
- CI는 "알려 주는" 장치고, "막는" 건 브랜치 보호다. 둘을 같이 걸어야 "빨간불이면 못 들어간다"가 성립한다.
- 혼자 하는 저장소에서 "승인 필요"를 켜면 영영 merge할 수 없다. 필요한 건 승인이 아니라 검사 통과다.
- 실패 실행의 경고(annotation)도 읽는다. 버전이 낡았다는 신호가 거기 먼저 뜬다.

**한 줄 요약** "CI를 붙인 첫 PR이 테스트가 끝나기 3분 전에 merge됐다. CI는 결과를 보여 줄 뿐이고 막는 건 브랜치 보호라는
걸 알고 규칙을 건 뒤, 일부러 깨뜨린 PR의 필수 검사가 ❌로 떨어지는 걸 확인했다."

## 2026-10-15. 방이 자기 인원을 들고 있게 하자 10명 중 1명만 들어갔다. 진 9명은 500을 받는다


10명이 모두 버전 0을 읽고 `participant_count = 4`로 고치려 했고, 먼저 커밋한 한 명이 버전을 1로 올렸다. 나머지의

**같이 겪은 것**

- 테스트 픽스처가 참여 행을 리포지토리로 직접 넣던 곳은 인원 칸이 안 늘어서 어긋났다. 실제 참여 API로 채우거나 인원 칸을

**남은 것** 진 9명이 받는 예외를 `ApiExceptionHandler`가 따로 처리하지 않아 500으로 나간다.

**한 줄 요약** "참여할 때 방 행의 인원 칸을 고치게 하자 @Version 검사가 실제로 걸려 10명 중 1명만 들어갔다. 대신 진 9명은 500을 받는다."

## 2026-10-15. 재시도 반복문을 같은 서비스에 두자 10명이 전부 LazyInitializationException으로 떨어졌다

**상황** 버전 충돌로 진 사람을 다시 시도하게 하려고 `ParticipationService`에 `joinWithRetry`(`@Transactional` 없음)를 두고,
그 안에서 `join`(`@Transactional`)을 최대 3번 부르게 했다. 컨트롤러와 동시성 테스트가 `joinWithRetry`를 부른다.

두 테스트(자리 1개에 10명, 자리 3개에 10명)를 세 번씩 돌렸다. 매번 같은 결과였다.

```
성공 0명, 방 인원 그대로
실패 {LazyInitializationException: Could not initialize proxy [com.bandal.pickupspot.PickupSpot#1] - no session = 10}
```

버전 충돌까지 가지도 못했다. 직전까지 테스트가 `join`을 바로 부를 때는 잘 돌았다.

**원인** `@Transactional`은 Spring이 빈을 감싼 프록시가 처리한다. 다른 빈(컨트롤러, 테스트)이 부르면 프록시를 지나며
트랜잭션이 열린다. `joinWithRetry` 안의 `join(...)`은 `this.join(...)`이라 프록시를 거치지 않는다(자기 호출). 그래서
`join`이 트랜잭션 없이 돌았다. 리포지토리 호출마다 짧은 트랜잭션이 열렸다 닫히고, 방을 읽은 뒤에는 세션이 없다.
`checkJoinable`이 학교를 비교하려고 지연 로딩인 `pickupSpot.getUniversity()`를 건드리는 순간 터졌다.

"반복문은 `@Transactional`을 안 붙이면 트랜잭션 바깥이니 같은 클래스에 둬도 된다"는 반은 맞았다. 바깥인 건 맞지만,
바깥에서 같은 클래스의 메서드를 부르면 안쪽의 `@Transactional`도 같이 사라진다.

**한 줄 요약** "재시도 반복문을 같은 서비스에 두자 자기 호출로 `@Transactional`이 무시돼, 10명 전부 `no session`으로 떨어졌다."

## 2026-10-15. @Version을 빼자 참여와 나가기가 동시에 일어난 방에서 인원 칸이 6이 아니라 4가 됐다. 에러는 없었다

**상황** 참여에 비관적 락을 붙인 뒤 `@Version`을 지워도 되는지 보려고, 참여와 나가기가 동시에 일어나는 테스트를 만들었다.
정원 10명 방에 방장 + 4명이 있고, 그 4명이 나가는 순간 5명이 들어온다. 결과는 1 + 4 - 4 + 5 = 6명이어야 한다.
방 5개에서 반복하고, 이 묶음을 세 번 돌렸다. 나가기는 방을 잠그지 않는다.

`@Version`이 있을 때(15개 방 모두 같은 결과):
```
성공 5명(참여), 참여 행 10, 인원 칸 10
실패 4명(나가기): ObjectOptimisticLockingFailureException ... where id=? and version=?
```
숫자는 맞지만 나가기 4명이 매번 전부 500을 받았다.

`@Version`을 뺐을 때(15개 방 모두 같은 결과):
```
성공 9명, 참여 행 6, 인원 칸 4, 실패 없음
```

**원인** 나가기는 방을 잠그지 않고 읽는다. 나가기 4명이 모두 인원 5를 읽고, 그사이 참여 5명이 잠금을 차례로 쥐고 5 → 10으로
올린다. 그 뒤 나가기가 각자 "5 − 1 = 4"를 쓴다. Hibernate는 방을 저장할 때 바뀐 칸만이 아니라 모든 칸을 덮어쓰므로 참여가
올린 숫자가 통째로 사라진다(갱신 손실). 실제로는 6명인데 방은 4명이라고 믿으니, 정원보다 2명 더 받을 수 있는 방이 됐다.
에러는 하나도 없었다.

`@Version`은 이걸 막아 주고 있었다. 대신 진 쪽을 500으로 떨어뜨린다. 막는 장치가 한쪽(참여)에만 있으면, 잠그지 않은 다른
쪽(나가기)이 그 효과를 지운다.

**해결** 나가기도 `findByIdForUpdate`로 방을 잠그면서 읽게 했다. 이 줄을 `checkLeavable`보다 앞에 둬서, 트랜잭션 안에서
방을 처음 읽는 순간이 잠그는 순간이 되게 했다. 그러면 참여와 나가기가 같은 줄에 서고, 차례가 온 쪽이 늘 최신 인원을 읽는다.
`@Version` 없이 세 번 돌린 결과(15개 방 모두):
```
성공 9명, 참여 행 6, 인원 칸 6, 실패 없음, 걸린 시간 37~73ms
```
전체 테스트 666개도 통과해서 `@Version`은 지운 채로 둔다.

**한 줄 요약** "참여에만 비관적 락을 걸고 @Version을 빼자, 잠그지 않은 나가기가 참여의 +1을 덮어써 6명 방이 4명으로 기록됐다. 에러 없이."

## 2026-10-15. 방장이 3명으로 센 채 마감한 방에 8명이 들어가 있었다

**상황** 참여와 나가기는 방을 잠그게 됐지만 방장 마감(`GroupOrderService.close`)은 여전히 방을 그냥 읽는다.
정원 10명 방에 방장 + 2명, 메뉴 15,000원(최소주문금액 충족). 방장의 마감 1건과 참여 5건을 출발선에서 한꺼번에 놓았다.
방 10개에서 반복하고, 이 묶음을 세 번 돌렸다.

```
방 상태 CLOSED, 방장이 센 인원 3, 참여 행 8, 인원 칸 3, 실패 없음        <- 30개 방 중 26개
방 상태 CLOSED, 방장이 센 인원 3, 참여 행 4, 인원 칸 3, 실패 {모집이 끝난 방입니다=4}  <- 나머지 4개
```

30개 방이 **모두** 깨졌다. 대부분은 참여 5명이 전부 마감된 방에 들어갔다. 에러는 없었다.

**원인** 마감은 방을 잠그지 않고 읽어 "모집중, 3명"을 손에 든다. 참여 행도 3개로 센다. 마감이 커밋하기 전까지 다른 트랜잭션
눈에는 방이 여전히 모집중이라, 참여들은 방 잠금을 차례로 쥐고 들어가 인원 칸을 3 → 8로 올린다. 마감은 그걸 모른 채 상태를
CLOSED로 바꿔 저장하고, 모든 칸을 덮어써 인원 칸도 3으로 되돌린다(갱신 손실).

마감 뒤에는 메뉴 담기와 나가기가 모두 모집중에서만 되므로, 늦게 들어온 사람은 음식도 못 시키고 나가지도 못한다. 그런데 정산은
참여 행 전부를 명단으로 잡고 배달비를 인원 수로 나누므로 배달비는 낸다.

예상과 달랐던 점: "마감 처리 몇 ms 사이에 끼어야 하니 드물 것"이라고 봤는데, 동시에 출발시키면 거의 매번 끼었다. 마감 한 건이
참여 다섯 건이 차례로 끝나는 시간보다 오래 걸렸다.

**해결** 마감도 첫 줄에서 `findByIdForUpdate`로 방을 잠그면서 읽게 했다. 참여 행 세기와 메뉴 합계는 잠금을 쥔 뒤에 돈다.
세 번 돌린 결과 30개 방 모두 "방장이 센 인원 = 참여 행 = 인원 칸"이었다. 마감보다 먼저 잠근 참여는 들어가서 방장이 세는
인원에 들어갔고(3~8명), 마감 뒤에 차례가 온 참여는 "모집이 끝난 방입니다"로 거절됐다.

**한 줄 요약** "참여만 방을 잠그고 마감은 잠그지 않자, 방장이 3명으로 센 마감된 방에 8명이 들어가 있었다. 에러 없이, 30개 방 전부."

## 2026-10-15. 취소된 방에 참여가 성공했고 인원 칸이 8이 아니라 3으로 남았다

**상황** 마감을 고친 뒤 같은 틀로 방장 취소(`GroupOrderService.cancel`)를 봤다. 취소도 방을 그냥 읽는다.
정원 10명 방에 방장 + 2명. 모집중 취소 1건과 참여 5건을 한꺼번에 놓았다. 방 10개 × 3번.

```
방 상태 CANCELED, 성공 6(취소 1 + 참여 5), 참여 행 8, 인원 칸 3   <- 30개 방 중 28개
방 상태 CANCELED, 참여 행 4~5, 인원 칸 3, 나머지 "모집이 끝난 방입니다"  <- 2개
```

30개 방이 모두 깨졌다. 마감과 같은 모양이다. 취소가 커밋하기 전이라 참여 눈에는 방이 모집중이었고, 취소는 저장하면서
인원 칸을 자기가 읽은 3으로 덮어썼다.

마감보다 피해는 작다. 취소된 방은 정산이 없어서 돈이 걸리지 않는다. 남는 건 "참여 성공"을 받았는데 방은 이미 취소된
참여자와, 실제와 다른 인원 칸이다.

**한 줄 요약** "취소도 방을 잠그지 않아서, 취소된 방에 참여 5명이 성공했고 인원 칸은 3으로 덮였다."

**해결** 취소도 첫 줄에서 `findByIdForUpdate`로 읽게 했다. 30개 방 모두 인원 칸 = 참여 행(3~8명)이었고, 취소 뒤에 차례가 온
참여는 "모집이 끝난 방입니다"로 거절됐다.

## 2026-10-15. 스케줄러가 3명으로 자동 마감한 방에 8명이 들어가 있었다

**상황** 마지막으로 스케줄러의 자동 마감(`GroupOrderService.expire`)을 봤다. 이것도 방을 그냥 읽는다.
정원 10명 방에 방장 + 2명, 메뉴 15,000원. 자동 마감 1건과 참여 5건을 한꺼번에 놓았다. 방 10개 × 3번.
테스트는 시각을 조작했다. 참여는 지금 시각(마감 2시간 전)으로 돌고, 스케줄러에는 마감 1초 뒤를 넘겼다.
"마감 직전에 누른 참여가 아직 처리 중일 때 스케줄러가 도는" 장면을 흉내 낸 것이다.

```
방 상태 CLOSED, 성공 6(자동 마감 1 + 참여 5), 참여 행 8, 인원 칸 3   <- 30개 방 전부
```

방장 마감과 똑같은 모양이다. 실제로는 참여의 시각 확인이 마감 직전에 통과하고, 그 참여가 커밋하기 전에 스케줄러가 방을 읽어야
겹친다. 그래서 테스트만큼 자주 일어나지는 않을 것이다. 다만 얼마나 드문지는 재지 않았다.

**해결** 자동 마감도 첫 줄에서 `findByIdForUpdate`로 읽게 했다. 30개 방 모두 인원 칸 = 참여 행(3~8명)이었고, 스케줄러 뒤에
차례가 온 참여는 "모집이 끝난 방입니다"로 거절됐다. 이로써 모집중인 방의 상태와 인원을 바꾸는 다섯 곳(참여, 나가기, 마감, 취소,
자동 마감)이 모두 같은 잠금으로 줄을 선다.

**한 줄 요약** "자동 마감도 방을 잠그지 않아서, 스케줄러가 3명으로 마감한 방에 8명이 들어갔다."

## 2026-10-16. 방장이 배달비 입력을 두 번 누르자 정산표가 두 벌 생겼다

**상황** 정산 쪽(`SettlementService`)의 방 상태를 바꾸는 메서드는 방장만 부를 수 있어서, 사람이 몰리는 일은 없다.
그래도 방장이 응답을 기다리다 버튼을 두 번 누르는 일은 흔하다. 마감된 방(방장 + 2명, 메뉴 15,000원)에
`start`(배달비 3,000원 입력) 2건을 한꺼번에 놓았다. 방 10개 × 3번.

```
성공 2, 실패 없음, 정산표 6줄   <- 30개 방 전부 (3줄이어야 한다)
```

**원인** 두 요청 모두 방을 그냥 읽어 "마감"을 보고 `startSettlement` 검사를 통과했다. 그리고 각자 정산표를 3줄씩 만들었다.
방 행의 UPDATE는 두 번째가 첫 번째의 커밋을 기다렸지만, 이미 "마감"을 읽어 둔 뒤라 다시 확인하지 않았다.
`Settlement`에는 "한 방에 한 사람 한 줄"이라는 유니크 제약이 없어서 DB도 막지 못했다.

이어질 피해(재현은 안 함): 참여자는 자기 줄 둘 중 하나만 보고(`findFirst`) 보냈어요를 누른다. 주문완료는 모든 줄이 확인돼야
넘어가므로, 방장이 남은 줄을 확인할 길이 화면에 없으면 방이 정산중에서 멈출 수 있다.

**해결** 정산 쪽에서 방 상태를 바꾸는 네 곳(`start`, `changeDeliveryFee`, `order`, `deliver`)을 모두 `findByIdForUpdate`로
바꿨다. 조회(`find`)는 보여 주기만 해서 그대로 뒀다. 세 번 돌린 결과 30개 방 모두 성공 1, "마감된 방만 정산을 시작할 수
있습니다" 1, 정산표 3줄이었다. 두 번째 요청은 잠그는 줄에서 첫 번째의 커밋을 기다렸다가 "정산중"을 읽고 거절됐다.

**한 줄 요약** "방장 한 명이 배달비 입력을 두 번 누르는 것만으로 정산표가 3줄이 아니라 6줄이 됐다. 30개 방 전부, 에러 없이."

## 2026-10-16. 참여자 둘이 보냈어요를 성공했는데 입금 기록이 하나도 남지 않았다

**상황** 방 행은 정리했지만, 정산 줄은 아무도 잠그지 않는다. 정산중인 방(방장 + 2명)에서 방장의 배달비 수정
(`changeDeliveryFee`, 3,000원 → 4,000원) 1건과 참여자 둘의 보냈어요(`markPaid`) 2건을 한꺼번에 놓았다. 방 10개 × 3번.

```
보냈어요 성공 2, 배달비 수정 성공 1, 실패 없음, 남은 입금 기록 0   <- 30개 방 전부
```

**원인** 배달비 수정은 방을 잠그고 정산 줄을 그냥 읽어 "입금 기록 없음"을 확인한다. 보냈어요는 방을 건드리지 않고 자기 정산 줄만
고치므로 방 잠금과 상관없이 끼어든다. 그 뒤 배달비 수정이 정산표를 지우고 새로 만들면서 보냈어요 기록이 함께 사라졌다.
참여자는 "보냈어요 성공"을 받았고 실제로 돈도 보냈을 텐데, 방장 화면에는 미입금으로 보인다.

방 잠금을 보냈어요에 붙이는 길은 버렸다. 보냈어요는 정산 줄을 먼저 읽어야 어느 방인지 알 수 있어서, 잠그는 읽기가 첫 읽기가
될 수 없다. 둘이 함께 건드리는 건 정산 줄이니 정산 줄을 잠근다.

**한 줄 요약** "배달비 수정이 정산 줄을 잠그지 않고 확인해서, 그사이 성공한 보냈어요 2건이 정산표째로 지워졌다."

## 2026-10-16. 보냈어요와 받았어요를 같은 줄에 동시에 누르자 둘 중 하나가 사라졌다

**상황** 같은 정산 줄을 참여자의 보냈어요(`markPaid`, 보낸 시각 칸)와 방장의 받았어요(`confirm`, 확인 시각 칸)가 함께 고친다.
방장이 통장을 보고 바로 확인을 누를 수 있게 해 둬서, 순서가 정해져 있지 않다. 둘을 한꺼번에 놓았다. 방 10개 × 3번.

```
성공 2, 실패 없음
보낸 시각 null, 확인 시각 05:18:20.511   <- 이런 방과
보낸 시각 05:18:20.533, 확인 시각 null   <- 이런 방이 섞여서, 30개 방 전부
```

**원인** 두 요청이 같은 줄을 그냥 읽는다. 각자 자기 칸만 바꾸지만, JPA는 줄의 모든 칸을 자기가 읽은 값으로 덮어쓴다.
그래서 나중에 커밋한 쪽이 상대 칸을 빈 값으로 되돌렸다. 나가기의 인원 칸과 같은 갱신 손실이다. 칸이 달라도 줄이 같으면 생긴다.

**해결(위 두 항목)** 정산 줄을 잠그는 쿼리 둘을 만들었다. 줄 하나(`findByIdForUpdate`)와 방의 줄 전부
(`findByGroupOrderIdForUpdate`)다. 정산 줄 버튼 여섯 개가 함께 쓰는 헬퍼 `findLine`이 줄 하나를 잠그고, 배달비 수정은
"입금 기록 없음"을 확인할 때 방의 줄 전부를 잠근다. 세 번 돌린 결과:

```
배달비 수정 + 보냈어요 2건: 30개 방 모두 보냈어요 성공 2, 입금 기록 2, 배달비 수정은 "입금 기록이 있어 배달비를 수정할 수 없습니다"
보냈어요 + 받았어요: 둘 다 성공한 방은 두 칸 모두 남음(14개 방).
                     받았어요가 먼저 잠근 방은 보냈어요가 "이미 송금을 완료했습니다"로 거절(16개 방). 원래 있던 규칙이 이제 제대로 걸린다
```

배달비 수정이 먼저 잠그고 줄을 지워서, 기다리던 보냈어요가 "없는 정산입니다…"를 받는 순서는 30번 중 한 번도 나오지 않았다.
보냈어요가 더 짧아서 늘 먼저 잠근 것으로 보인다. 그 길은 재현하지 못했다.

**한 줄 요약** "보냈어요와 받았어요가 서로 다른 칸을 고쳤는데도, 줄 전체를 덮어써서 30개 방 모두 한쪽 기록이 사라졌다."

## 2026-10-16. 한 번만 쓸 수 있어야 할 리프레시 토큰 하나로 새 토큰 10개가 나왔다

**상황** Phase 1 정리 때 코드를 읽다 찾아 "아직 재현 전"으로 적어 둔 것이다. 갱신(`AuthService.refresh`)은 Redis에서 토큰을
찾고(`findUserId`), 지우고(`revoke`), 새로 발급한다. 갱신할 때마다 토큰을 바꿔 주니(회전), 한 토큰은 한 번만 쓸 수 있어야 한다.
같은 토큰으로 갱신 10건을 한꺼번에 놓았다. 10회 × 3번.

```
성공 10, 살아 있는 새 토큰 10, 실패 없음   <- 30회 중 29회
성공 7, 살아 있는 새 토큰 7, 실패 {다시 로그인해주세요=3}   <- 1회
```

**원인** 찾기와 지우기가 Redis 명령 두 개라 그 사이에 다른 요청이 끼어든다. 10건 모두 지워지기 전에 찾아서 통과했다.
DB가 아니라서 `@Transactional`도 `FOR UPDATE`도 걸 데가 없다. 모양은 정원 초과(확인 → 행동 사이에 끼어들기)와 같다.
훔친 토큰과 진짜 주인이 동시에 갱신하면 둘 다 살아 있는 토큰을 갖게 되어, 회전으로 막으려던 것이 막히지 않는다.

**해결** `RefreshTokenStore.consume`을 만들어 Redis `GETDEL` 한 명령으로 꺼내면서 지운다. 갱신은 이것 하나만 부르고 따로
지우지 않는다. 락이 아니라 확인과 행동을 쪼갤 수 없는 명령 하나로 합친 것이다. 30회 모두 성공 1, 살아 있는 새 토큰 1,
"다시 로그인해주세요" 9였다.

화면도 고쳤다. 토큰은 모든 탭이 같이 쓰는 `localStorage`에 있고, 갱신에 실패하면 저장소를 비웠다. 서버를 고치면 탭 두 개가
동시에 갱신할 때 진 탭이 이긴 탭의 새 토큰까지 지워서 둘 다 로그아웃될 것으로 봤다. 그래서 실패하면 비우기 전에 저장소를 다시
보고, 다른 탭이 새 토큰을 써 뒀으면 그걸로 다시 요청한다. 이 탭 두 개 장면은 브라우저에서 재현하지 않았다(예상만 했다).
→ 2026-10-19에 브라우저에서 재현했고, 이 화면 수정으로는 부족해서 다시 고쳤다(아래 2026-10-19).

**한 줄 요약** "찾고 지우기가 두 명령이라, 같은 토큰으로 동시에 갱신한 10건이 모두 새 토큰을 받았다."

## 2026-10-16. 같은 이름 거점을 동시에 만들자 9건이 "이미 있는 거점입니다"가 아니라 서버 오류로 끝났다

**상황** Phase 1 정리 때 "아직 재현 전"으로 적어 둔 것이다. 거점 만들기(`PickupSpotService.create`)는 같은 학교에 비교용
이름이 같은 거점이 있는지 확인하고(`existsByUniversityIdAndNormalizedName`), 없으면 저장한다. DB에도 (학교, 비교용 이름)
유니크 제약이 있다. 10명이 같은 이름으로 동시에 만들었다. 3번 돌렸다.

```
성공 1, 만들어진 거점 1, 실패 {DataIntegrityViolationException=9}   <- 3번 모두
could not execute statement [ERROR: duplicate key value violates unique constraint
  "pickup_spot_university_id_normalized_name_key"
```

**원인** 10건 모두 확인할 때는 아직 아무도 커밋하지 않아서 "없다"를 보고 INSERT까지 갔다. 정원 초과와 같은 확인 → 행동 사이의
끼어들기다. 다른 점은 데이터가 깨지지 않았다는 것이다. 거점은 하나만 남았다. 유니크 제약이 마지막에 막았기 때문이다.
틀린 건 응답이다. 제약 위반 예외는 핸들러가 따로 처리하지 않아서 마지막 `Exception` 핸들러로 떨어져 500이 된다.
한 명씩 만들었으면 받았을 "이미 있는 거점입니다"(409) 대신 서버 오류를 받는다.

**같이 확인한 것: 같은 사람의 동시 참여는 피해 갔다** 같은 목록에 "같은 사람이 [참여]를 동시에 누르면 참여 행 유니크 제약에
걸려 500"도 적어 뒀다. 같은 사람으로 참여 10건을 동시에 놓았다(방 5개 × 3번). 15번 모두 성공 1, 나머지 9는
"이미 참여한 방입니다"였고 500은 없었다. 동시성 단계에서 `join`이 맨 앞에서 방 행을 잠그게 됐기 때문이다(ADR-058).
두 번째 요청은 첫 번째가 커밋할 때까지 기다렸다가 "이미 참여" 확인을 하니, 확인을 둘이 함께 통과할 수가 없다.

**해결** 락은 쓰지 않았다. 겹치는 건 아직 없는 거점이라 잠글 행이 없고, 데이터는 제약이 이미 지키고 있었다. `create`에서 거점을
저장하는 한 줄만 try-catch로 감싸 `DataIntegrityViolationException`을 `IllegalStateException("이미 있는 거점입니다")`로 바꿔
던진다(ADR-060). 저장은 `saveAndFlush`로 바꿔 INSERT가 그 줄에서 나가게 했다. 커밋 때 나가면 예외도 메서드 밖에서 나서
try-catch가 못 잡는다. 15번 모두 성공 1, 만들어진 거점 1, 나머지 9는 "이미 있는 거점입니다"였다.

**한 줄 요약** "확인은 둘 다 통과했고 DB 제약이 막았는데, 그 거절이 409가 아니라 500으로 나갔다."

## 2026-10-17. 나가기 끝에 캐시 지우기 한 줄을 넣자 트랜잭션 안인데 no session으로 500이 났다

**상황** 방 목록 캐시를 넣고, 목록을 바꾸는 곳마다 `roomListCache.evict(학교 id)`를 붙였다. 학교 id는
`groupOrder.getPickupSpot().getUniversity().getId()`로 꺼낸다. 참여, 메뉴 담기·고치기·빼기는 통과했는데 나가기만 500이었다.

```
LazyInitializationException: Could not initialize proxy [com.bandal.pickupspot.PickupSpot#8] - no session
  at PickupSpot$HibernateProxy.getUniversity
  at ParticipationService.leave(ParticipationService.java:64)
```

**원인** `leave`는 `@Transactional`이라 세션이 없을 리가 없어 보였다. 범인은 바로 위 줄의 메뉴 일괄 삭제
`deleteByParticipationId`다. 이 쿼리는 `clearAutomatically = true`라서, DELETE 뒤에 영속성 컨텍스트를 통째로 비운다
(2026-10-02에 남은 메뉴 객체 때문에 넣은 설정이다). 비우기 전에 꺼낸 `groupOrder`는 변수에 그대로 있지만 컨텍스트 소속이 아니게 된다.
`groupOrder`의 거점은 아직 안 읽은 프록시였고, 컨텍스트에서 떨어진 프록시는 SELECT를 보낼 수 없다. 참여(`join`)는 같은 줄을 써도
중간에 비우는 쿼리가 없어서 멀쩡했다.

**해결** 학교 id를 메뉴 일괄 삭제보다 먼저, 방을 불러온 바로 뒤에 `Long`으로 꺼내 두고 `evict`에는 그 값을 넘긴다.
꺼내는 순간 프록시가 SELECT를 보내고, 숫자는 컨텍스트를 비워도 남는다. `evict` 줄은 "다 바꾼 다음에 지운다" 순서를 지키려고
끝에 그대로 뒀다. 나가기 테스트를 포함해 전체 700개가 통과했다.

**배운 것**
- `@Transactional` 안이라도 컨텍스트가 비워진 뒤의 객체는 지연 로딩을 못 한다. "no session"이 꼭 트랜잭션 밖이라는 뜻은 아니다.
- `clearAutomatically`는 그 쿼리 한 줄이 아니라 메서드 전체에 영향을 준다. 그 뒤에 줄을 더할 때는 앞에서 꺼낸 객체를 믿으면 안 된다.

**한 줄 요약** "나가기 끝에 캐시 지우기 한 줄을 넣었더니, 위의 메뉴 일괄 삭제가 컨텍스트를 비워 둔 탓에 방의 거점 프록시가
트랜잭션 안에서 no session으로 터졌다. 학교 id를 비우기 전에 꺼내 두는 걸로 고쳤다."

## 2026-10-17. 캐시를 지운 뒤 커밋 전에 다른 사람이 목록을 열자, 옛 인원이 다시 담겨 남았다

**상황** 방 목록 캐시는 목록을 바꾸는 곳마다 `evict`를 부르고, `evict`는 그 자리에서 바로 Redis 키를 지운다. 참여 테스트(목록 열기 →
참여 → 다시 열기)는 통과했다. 하지만 지우는 줄은 트랜잭션 한가운데에 있고, 커밋은 메서드가 끝난 뒤다. 그 틈을 테스트로 고정했다.
A가 참여하고(키 삭제) 커밋하기 전에, 다른 스레드의 B가 목록을 연다. 그다음 A가 커밋한다.

```
[커밋 전에 B가 담은 옛 목록(인원 1)이 남아 있으면 안 된다]  Expecting value to be false but was true
```

B가 연 목록은 인원 1이었다. 캐시가 비어 있어서 DB를 읽었지만 A의 참여는 커밋 전이라 안 보였고(READ COMMITTED), B는 그 인원 1을
캐시에 다시 담았다. A의 커밋 뒤 DB는 인원 2인데 캐시에는 인원 1이 남았고, 이걸 지울 코드는 이미 지나갔다. TTL 10초가 끝날 때까지
모든 사람이 옛 인원을 본다. 캐시 클래스 단위 테스트에서도 "트랜잭션 안이면 커밋 전에는 안 지운다", "롤백이면 안 지운다"가
`delete`가 바로 불려서 실패했다.

**해결** `evict`는 트랜잭션 안이면(`TransactionSynchronizationManager.isSynchronizationActive()`) 지우지 않고
`registerSynchronization`으로 "커밋 뒤에 지워 달라"는 객체만 맡긴다. 스프링이 커밋 직후 그 객체의 `afterCommit()`을 부를 때
지운다. 롤백되면 `afterCommit`이 불리지 않아 안 지운다. 트랜잭션 밖이면 쿼리가 그 자리에서 확정되므로 바로 지운다.
Redis 예외를 삼키는 try-catch는 `afterCommit` 안에서 도는 `delete`로 옮겼다. 등록 줄을 감싸면 실제 호출은 커밋 뒤라 못 잡는다.
B는 여전히 커밋 전에 인원 1을 담지만, 커밋 뒤 A가 그걸 지워서 다음 목록은 인원 2다. 경합 테스트와 단위 테스트 4개를 포함해
전체 706개가 통과했다.

남는 틈: A의 커밋과 `afterCommit` 사이에 B가 커밋 전 값을 읽어 놓고, A가 지운 뒤에 담으면 다시 옛 값이 남는다. 이번 것보다 훨씬
좁고, TTL 10초가 덮는다(ADR-061).

**배운 것**
- 캐시 지우기는 DB 트랜잭션에 묶이지 않는다. "언제 지우느냐"까지가 무효화다.
- 지운 다음 다시 담는 쪽은 다른 사람의 읽기다. 내 코드만 보면 순서가 맞아 보여도 그 사이에 남이 끼어든다.
- 커밋 뒤에 도는 콜백 안의 예외는 등록한 자리의 try-catch가 못 잡는다. 예외 처리는 실제로 도는 곳에 둔다.

**한 줄 요약** "캐시를 트랜잭션 한가운데서 지웠더니, 커밋 전 DB를 읽은 다른 사람이 옛 인원을 다시 담았고 그게 10초 동안 남았다.
`afterCommit`으로 커밋 뒤에 지우게 고쳤다."

## 2026-10-19. 탭 두 개가 동시에 토큰을 갱신하면, 진 탭의 401이 먼저 올 때 그 탭이 로그아웃됐다

**상황** 2026-10-16에 "예상만 했다"고 적은 장면을 브라우저에서 확인했다. 크롬(헤드리스, playwright-core)에 탭 두 개를 띄웠다.
같은 브라우저라 `localStorage`를 같이 쓴다. 로그인한 뒤 액세스 토큰만 망가뜨려(만료된 것처럼) 두 탭을 동시에 새로고침했다.
두 탭 모두 401을 받고 같은 리프레시 토큰으로 갱신하러 간다. 서버는 하나만 받아 준다(ADR-059).

먼저 10-16 이전 코드(실패하면 바로 저장소를 비움)로 되돌려 돌렸다.

```
#1 로그아웃 A=true B=false | 저장소=비었음 | B refresh 200, A refresh 401   <- 3번 중 3번
```

이긴 B가 새 토큰을 써 둔 뒤 진 A가 저장소를 비웠다. B도 다음 요청부터 토큰이 없다. 예상했던 "둘 다 로그아웃"이 재현됐다.

10-16 코드(실패하면 비우기 전에 저장소를 다시 봄)로는 보통 순서에서 10번 모두 둘 다 유지됐다. 그런데 매번 B의 200이 A의
401보다 먼저 왔다. 그래서 B의 갱신 응답만 300ms 늦게 받게 해서, A의 401이 먼저 오는 순서를 만들었다.

```
#1 로그아웃 A=true B=false | 저장소=있음 | A refresh 401, B refresh 200   <- 5번 중 5번
```

**원인** "다시 본다"는 이긴 탭이 이미 새 토큰을 써 둔 경우에만 통한다. A가 다시 봤을 때는 B가 아직 저장 전이라 옛 토큰 그대로였고,
A는 진짜 실패로 보고 로그아웃했다. 이 순서는 지어낸 게 아니다. 진 쪽 요청은 Redis 명령 하나(`GETDEL`이 빈 값)로 바로 거절되고,
이긴 쪽은 발급과 저장까지 해야 해서 진 쪽 응답이 먼저 올 수 있다. 다만 실제로 그 순서를 만든 건 내가 넣은 지연이다.

**해결** 탭끼리 갱신 차례를 정했다. 브라우저의 Web Locks(`navigator.locks.request('bandal.refresh', ...)`)는 같은 사이트의 모든 탭이
같이 보는 잠금이다. 갱신은 이 잠금 안에서만 한다. 기다린 탭은 차례가 오면 저장소를 다시 보고, 요청에 썼던 리프레시 토큰과 다르면
다른 탭이 이미 갱신한 것이라 서버에 가지 않고 새 토큰으로 다시 요청한다. 보통 순서 10번, 지연 순서 10번 모두 서버 갱신 1번,
로그아웃 0이었다.

곁에서 본 것: 갱신 응답을 받기 전에 그 탭을 새로고침하면, 서버는 토큰을 이미 바꿨는데 브라우저는 새 토큰을 못 받아 로그아웃된다.
확인 스크립트를 처음 짰을 때 이것 때문에 결과가 전부 "저장소 비었음"으로 나왔다. 회전 방식에서는 피할 수 없는 일이라 그대로 둔다.

**배운 것**
- "실패하면 다시 확인한다"는 상대가 먼저 끝냈을 때만 맞다. 순서가 정해지지 않은 둘 사이에서는 줄을 세워야 한다.
- 서버 쪽 경쟁(GETDEL)을 고치면 진 쪽이 생기고, 그 진 쪽을 어떻게 다룰지가 화면의 경쟁이 된다.
- 보통 순서로 열 번 통과해도, 응답 순서를 바꿔 보기 전에는 고쳤다고 말할 수 없다.

**한 줄 요약** "탭 두 개가 동시에 토큰을 갱신할 때 진 탭의 401이 먼저 오면 그 탭이 로그아웃됐다. 브라우저 잠금(Web Locks)으로
탭끼리 갱신 차례를 세워 고쳤다."

## 2026-10-19. 메일 서버에 못 닿는다는 이유로 앱 전체가 DOWN이 되어, 입구가 뜨지 않았다

**상황** 서버 구성(바깥 Nginx, bandal-web, backend, postgres, redis)을 노트북에서 그대로 띄웠다. 메일 발송 수단은 아직 안 정해서
없는 주소(`smtp.nowhere.invalid`)를 줬다. `docker compose up`이 이렇게 끝났다.

```
dependency failed to start: container bandal-stage-backend-1 is unhealthy
```

원인이 둘 겹쳐 있었다. healthcheck 기록에는 명령 자체가 안 돌았다고 나왔다.

```
/bin/sh: 1: cannot create /dev/tcp/127.0.0.1/8080: Directory nonexistent
```

`CMD-SHELL`은 `/bin/sh`로 돌고, Ubuntu 기반 JRE 이미지의 `/bin/sh`는 dash다. `/dev/tcp`는 bash에만 있는 기능이다. 그런데 컨테이너
안에서 bash로 직접 물어보니 health 자체도 `{"status":"DOWN"}`이었다. 앱 로그에는 이렇게 있었다.

```
WARN o.s.b.mail.health.MailHealthIndicator : Mail health check failed
MailConnectException: Couldn't connect to host, port: smtp.nowhere.invalid, 587; timeout -1;
```

**원인** Spring의 health는 붙어 있는 외부 서비스를 전부 확인하고, 메일 서버 하나가 안 닿아도 앱 전체를 DOWN으로 본다. 그래서
backend가 unhealthy가 됐고, backend가 healthy가 되길 기다리던 입구(web)는 아예 뜨지 않았다. 운영이었다면 메일 서비스가 잠깐 멈춘
것만으로 방 목록, 참여, 정산까지 들어갈 수 없게 된다. `timeout -1`은 접속을 끝없이 기다린다는 뜻이다. 메일 서버가 응답을 안 하면
인증 메일을 보내던 요청 스레드가 영영 묶인다.

**해결**
- healthcheck를 `["CMD", "bash", "-c", "..."]`로 bash를 직접 부르게 했다.
- health에서 메일을 뺐다(`management.health.mail.enabled=false`). 메일 없이도 앱은 일한다. DB와 Redis는 남겼다.
- 메일 접속 5초, 응답과 쓰기 10초로 상한을 뒀다.

다시 띄우자 backend가 healthy가 되고 web이 떴다. 밖에서 화면 200, 화면 안 주소(`/rooms/3`) 200, 로그인이 필요한 API 401, 모르는
주소는 응답 없이 끊음. 바깥 Nginx 안에서 이름을 찾아보니 `bandal-web`만 보이고 `backend`, `postgres`, `redis`는 안 보였다(ADR-065).
밖으로 열린 포트는 바깥 Nginx 하나였다.

곁에서 본 것: 다시 띄우는 사이에 `password authentication failed for user "bandal"`로 backend가 4번 다시 켜졌다. 확인 스크립트가
띄울 때마다 DB 비밀번호를 새로 만들었는데, Postgres는 `POSTGRES_PASSWORD`를 볼륨이 비어 있는 첫 실행 때만 쓴다. 운영에서 `.env`의
비밀번호만 바꿔도 똑같이 멈춘다.

**배운 것**
- health는 "앱이 일할 수 있는가"여야 한다. 없어도 되는 외부 서비스까지 넣으면, 그 서비스의 장애가 앱 전체의 장애가 된다.
- 외부를 부르는 곳은 기다리는 시간에 상한이 있는지 본다. 기본값이 "끝없이"인 라이브러리가 있다.

**한 줄 요약** "메일 서버에 못 닿는다는 이유로 health가 DOWN이 되어 입구 컨테이너가 뜨지 않았다. health에서 메일을 빼고, 메일 대기
시간에 상한을 뒀다."

## 2026-10-20 이미 돌린 V2의 줄바꿈을 고쳤더니 로컬 앱이 뜨지 않았다

**상황** 로컬 개발 DB에 V2(캠퍼스 학교 넣기)가 이미 돌아간 뒤에, V2 파일에서 `insert ... values`의 `values`를 다음 줄로 내렸다.
SQL의 뜻은 그대로다.

**증상** 다음에 개발 서버를 띄우자 Flyway가 멈췄다.

```
FlywayValidateException: Validate failed: Migrations have failed validation
Either revert the changes to the migration, or run repair to update the schema history.
```

**원인** Flyway는 돌린 파일마다 내용의 체크섬을 `flyway_schema_history`에 적어 두고, 뜰 때마다 지금 파일과 비교한다. 체크섬은
글자 단위라 줄바꿈 하나도 "다른 파일"이다. 운영이었다면 배포한 앱이 뜨지 않는다.

**해결** 아직 운영에 나가지 않은 파일이라 로컬 기록만 맞추면 된다. `docker compose down -v`로 로컬 DB 볼륨을 지우고 다시
띄웠다. Flyway가 기록 테이블부터 새로 만들고 V1, V2를 차례로 돌려 정상으로 떴다. `flyway repair`(기록된 체크섬만 고치기)는
로컬 데이터를 남길 이유가 없어서 쓰지 않았다.

**배운 것** 한 번 돈 마이그레이션 파일은 모양까지 얼린다. 운영에 나가기 전이면 로컬 기록을 맞추고(repair 또는 DB 다시 만들기),
나간 뒤면 새 번호 파일을 쓴다.

**한 줄 요약** "SQL 뜻은 그대로인데 줄바꿈만 바꿔도 Flyway 체크섬이 달라져 앱이 뜨지 않았다."

## 2026-10-20 운영 로그에 Spring Security 기본 계정 비밀번호가 찍혔다

**상황** 운영 메일(Resend)을 확인하려고 운영 구성(prod 프로필, 서버용 compose)을 로컬에 띄우고 backend 로그를 봤다.

**증상** 시작 로그에 이 줄이 있었다.

```
Using generated security password: (값)
```

**원인** Spring Security는 사용자 저장소(`UserDetailsService`)를 앱이 따로 만들지 않으면 "user"라는 기본 계정을 메모리에 만들고, 그
비밀번호를 시작 로그에 찍는다(`UserDetailsServiceAutoConfiguration`). 우리는 로그인을 JWT 필터로 직접 해서 이 저장소를 만든 적이 없다.
폼 로그인과 Basic 인증을 꺼 두어서 이 계정으로 들어올 길은 없었다. 하지만 설정을 바꾸다 Basic 인증이 켜지면 바로 쓸 수 있는 계정이고,
로그는 여러 사람과 도구가 보는 곳이다.

**해결** 공통 설정에서 그 자동 설정을 껐다(`spring.autoconfigure.exclude`). `UserDetailsService` 빈이 없다는 테스트를 더했고, 다시 띄운
로그에 그 줄이 0번이었다. 테스트 718개 통과.

**배운 것** 프레임워크가 "알아서" 만들어 주는 것 중에 우리가 안 쓰는 게 있는지 시작 로그를 한 번 읽어 본다. 안 쓰는 기본값은 끈다.

**한 줄 요약** "JWT만 쓰는데 Spring Security가 기본 계정을 만들어 비밀번호를 운영 로그에 찍고 있었다. 자동 설정을 껐다."

## 2026-10-20 백업 설정이 빠졌는데 실패 알림이 가지 않았다

**상황** DB 백업 스크립트(`deploy/bandal/backup.sh`)를 로컬 리허설로 돌렸다. 실패하면 감시 서비스(healthchecks.io)에 `/fail`을 보내고,
하루 넘게 성공 신호가 없어도 그쪽에서 메일이 오게 했다. 리허설에 R2 설정을 뺀 `.env`로 돌리는 경우를 넣었다.

**증상** 스크립트는 "R2_BUCKET, R2_ENDPOINT가 .env에 없다"를 찍고 1로 끝났는데, 감시 서비스 대역(요청을 기록하는 작은 HTTP 서버)에는
`/fail`이 오지 않았다. 같은 리허설에서 덤프가 실패한 경우는 `/fail`이 왔다.

**원인** 실패 알림은 `trap finish EXIT`로 걸어 두었는데, R2 설정 검사가 그 `trap`보다 위에 있었다. 검사에서 `exit 1`로 나가는 순간에는
아직 알림이 걸려 있지 않았다. 설정 누락은 서버에서 가장 일어나기 쉬운 실패다(Secrets 하나를 안 넣은 배포).

**해결** 알림 함수와 `trap`을 설정 검사보다 먼저 걸었다. 다시 돌린 리허설에서 `/fail`이 왔다. 고치지 않았어도 하루 뒤 "신호 없음"
메일은 왔겠지만, 바로 알 수 있는 실패를 하루 늦게 알게 된다.

**배운 것** 실패 처리는 스크립트 맨 앞에 건다. "어디서 실패해도"라고 써 놓고 실제로는 그 줄 아래에서만 실패를 잡고 있었다.

**한 줄 요약** "실패 알림을 trap으로 걸었는데, 설정 검사가 trap보다 위에 있어서 설정 누락은 조용히 끝났다."
