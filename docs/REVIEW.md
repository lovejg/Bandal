### 0단계. 전체 그림

- **한 문장**: 최소주문금액을 같은 수령 거점의 사람들이 1인분씩 담아 함께 채운다. 방장이 배달앱에서 대표로 주문하고, Bandal은 모집, 메뉴 취합, 정산 계산만 한다.
- **대학으로 좁힌 이유**: 같은 시각 × 같은 가게 × 같은 수령지의 교집합이 캠퍼스에서 실제로 생긴다. 학교 메일 하나로 신원과 거점 자격이 같이 확인된다. 수령 장소가 이미 있다.
- **면접에서 "왜"가 나올 결정 셋**

  | 결정 | 이유 | 버린 안 |
  |---|---|---|
  | 앱은 돈을 옮기지 않는다(계좌 복사, 송금 링크) | 돈이 잠깐이라도 플랫폼에 머물면 전자금융거래법상 등록 대상 | 앱이 받아서 전달 |
  | 송금이 주문보다 먼저 | 방장이 먼저 결제하면 한 명만 잠수해도 방장이 떠안고, 방장을 할 사람이 없어진다 | 방장 선결제 후 정산 |
  | 배달비는 균등, 원 단위 아래는 버리고 나머지는 방장이 | 배달비는 메뉴 금액과 상관없다. 청구 금액이 깔끔하다 | 메뉴 금액 비율 |

- **상태 흐름**: 모집중 → 마감 → 정산중 → 주문완료 → 배달완료. 주문완료 전까지는 취소로 갈 수 있다. 정산중 취소는 환불을 끝까지 기록한다. 방장이 사라지면 1분마다 도는 스케줄러가 멈춘 방을 넘긴다(마감 3시간·정산중 24시간 → 취소, 주문완료 6시간 → 배달완료).
- **테이블 7개**: University, User, PickupSpot, GroupOrder, Participation, OrderItem, Settlement. 토큰(메일 인증, 리프레시)은 Redis에 TTL로. 가장 중요한 불변식은 "참여 인원 ≤ 정원"이고, 이게 Phase 3의 출발점이다.
- **코드 구조**: 기능별 패키지(auth, university, pickupspot, grouporder, participation, settlement, user, common). Controller → Service(트랜잭션) → Entity(규칙 검사) / Repository(쿼리). 상태 전이 규칙은 서비스가 아니라 엔티티 안에 있다.
- **기술마다 쓴 이유**: DESIGN 6번 표. 원칙은 "써 봤다"가 아니라 "이 문제가 이렇게 터졌고 이렇게 고쳤다"로 말할 수 있어야 남긴다. Kafka와 Batch는 아직 안 썼다.
- **요청 한 번의 길**: Cloudflare DNS(A 레코드, 프록시 끔) → 바깥 Nginx(443, HTTPS를 풀고 요청 id) → bandal-web(화면, /api는 넘김) → backend:8080 → postgres:5432, redis:6379. DB, Redis, backend는 `ports`가 없다.
- **확인 질문**: 앱 안 결제가 더 편하지 않나? / 방장 선결제면 무슨 일이? / 배달비 3,500원을 3명이 나누면? / 동시성 문제가 가장 먼저 터지는 곳은?
- **답해 보고 고친 것 (2026-10-22)**
  - 앱 안 결제: "지금은 승인을 못 받아서"가 아니라 **"돈이 플랫폼을 지나가지 않게 설계해서 등록이 필요 없는 구조를 골랐다"**로 말한다. 사기, 분쟁, 정산 사고의 책임도 앱이 지지 않는다. 대신 복사 버튼과 송금 딥링크로 불편을 줄였다(딥링크는 공식 API가 아니라 복사 버튼이 폴백).
  - 방장 선결제: 핵심은 환불의 어려움이 아니라 **방장의 외상**이다. 한 명만 잠수해도 방장이 그 돈을 떠안는다 → 방장을 할 사람이 없다 → 방이 안 열린다 → 서비스가 돌지 않는다. "주문 뒤에는 취소가 안 된다"는 그다음 이야기다.
  - 배달비: 100원 단위가 아니라 **원 단위**로 버린다. 3,500 / 3 = 1,166.67 → 참여자 1,166원씩, 방장은 3,500 − 1,166 × 2 = **1,168원**(나머지 2원을 더 낸다). `SettlementCalculator`의 `hostDeliveryFee = deliveryFee - generalDeliveryFee * (participants.size() - 1)`.
  - 동시성: 방 참여가 맞다. 이유를 한 단계 더: "읽고(인원 3) → 비교하고(< 4) → 쓴다"가 쪼개져 있어서, 두 트랜잭션이 같은 3을 읽으면 둘 다 들어간다(check-then-act). 다른 곳도 있다: 참여와 방장 취소가 겹치면 취소가 덮인다(갱신 손실), 같은 사람이 두 번 누르면 중복 참여(유니크 제약). 3단계에서 본다.
  - 추가 질문 "참여와 취소가 겹치면?": 두 번 깨 봤다. 취소가 안 잠그면 취소가 참여의 +1을 지우고(취소된 방에 8명, 인원 칸 3), 참여가 옛 방을 들고 있으면 참여가 취소를 지운다(방이 다시 모집중). Hibernate가 모든 칸을 UPDATE해서 칸이 달라도 줄이 같으면 덮인다. NOTES "갱신 손실".

### 3단계. 동시성 — ADR-058, 059, 060, 078

**모든 문제의 모양은 하나**: 확인하고 → 행동하는 사이에 남이 끼어든다(check-then-act). 트랜잭션은 "내 일이 전부 되거나 전부 안 된다"만 보장하고, 남이 끼어드는 건 막지 않는다.
겹치는 대상에 따라 도구가 달랐다.

| 겹치는 것 | 도구 | 어디 |
|---|---|---|
| 이미 있는 행 하나를 여럿이 고친다 | DB 비관적 락 `FOR UPDATE` | 방 행(참여, 나가기, 마감, 취소, 자동 마감, 정산 4곳), 정산 줄(버튼 6개, 배달비 수정) |
| 아직 없는 행을 여럿이 만든다 | 유니크 제약 + 예외를 409로 | 같은 이름 거점 |
| Redis 명령 두 개 사이 | 명령 하나로 합친다(GETDEL) | 리프레시 토큰 회전 |
| 락 앞 줄이 커넥션을 붙잡는다(성능) | 트랜잭션 밖 미리 보기 | `ParticipationGate`(Phase 4) |

**재현 방법(출발선)**: `GroupOrderConcurrencyTest.sendAllAtOnce`. `ready` 래치로 스레드 n개가 다 준비될 때까지 기다리고, `start` 래치 하나를 놓아 한꺼번에 출발, `done`으로 끝을 기다린다. 스레드 풀만 쓰면 앞 스레드가 먼저 끝나 버려 겹치지 않는다. 실패는 예외 이름 + 메시지로 세서 "500이 아니라 한 명씩 눌렀을 때와 같은 거절"인지까지 본다.

**정산 쪽 (2026-10-16)**
- 방장이 배달비 입력을 두 번 → 정산표 6줄(3줄이어야). 정산 4곳도 방을 잠근다.
- 배달비 수정(정산표를 지우고 다시 만듦)과 보냈어요 2건 → 입금 기록 0. 보냈어요는 방을 안 건드려서 방 잠금과 상관없이 끼어들었다. 정산 줄을 잠근다.
- 보냈어요와 받았어요 → 둘 중 하나가 사라짐. 칸이 달라도 줄이 같아서(갱신 손실).
- 잠그는 순서는 늘 "방 → 정산 줄" 한 방향(교착을 피하려고). 보냈어요가 방을 잠그지 않는 까닭: 정산 줄을 먼저 읽어야 어느 방인지 알아서 잠그는 읽기가 첫 읽기가 될 수 없다.

**DB가 아닌 곳**
- 리프레시 토큰: 찾기와 지우기가 명령 둘이라 한 토큰으로 새 토큰 10개. `GETDEL` 한 명령으로(Redis는 명령을 하나씩 처리한다). 화면은 Web Locks로 탭끼리 줄 세움(진 탭 로그아웃을 브라우저에서 재현하고 고쳤다).
- 같은 이름 거점: 없는 행은 잠글 수 없다. 데이터는 유니크 제약이 지켰고 틀린 건 응답(500). 저장 한 줄만 try-catch로 409. `saveAndFlush`로 INSERT를 그 줄에서 보낸다. 전역 핸들러로 409를 만들지 않은 까닭: 외래 키 같은 우리 버그까지 409로 묻힌다.
- 같은 사람 동시 참여: 피해 갔다. 방 잠금 뒤에 "이미 참여" 확인을 해서 15번 모두 409.

**비관적 락을 고른 까닭(ADR-058)**: 몰리는 곳이 정해져 있다(마지막 자리) → 충돌이 드물다는 낙관적 락의 전제가 틀렸다. 진 사람이 정확한 사유를 받는다. 일이 적다(10명이 자리 3개면 낙관적은 30번 넘게, 비관적은 10번). 서버가 여러 대여도 DB가 하나면 같은 줄에 선다. 대가: 기다리는 동안 커넥션을 쥔다 → Phase 4에서 재서 미리 보기로 줄였다(ADR-078). Redis 분산 락은 보류(대상이 전부 한 DB의 행이고, Redis 장애·만료·커밋 전 해제 문제를 새로 떠안는다).

**규칙 하나**: 잠그는 읽기는 그 트랜잭션에서 그 행을 처음 읽는 줄. 2026-10-22에 직접 어겨서 정원 4명 방에 13명이 다시 들어갔다(Phase 4 개선 2).

- **자세히**: ADR-058, 059, 060 / JOURNAL 2026-10-15 ~ 16 전부, 2026-10-19 탭, 2026-10-22 미리 보기 / NOTES "트랜잭션과 동시성" 전부, "DB 제약과 예외"

**답해 보고 고친 것 (2026-10-22)**
- 1~3번(@Version, 자기 호출, 거점)은 맞았다. 2번은 "외부 호출 → 프록시가 트랜잭션 열기 → 진짜 객체", `this.join()`은 진짜 객체 안에서 바로 불러 프록시를 건너뛴다까지 말한다. 3번은 "데이터는 제약이 지켰고 틀린 건 응답(500)이라 409로만 바꿨다"까지.
- 4번 서버 여러 대: 모르고 있었다. 잠금은 DB가 행에 표시한다 → 서버가 몇 대든 DB가 하나면 같은 줄. `synchronized`는 한 서버 안에서만. 안 되는 경우: 대상이 DB 행이 아님, DB가 나뉨, 복제본으로 간 조회, 커넥션 수(서버마다 풀 10 × 대수 vs Postgres 100). NOTES "잠금은 DB 안에 있다".
- 5번 나가기: 결론(안 어겼다)은 맞았다. 규칙은 "그 행(방)의 첫 읽기"라 참여 행을 먼저 읽는 건 상관없다. 진짜 함정은 `participation.getGroupOrder()`다. LAZY라 껍데기의 `getId()`는 방을 읽지 않는다. `@ManyToOne` 기본값은 EAGER라서 LAZY를 빼먹으면 참여 행을 읽을 때 방도 같이 읽혀 2026-10-22와 같은 함정이 된다(재현은 안 했다). NOTES "지연 로딩과 프록시".

### 4단계. 캐시 — ADR-061

**무엇**: 학교별 방 목록 **첫 페이지**(page 0, size 20)만 Redis `rooms:{학교id}`에 JSON으로 10초. 목록을 바꾸는 곳(방 만들기, 참여, 나가기, 메뉴 담기·고치기·빼기, 마감, 취소, 스케줄러)이 그 학교 키를 **커밋 뒤에 지운다**. 코드는 `RoomListCache` 한 클래스.

**왜 방 목록만**: 캐시하기 좋은 곳의 조건 넷(자주 읽힌다, 여러 사람이 같은 결과, 옛것이어도 피해가 작다, 버릴 곳이 적다)에 다 맞는 건 이것뿐. 내 방 목록은 사람마다 다르고, 방 상세에는 보는 사람의 참여 id가 섞이고, 정산표는 돈이다. 캐시는 보여 주기에만 쓰고 판단(참여 가능?)은 늘 잠근 DB 값으로 한다 → 최악은 "눌렀더니 마감"(409).

**읽는 길(cache-aside)**: `findList` → `covers(page,size)` → `get` → 있으면 반환 / 없으면 DB 쿼리 → `put`(TTL 10초).

**지우기만 하고 새 값은 안 쓴다**: 바꾸는 쪽이 목록을 다시 만들 필요가 없고, 여러 요청의 SET이 뒤집혀 닿으면 옛 값이 남는다. 지우기는 순서가 상관없다.

**지우기 + TTL 둘 다**: 지우기는 사건이 있는 변화(참여)를 바로, TTL은 사건 없는 변화(마감 시각이 지남)와 지우기를 빠뜨린 곳을 따라잡는다.

**첫 페이지만**: 학교마다 키 하나라 `DEL` 한 번. 페이지마다 키면 지울 키를 다 알아야 하는데 `KEYS`는 Redis를 멈추고 `SCAN`은 놓칠 수 있다.

**깨진 것 둘 (2026-10-17)**
1. 커밋 전에 지움 → A가 참여하며 키를 지우고, 커밋 전에 B가 목록을 열어 DB(아직 인원 1, READ COMMITTED)를 읽고 캐시에 다시 넣음 → A 커밋 뒤에도 10초 동안 인원 1. 고침: 트랜잭션 안이면 `registerSynchronization`으로 `afterCommit()`에서 지운다. 롤백이면 안 지운다. 트랜잭션 밖이면 바로 지운다. 남는 틈(A 커밋과 afterCommit 사이에 B가 읽고, 지운 뒤에 넣음)은 훨씬 좁고 TTL이 덮는다.
2. 나가기 끝의 `evict` 줄에서 `no session` 500 → 위의 메뉴 일괄 삭제가 `clearAutomatically = true`로 영속성 컨텍스트를 비워 방의 거점 프록시가 떨어져 나갔다. 학교 id를 비우기 전에 `Long`으로 꺼내 둔다(`ParticipationService.leave`의 주석).

**Redis가 죽으면**: 읽기 실패 = 캐시 없음 → DB로. 넣기·지우기 실패 = 로그만. 이미 커밋된 참여를 500으로 돌려주면 다시 눌러 "이미 참여"를 본다. 응답 대기 500ms. try-catch는 `afterCommit` 안에서 실제로 도는 `delete`에 있다(등록하는 줄을 감싸면 못 잡는다).

**버린 것**: `@Cacheable`/`@CacheEvict`(키가 메서드 매개변수라 사람마다 캐시가 생기고, `join(groupOrderId)`는 학교 id를 몰라 그 학교만 못 지운다, 커밋 뒤 지우기·에러 무시가 설정으로 숨는다), 이벤트 + `@TransactionalEventListener`(받는 쪽이 하나뿐이라 과하다, 여럿이 되면 다시 본다), TTL만(참여해도 10초 동안 그대로), 지우기만(마감 시각 지남을 못 잡는다).

**숫자 (Phase 4)**: 적중 97~99%, 캐시 켬 목록 p95 약 8ms. 끄면(개선 1 전) 5.1초, 초당 40건 천장. 개선 1 뒤에는 꺼도 12ms. 몰림 때는 참여마다 지워서 캐시가 비는 순간 쿼리 비용이 드러났다(1차 C의 p99 300ms).

**답해 보고 고친 것 (2026-10-22)**
- 커밋 전 지우기 순서: 맞게 설명했다("빈 캐시 → 커밋 전 DB를 읽은 남이 옛 값을 채움 → 커밋 뒤 DB와 어긋남"). 처음 설명이 복잡해서 "내가 지운 빈자리에, 아직 옛 값을 보는 남이 옛 값을 채웠다" 한 줄로 다시 들었다.
- 지우기만 하는 이유: "다음 조회가 채운다"는 반쪽. 바꾸는 쪽이 목록을 다시 만들 필요가 없다 + 여러 SET이 뒤집혀 닿으면 옛 값이 남는데 지우기는 순서가 상관없다.
- TTL만 / 지우기만: 맞았다. 지우기만 쓰면 지우기를 빠뜨린 곳은 영영 옛 값이라는 것도 하나 더.
- Redis가 죽으면: "DB만 쓴다"는 목록 읽기 쪽 답이다. 참여는 이미 커밋됐고, 지우기 실패는 로그만 남기고 성공으로 돌려준다. 500을 주면 다시 눌러 "이미 참여한 방"을 본다. 못 지운 캐시는 TTL이 치운다. 대가: Redis가 응답 없이 멈추면 요청마다 최대 500ms(타임아웃)를 기다린다. 캐시와 달리 리프레시 토큰은 Redis가 원본이라 그쪽은 대신할 곳이 없다(코드로 따진 것).
- 캐시가 아직 필요한가: "12ms가 긴가?"부터 물었다. 판정선 300ms의 1/25이고 사람이 느끼는 시간으로는 즉시다. 그래서 질문은 속도가 아니라 DB 여유와 복잡도의 교환이다. 남길 이유: 캐시를 끄면 240명에 DB 서버 CPU 47%, 켜면 요청 대부분이 DB에 안 간다. 실행 계획의 추정은 여전히 11(실제 375)이라 데이터가 바뀌면 계획이 다시 뒤집힐 수 있다. 뺄 이유: 지우기 호출 9곳, 최대 10초 옛것, 남는 틈, Redis 장애 경로. 판단: 지금은 남긴다(대가는 이미 치렀고 테스트가 지킨다). 면접에서는 "지금 크기에서는 없어도 판정선 안"이라고 솔직히 말한다.

- **자세히**: ADR-061 / JOURNAL 2026-10-17 두 건 / NOTES "캐시" 전부(특히 "Redis 명령은 DB 트랜잭션에 묶이지 않는다", "registerSynchronization은 어떻게 동작하나", "Redis가 멈췄을 때") / 테스트 `RoomListCacheTest`, `GroupOrderListCacheTest`, `GroupOrderListCacheRaceTest`

### 5단계. JPA와 쿼리 — ADR-012, 035, 037, 062, 076

**5-A. 영속성 컨텍스트 = 트랜잭션마다 하나 있는 보관함.** 지금까지 겪은 JPA 문제는 전부 이 보관함의 네 가지 동작에서 나왔다.

| 동작 | 뜻 | 겪은 것 |
|---|---|---|
| 1차 캐시 | 같은 id를 다시 읽으면 DB 대신 보관함의 객체를 준다 | 미리 보기 뒤 잠그는 읽기가 옛 방을 받음 → 정원 4명 방에 13명 (2026-10-22) |
| 변경 감지 | 보관함 안 객체의 필드를 바꾸면 커밋 때 UPDATE가 저절로 나간다. 보관함 밖이면 안 나간다 | `@Transactional`을 빠뜨린 취소가 200 CANCELED인데 DB는 그대로 (2026-10-12). 정산 시작은 `saveAll`한 정산표만 저장되고 방 상태는 그대로 (2026-10-07) |
| flush | SQL을 모아 뒀다가 커밋 때 보낸다 | `save`를 감싼 try-catch는 예외를 못 잡을 수 있다 → `saveAndFlush` (ADR-060) |
| LAZY 껍데기 | 연관 객체는 id만 든 껍데기. `getId()`는 공짜, 다른 필드를 읽을 때 SELECT. 보관함과 끊기면 `no session` | 트랜잭션 없는 정산 시작에서 방장 계좌 읽다 500 (2026-10-07), 나가기의 캐시 지우기 줄 (2026-10-17) |

**보관함을 건너뛰는 쿼리**: `@Modifying @Query` DELETE는 DB로 바로 간다. 메뉴를 같은 트랜잭션에서 읽어 둔 뒤 지우면 보관함에는 메뉴가 남아 flush 때 `TransientPropertyValueException` (2026-10-01). `flushAutomatically`(먼저 보내고) + `clearAutomatically`(뒤에 비우기)로 맞췄고, 그 대가가 나중의 `no session`이었다.

**거짓 200이 500보다 나쁘다**: `@Transactional`이 빠졌을 때 500이 나느냐는 응답 DTO가 LAZY 필드를 읽느냐는 우연에 달렸다. 그래서 상태 전이 테스트는 응답 뒤에 DB를 다시 읽는다.

**답해 보고 고친 것 (2026-10-23)**
- Q1 거짓 200: 맞다. 트랜잭션이 없으니 커밋도 없고, 커밋이 없으니 변경 감지가 돌 때가 없다. 응답은 바뀐 자바 객체로 만들어서 CANCELED가 찍혔다.
- Q2 try-catch가 못 잡는 save: 몰랐다. 예외는 SQL이 DB에 갈 때 난다. INSERT가 커밋 때 가면 예외도 커밋 때, 즉 메서드가 끝난 뒤 try 바깥에서 난다 → 409가 아니라 500. 지금은 IDENTITY라 `save` 줄에서 바로 INSERT가 가서 잡히긴 한다. 그건 id 방식 한 줄에 기대는 우연이라 `saveAndFlush`로 "지금 보내라"를 코드에 적었다.
- Q3 clearAutomatically: 맞다.
- Q4 트랜잭션 안의 no session: 맞다(clear 경우). 뿌리는 "그 객체가 지금 보관함 것이 아니다"이고, 앞 트랜잭션에서 넘겨받은 객체나 다른 스레드로 넘긴 객체도 같다. 겪은 건 clear 하나.

- **자세히**: JOURNAL 2026-10-01 "메뉴를 담아둔 채로 방을 나가니", 10-07 "배달비 입력이 500", 10-12 "방 취소가 200에", 10-17 "no session" / NOTES "JPA" 전부

**5-B. 쿼리.** 네 가지를 했다.

1. **N+1 (2026-10-06, 방장 검수 목록)**: 참여자 2명에 7번, 5명에 13번(3 + 2N). 사람마다 메뉴 조회 1번, 닉네임을 읽을 때 LAZY user 조회 1번.
   명단을 `JOIN FETCH p.user`로, 메뉴는 방 단위로 한 번에 받아 `groupingBy`로 나눠서 4번 고정. 테스트는 "2명과 5명의 쿼리 수가 같다"로 본다(숫자를 박지 않는다).
2. **방 목록은 쿼리 4번 (ADR-035)**: 사용자 1 + 방 한 페이지 1(방장, 거점은 JOIN FETCH) + 인원수 1 + 합계 1. 인원과 합계는 방 id들을 모아 `IN` + `GROUP BY`로 한 번씩.
   버린 것: 참여와 메뉴를 한 쿼리에 join(3명 × 메뉴 5개 = 15줄로 불어나 COUNT, SUM이 부푼다), `@BatchSize`(연관이 아니라 집계라 붙을 자리가 없다).
3. **EXPLAIN으로 찾은 느린 목록 (ADR-076)**: 캐시를 끄자 목록 p95 5초. 쿼리 한 번 101ms. DB가 남을 방을 11개로 추정했는데 실제 375개 →
   적을 줄 알고 방장을 하나씩 비교하는 조인(758,700번 비교)을 골랐다. 정원 조건을 하위 쿼리 COUNT에서 `participantCount` 열로 바꾸자 1.8ms, 목록 p95 12ms.
   열을 믿어도 되는 근거: 인원이 바뀌는 곳은 만들기, 참여, 나가기 셋이고 참여와 나가기는 방 락 안에서 행과 숫자를 같이 바꾼다. 4,126개 방에서 어긋난 방 0개.
   대가: 참여 행을 바꾸는 새 길을 만들면 숫자도 같이 바꿔야 한다. 추정은 여전히 34배 틀린다.
4. **Flyway (ADR-062)**: `create-drop`이면 배포마다 데이터가 사라진다. SQL을 `V1__init.sql`부터 번호 파일로 두고, Hibernate는 `validate`만.
   한 번 돌린 파일은 고치지 않는다(체크섬). 옛 행을 채우는 변경은 열 추가 → 채우기 → NOT NULL. 버린 것: `ddl-auto: update`(이름 바꾸면 빈 새 열, 기록 없음), Liquibase.

**답해 보고 고친 것 (2026-10-23)**
- Q1 쿼리 수 비교: 맞다. 덧붙이면 4를 박으면 인증 필터 같은 고정분이 바뀔 때 상관없는 테스트가 깨진다.
- Q2 getId는 공짜: 반만 맞다. "있는 정보"의 출처가 핵심이다. 참여 행에 `user_id` 열(외래 키)이 있어서 JPA가 그 값으로 껍데기를 만든다. 닉네임은 users 행에 있어서 따로 읽어야 한다.
- Q3 추정 11: 맞다. 정확히는 "추정에 맞는 조인 방식을 골랐다"가 원인. 몇 줄뿐이면 하나씩 비교(Nested Loop)가 가장 싸고, 수백 줄이면 해시표(Hash Join)가 싸다. 11줄로 보고 앞의 것을 골랐다.
- Q4 열을 처음부터 안 쓴 이유: 위험은 맞다(숫자와 행이 늘 같아야 한다). 이유는 ADR-035에서 "세는 값은 한 곳(참여 행)에만 둔다"였기 때문. 열은 Phase 3 동시성(ADR-058)에서 락 안에서 정원을 보려고 생겼고, 목록 쿼리만 옛 모양으로 남아 있었다.
- Q5 이미 돈 V3를 고치면: 몰랐다. 다시 돌지 않는다. 체크섬이 달라서 앱이 아예 안 뜬다(로컬에서 겪음, JOURNAL "줄바꿈만 바꿔도"). 운영에 나간 파일은 되돌리고 V4로 바로잡는다.

### 1단계. 도메인 — ADR-001~022, 029~053

세 부분으로 나눠 본다. 1-A 방의 규칙, 1-B 정산, 1-C 취소와 환불, 스케줄러.

**1-A. 방의 규칙은 엔티티(`GroupOrder`) 안에 있다**

1. **상태 흐름**: 모집중 → 마감 → 정산중 → 주문완료 → 배달완료. 상태마다 그 상태가 된 시각 칸(`closedAt`, `settlementStartedAt` …)이 있고, 거치지 않았으면 null(ADR-017).
2. **규칙을 엔티티에 둔 이유(ADR-020)**: 서비스가 몇 개가 되든 검사가 빠지지 않는다. 엔티티는 인원, 합계, 현재 시각을 **숫자와 인자로 받는다** → DB 없이 "마감 1초 전", "정확히 마감 시각"을 단위 테스트한다. 세고 더하는 건 서비스가 한다.
3. **마감은 둘(ADR-020)**: 방장 수동 마감(`closeByHost`)은 조건(2명 이상, 합계 ≥ 최소주문금액)이 안 되면 **거부**하고 모집중으로 남는다. 마감 시각 도달(`closeAtDeadline`)은 **취소**하고 사유를 남긴다. 수동은 "이제 됐다"는 판단이라 더 기다리면 되지만, 시각은 약속된 끝이라 더 기다릴 근거가 없다.
4. **깨진 것(JOURNAL 2026-10-06)**: 마감 시각이 지난 뒤 누른 마감 버튼을 자동 규칙에 맡기려다 두 번 깨졌다. ① 엔티티 안에서 `Instant.now()`와 비교해 41개 중 18개 실패(테스트의 `now`는 늘 과거). ② `closeAtDeadline` 뒤에 `return`이 없어 아래 수동 규칙까지 흘러내려가 예외 → 서비스였다면 롤백돼 취소가 저장되지 않는다. 조건을 채운 방은 결과가 우연히 같아서 가려졌다.
5. **취소는 지우지 않는다(ADR-021)**: 상태 `CANCELED`로 남긴다. 참여자에게 이유를 보여 주고, 정산표가 환불의 근거고, 감점과 통계의 재료다. `CancelType`에 **취소 직전 상태**까지 담는다(`HOST_WHILE_RECRUITING`/`CLOSED`/`SETTLING`, `DEADLINE_UNMET`, 시간 초과 둘). CANCELED가 되면 직전 상태가 사라지기 때문.
   반대로 나가기는 참여 행을 지운다(ADR-019, 037). 모집중에만 되고 아직 아무 일도 없었다. 기준은 "나중에 누가 이 기록을 찾을 일이 있나".
6. **검사 순서는 상태 → 사람 → 값, 권한 위반만 403(ADR-050)**: 403은 "이 사람에게 버튼을 보여 준 게 잘못", 409는 "화면의 방 상태가 낡았다". 상태가 먼저라 참여자가 주문완료된 방에서 방장 버튼을 누르면 409다. `ForbiddenException`이 `IllegalStateException`을 상속하지 않게 하자 테스트 50개가 정확히 권한 검사 자리에서 깨졌다.

**답해 보고 고친 것 (2026-10-23)**
- Q1 now를 인자로: 방향은 맞지만 핵심은 **테스트**다. 시각을 고정해 넘겨야 "마감 1초 전, 정각"을 확인할 수 있다. 엔티티에서 실제 시계를 보다가 18개가 깨진 게 그 증거. 덤으로 한 요청의 검사들이 같은 "지금"을 본다. NOTES "현재 시각을 인자로 받는다".
- Q2 직전 상태: 맞다. 더 구체적으로, 지금 코드가 이미 쓴다. 환불과 정산 정보 보기는 "정산중에 취소된 방"에만 열린다(`isCanceledWhileSettling`). 상태만 보면 CANCELED라 구분이 안 된다.
- Q3 주문완료 방의 방장 버튼: 403이 아니라 **409**. 검사 순서가 상태 먼저라 "주문완료된 방만/정산중인 방만"에서 먼저 걸린다. 상태 사유는 누구에게나 같은 답이라 먼저 본다.
- Q4 수동 마감을 취소로 안 한 이유: "당연하다"도 면접에서는 말로 풀어야 한다. DESIGN 문구가 실제로 "미달이면 자동 취소"였고 규칙이 하나로 줄어드는 대안이었다. 답은 **거부는 되돌릴 수 있고 취소는 못 되돌린다**. 방장의 이른 판단 한 번에 모인 사람들의 방이 사라지면 안 된다. NOTES "되돌릴 수 있는 쪽을 고른다".

- **자세히**: ADR-017, 019~021, 037, 040, 050 / JOURNAL 2026-10-06 "마감 시각이 지난 방의 마감을 자동 규칙에 맡겼는데" / `GroupOrder.java`

**1-B. 정산**

1. **송금이 주문보다 먼저(ADR-029)**: 방장 외상을 없앴다. 안 모이면 주문을 안 하면 되니 미입금 피해가 0원. 금액은 명단과 메뉴가 굳은 마감 뒤에만 정해진다. 대가: 리스크가 없어지지 않고 옮겨간다(방장이 돈을 받고 주문하지 않으면 참여자 손해), 주문이 늦어진다.
2. **정산표를 저장한다(ADR-030)**: 금액은 계산으로 나오지만 **입금 확인은 계산으로 나오지 않는다**. 누가 눌러야만 아는 사실이라 참여자마다 줄이 필요하다. 덤으로 스냅샷(분담 규칙이 바뀌어도 옛 방 금액이 안 바뀐다).
   방장 줄도 만들고 처음부터 "확인됨"으로 채운다 → 모든 줄 합 = 메뉴 합계 + 배달비로 검증되고, "전원 확인"에 방장 건너뛰기 분기가 없다.
3. **시각 두 개, 판정하지 않는다(ADR-032)**: `markedPaidAt`(참여자 "보냈어요"), `confirmedPaidAt`(방장 "받았어요"). 앱은 은행이 아니라 진실을 볼 수단이 없다. 그래서 양쪽 주장을 각각 남긴다. 확인은 줄마다(부분 확인과 환불 대상이 줄에만 남는다. 화면은 묶을 수 있지만 서버에서 묶으면 못 쪼갠다).
4. **주문완료 기준은 방장 확인(ADR-047)**: "보냈어요"로 통과시키면 이체 없이 방장 돈으로 주문시킬 수 있다. 돈이 들어온 걸 아는 사람은 방장뿐.
5. **확인 취소(ADR-045)**: 확인만 비우고 `confirmRevokedAt`을 찍는다. "보냈어요"는 참여자의 주장이라 방장이 지울 수 없다. 흔적이 없으면 "확인한 적이 있다"는 증거가 사라진다.
6. **배달비 수정(ADR-046)**: 참여자 줄에 세 시각 중 하나라도 있으면 409, 없으면 정산표를 지우고 통째로 다시 만든다(배달비가 섞인 중간 상태가 없다). "보냈어요"만 보면 표시 없이 확인된 줄과 확인 취소 흔적이 재생성으로 지워진다. 무엇이 흔적인지는 줄(`hasPaymentRecord`)이, 모으는 건 서비스가 한다.
7. **동시성으로 이어진 것**: 확인 취소와 주문완료가 겹치면 주문완료가 취소 전의 줄을 볼 수 있다(ADR-047 "남은 문제") → 3단계, 방 → 정산 줄 순서로 잠근다.

**답해 보고 고친 것 (2026-10-23)**
- Q1 방장 줄을 확인됨으로: 당연하지 않다. 방장은 자기에게 송금하지 않으니 자연스러운 모양은 "방장 줄 없음"이나 "확인 안 된 방장 줄"이다. 확인 안 된 채로 두면 "전원 확인"이 영영 채워지지 않아 방이 정산중에 갇힌다. 그래서 주문완료, 환불 같은 "전원 ○○" 조건마다 `if (방장이면 건너뛴다)`가 붙는다. 처음부터 채워 두면 조건이 한 줄이고, 방장 줄의 확인 취소를 막는 이유도 이것이다.
- Q2 보냈어요를 안 지움: 맞다. 더 정확히는 **참여자의 주장이라 방장이 지울 수 없다**. 확인만 되돌리면 "보냈다는데 확인 안 됨"(분쟁 상태)으로 돌아가서 데이터가 사실 그대로다.
- Q3 confirmRevokedAt: 몰랐다. B가 19:00 송금, 방장이 19:08 확인, 21:00 확인 취소. 흔적이 없으면 DB에는 "보냈다고 함, 확인 안 됨"만 남아 처음부터 확인 안 한 방장과 구분이 안 된다. B가 따질 근거, 신뢰도 재료가 사라진다. 확인된 줄에서만 찍으므로 값이 있다는 것 자체가 "전에 확인이 있었다"는 증거라 칸 하나로 충분하다. NOTES "판정할 수 없으면 주장을 각각 기록한다".
- Q4 보냈어요만 보면: 맞다. B가 이체하고 버튼을 잊었고 방장이 확인했다 → 통과해서 정산표가 다시 만들어진다 → B의 새 줄은 "확인 안 됨"이 되고 방장의 확인 기록이 지워진다. 이미 보낸 돈과 새 금액도 어긋난다. 확인 취소 흔적도 같은 식으로 사라진다.

- **자세히**: ADR-001, 010, 029~032, 042~047 / `Settlement.java`, `SettlementCalculator.java`, `SettlementService.java`

**1-C. 취소와 환불, 스케줄러**

1. **취소가 먼저, 환불은 나중(ADR-048)**: 방장 취소는 모집중, 마감, 정산중 모두 한 주소. 취소해도 정산표는 남는다. 환불을 마쳐야 취소되게 하면 취소 소식이 늦어진다.
2. **환불 대상은 "보냈어요"나 "받았어요"가 있는 참여자 줄(ADR-048)**: 보냄만 있는 줄도 넣는다. 돈이 왔는데 방장이 확인을 안 눌렀을 수도 있고 앱은 구분 못 한다. 확인된 줄만 넣으면 방장이 확인 안 하고 취소하는 것으로 먹튀가 된다. 기본값은 "돌려줘야 함", 정말 안 왔으면 방장이 "입금 안 됐어요"로 **명시적으로 반박**한다. 대상인지는 저장하지 않고 계산한다.
3. **환불 완료는 참여자의 "돌려받았어요"(ADR-049)**: 입금 완료가 받는 사람(방장)의 확인이었듯, 환불은 방향이 반대라 받는 사람(참여자)이 기준. "돌려줬어요"를 앞에 요구하지 않는다(버튼을 잊은 방장 때문에 줄이 영원히 대기로 남지 않게). 되돌리기는 없다(이어지는 단계가 없고, 받았다는 말은 영수증 서명이다).
   늦은 "보냈어요"는 받는다(취소 20초 전에 이체한 사람). 확인 쪽은 언다(방장이 확인을 지워 환불 대상에서 빠지지 못하게).
4. **스케줄러(ADR-051)**: 1분마다 DB를 훑는다. 모집중 마감 시각 지남 → `closeAtDeadline`, 마감 3시간 → 취소, 정산중 24시간 → 취소(환불 흐름이 열린다), 주문완료 6시간 → 배달완료. 서버가 10분 꺼져도 켜진 뒤 밀린 방을 다 처리한다.
   버린 것: Redis TTL 만료 알림(보내고 잊는 pub/sub이라 배포 중이면 사라진다), 방마다 예약 작업(메모리라 재시작하면 사라진다), 조회할 때 넘기기(아무도 안 보는 방은 멈춰 있다).
5. **엔티티가 자기 시각으로 다시 판단(ADR-052)**: 쿼리가 14:00:00.0에 "마감 3시간" 방을 골랐는데 14:00:00.3에 방장이 배달비를 넣어 정산중이 됐다. 상태만 보면 "정산중이니 24시간 잠수"로 1초 만에 취소된다. `expireIfStale(now)`는 `settlementStartedAt`을 보고 조용히 넘어간다(예외가 아니라 정상). 방마다 따로 부르고, 기간 상수는 엔티티에 한 번만 적는다.
6. **내 방 목록(ADR-053)**: 진행 중 / 끝난 방 두 탭. 환불이 안 끝난 취소 방은 진행 중이다. 같은 방도 보는 사람마다 다르다. 판정은 쿼리 안 `EXISTS`(자바에서 빼면 페이지에 빈자리가 생긴다).

**답해 보고 고친 것 (2026-10-23)**

- Q2 완료 기준이 참여자: 맞다. 근거를 한 줄로: 돈이 들어왔는지는 받는 사람만 안다(입금은 방장, 환불은 참여자). 나머지 반쪽: "돌려줬어요"를 먼저 요구하지도 않는다(버튼을 잊은 방장 때문에 줄이 영원히 대기로 남지 않게).
- Q3 정산중 자동 취소: 맞다. 정확히는 환불 버튼이 "정산중에 취소된 방"에만 열려서, 취소가 안 되면 "돌려줘야 할 돈"이라는 기록 자체가 생기지 않는다. 받아들인 부작용: 실제로 주문하고 버튼만 안 누른 방장의 방에도 환불 대기가 뜬다(방장 책임).
- Q4 엔티티가 다시 확인: "2차 방어선"보다 정확한 말은 **3단계의 check-then-act**다. 쿼리로 후보를 고른 것(확인)과 방마다 처리하는 것(행동) 사이에 방장이 끼어들 수 있다. 그래서 `expire`는 방을 잠그고(`findByIdForUpdate`) 지금 값으로 엔티티가 다시 판단한다. 쿼리 결과는 고른 순간의 사진일 뿐이다.
- Q5 Redis TTL 알림: 방향만 맞았다. 이유 셋: ① 만료 알림은 보내고 잊는 pub/sub이라, 그 순간 받는 서버가 없으면(배포, 재시작) 알림이 영영 사라지고 방은 계속 모집중이다. ② 알림은 Redis가 키를 실제로 지울 때 나가서 늦을 수 있다. ③ 마감 시각이 DB와 Redis 두 곳에 생긴다. DB를 훑으면 놓친 방을 다음 실행이 줍는다. NOTES "스케줄러는 신호가 아니라 상태를 훑는다".

- **자세히**: ADR-021, 048, 049, 051~053 / `GroupOrder.expireIfStale`, `GroupOrderExpiryScheduler.java`

### 2단계. 인증과 보안 — ADR-024~028, 034, 055, 059

두 부분. 2-A 토큰, 2-B 가입, 메일 인증, 보안 기본값.

**2-A. 토큰**

1. **왜 토큰이 필요했나(ADR-024)**: 처음 요청자는 `X-User-Id` 헤더 숫자였다. 누구든 남이 될 수 있다. "방장만" 규칙에 넣는 id를 공격자가 정하면 규칙이 의미 없다.
2. **액세스 15분 JWT + 리프레시 2주 Redis(ADR-024)**: 액세스는 서명만 검증하고 저장소를 안 본다. 리프레시만 서버가 들고 있어서 로그아웃 = Redis에서 지우기. "JWT는 무상태라 저장소가 필요 없다"는 로그아웃을 포기할 때만 참이다. 대가: 로그아웃과 제재가 최대 15분 늦다.
   솔직한 이유: 이 규모면 세션 + Redis 세션이 더 알맞다. JWT를 고른 절반은 학습과 면접이다(숨기지 않고 적었다).
3. **토큰에 담는 것(ADR-026)**: `sub`(id), `iat`, `exp`만. 서명은 위조 방지지 비밀 유지가 아니다(payload는 base64라 누구나 읽는다). 닉네임, 인증 여부 같은 바뀌는 값은 15분 동안 낡은 사진이 돈다 → 인증 여부는 필터가 매 요청 DB에서 읽는다.
4. **리프레시는 불투명 토큰(UUID)**: JWT로 만들면 "서명만 보고 통과"시키고 싶어지고, 그러면 로그아웃이 안 된다. 불투명 토큰은 저장소를 보도록 강제한다.
5. **회전(ADR-024 수정)**: 처음엔 회전 없이 갱신마다 새 토큰을 주고 옛 것을 안 지웠다 → 로그아웃 뒤에도 옛 토큰으로 갱신 200(테스트로 재현). 쓴 토큰은 즉시 폐기.
6. **GETDEL(ADR-059)**: 찾기와 지우기가 명령 둘이라 같은 토큰 10건 동시 갱신에 10건 모두 성공. `GETDEL` 한 명령으로 30회 모두 1건만 성공. 탭 둘의 동시 갱신은 정상 사용이라 화면이 Web Locks로 한 탭씩 줄 세운다(진 탭 로그아웃 5/5 → 0/20).
7. **로그인 실패는 이유를 안 나눈다(ADR-026)**: 계정 열거를 막는다. 없는 이메일이면 BCrypt를 건너뛰어 응답이 빨라서 새므로 더미 해시로 시간을 맞춘다. BCrypt를 쓴 이유: 일부러 느리고 salt가 자동(SHA-256은 빨라서 GPU 대입).

**답해 보고 고친 것 (2026-10-23)**
- Q1 로그아웃: 반만 맞다. 이 프로젝트는 쿠키가 아니라 localStorage에 둔다. 핵심은 **서버가 Redis에서 리프레시 토큰을 지운다** → 더는 새 액세스 토큰을 못 받는다. 이미 나간 액세스 토큰은 최대 15분 산다(그래서 15분으로 짧다). 블랙리스트는 검토하고 버렸다(요청마다 Redis를 보면 세션과 같아진다). "화이트리스트"는 사실 지금 리프레시 저장소가 그 역할이다. NOTES "JWT에서 로그아웃은 무엇인가".
- Q2 바뀌는 값: 맞다. 실제 장면까지: 메일 인증을 마쳤는데 토큰에는 미인증이라 최대 15분 방 만들기가 403.
- Q3 회전이 없으면: 맞다. 실제로 재현한 건 한 단계 앞이다. 갱신해도 옛 토큰이 안 지워져 **로그아웃 뒤에도 옛 토큰으로 갱신 200**. 회전하면 훔친 쪽과 주인 중 먼저 쓴 쪽만 살고, 다른 쪽이 막혀 이상을 알 수 있다(재사용 탐지까지는 안 했다).
- Q4 GET + DEL: 맞다, check-then-act다. 고칠 표현은 "락처럼"이다. 락은 확인과 행동 **사이를 막는** 것이고 GETDEL은 **사이를 없애는** 것이다. 한 명령이라 끼어들 틈이 없어서 락이 필요 없다. NOTES "확인과 행동을 한 명령으로 합치면 락이 필요 없다".
- Q5 메시지를 합쳐도 새는 길: 비밀번호만 틀린 경우는 이미 같은 메시지로 합친 경우다. 새는 길은 둘: ① **응답 시간**(없는 이메일은 BCrypt를 건너뛰어 빠르다 → 더미 해시로 막음), ② **가입 API**("이미 쓰이는 이메일입니다" 409 → ADR-028에서 닫음, 2-B).

**2-B. 전체 흐름과 지금 구조 (질문 없이 정리만, 2026-10-23)**

- 가입 `POST /api/auth/signup`: 이메일 소문자로(ADR-055) → `@` 뒤 도메인으로 학교 찾기(없으면 400, ADR-025) → 닉네임 중복만 409 → 이메일 중복이면 계정을 안 만들고 "이미 계정이 있습니다" 메일, 새 가입이면 인증 메일. 응답은 둘 다 **202**(ADR-028, 계정 열거 차단). 메일은 커밋 뒤 이벤트 리스너가 보낸다(ADR-027).
- 메일 인증 `GET /api/auth/verify?token=`: Redis `verify:{UUID}` → 사용자 id, 30분. 쓰는 순간 지우고, 만료, 사용됨, 없음은 같은 응답. `emailVerifiedAt`이 찍힌다. 재전송은 1시간 5회(`verify:resend:{id}` INCR, 넘으면 429).
- 로그인 `POST /api/auth/login`: 실패는 401 한 문장, 없는 이메일도 더미 해시로 시간 맞춤 → 액세스 JWT(15분, `sub` `iat` `exp`) + 리프레시 UUID(Redis `refresh:{UUID}` → id, 2주).
- 매 요청: `Authorization: Bearer` → `JwtAuthenticationFilter`가 서명 검증 → id로 DB에서 사용자를 읽어 `ROLE_USER` 또는 `ROLE_VERIFIED`를 단다.
- 갱신 `POST /api/auth/refresh`: `GETDEL`로 꺼내며 지우고 새 쌍 발급(회전, ADR-059). 화면은 401이면 Web Locks로 한 탭씩 갱신.
- 로그아웃 `POST /api/auth/logout`: Redis에서 리프레시 삭제. 화면은 localStorage를 비운다.
- 권한 규칙(`SecurityConfig` 한 곳, 기본값 "전부 닫힘", ADR-034): `/api/auth/**`, `GET /api/universities` 열림 / `GET /api/**` 로그인 필요(미인증도 구경 가능) / 나머지(쓰기)는 `VERIFIED`만, 아니면 403. `/actuator`는 앱에서 열려 있지만 인터넷에서 backend까지 닿지 않는다. 막는 건 web의 Nginx다(`/api/`만 backend로 넘기고 나머지는 화면 `index.html`). 2026-10-23 `https://bandal.site/actuator/health`가 JSON이 아니라 화면 HTML(200)로 오는 걸 확인했다. Prometheus는 서버 안 monitoring 네트워크로 backend에 직접 닿는다.

- **자세히**: ADR-024, 026, 059 / JOURNAL 2026-10-16 "갱신 10건", 2026-10-19 탭 / NOTES "Redis 원자적 카운터"

### 6단계. 테스트와 CI — ADR-054, 057

1. **테스트 세 층(2026-10-23 기준 테스트 클래스 38개, `@Test` 726개)**
   - 엔티티 단위 테스트 8개(`GroupOrderTest`, `SettlementCalculatorTest` …): Spring도 DB도 없다. 엔티티가 숫자와 `now`를 인자로 받아서 가능하다(1-A).
   - 리포지토리 테스트 6개(`@DataJpaTest`): 쿼리와 제약.
   - API 테스트 24개(`@SpringBootTest` + MockMvc): 요청 → 응답 코드 → **DB를 다시 읽어 확인**(거짓 200 때문, 5-A).
2. **Testcontainers**: 테스트가 뜰 때 진짜 `postgres:17`과 Redis 컨테이너를 띄운다(`TestcontainersConfiguration`, `@ServiceConnection`). 테이블은 Flyway가 운영과 같은 SQL로 만든다. 인메모리 DB(H2)를 쓰지 않은 이유(ADR로 따로 적지는 않았다): 이 프로젝트에서 실제로 부딪힌 게 전부 Postgres 고유 동작이다. 잠금(`FOR NO KEY UPDATE`), 한글 정렬(en_US.utf8이 가나다를 뒤집음, JOURNAL 10-01), 제약 위반 뒤 `current transaction is aborted`, Flyway SQL 문법.
3. **동시성 테스트(3개)**: 스레드 N개를 출발선(`CountDownLatch` ready/start/done)에 세워 한꺼번에 놓는다. 그냥 스레드를 띄우면 앞 스레드가 끝난 뒤 뒤 스레드가 출발해서 경쟁이 안 생긴다.
4. **쿼리 수 테스트**: Hibernate 통계(`getPrepareStatementCount`)로 2명과 5명의 쿼리 수가 같은지 본다(5-B).
5. **먼저 깨뜨리고 고친다**: 순진한 버전 → 실패를 눈으로 → 고침. 정원 4명에 13명, 갱신 10/10, 거점 9건 500, `Instant.now()`로 18개 실패, 403 분리로 50개가 권한 자리에서 깨짐. 예상만 한 에러는 기록하지 않는다.
6. **CI(ADR-057)**: 작업 브랜치 → main PR. main은 보호, `backend`(`./gradlew test`, GitHub 서버의 Docker로 Testcontainers)와 `frontend`(`npm ci && npm run build`, 타입 검사)가 초록이어야 merge.
   바뀐 폴더의 job만 돈다. `on.paths`로 거르면 워크플로가 아예 안 떠서 필수 검사가 "대기 중"에서 멈추므로, 워크플로는 늘 띄우고 job을 `if`로 건너뛴다(건너뛴 job은 통과). 실패하면 테스트 보고서를 올려 둔다. 같은 PR에 새로 push하면 앞 실행은 취소.
7. **순서를 바꾼 것(ADR-054)**: 원래 배포 → 동시성이었는데 CI만 떼어 동시성 앞에 뒀다. 테스트가 650개를 넘어 락을 넣다가 다른 흐름을 깨면 바로 드러나야 했고, 동시성은 배포가 필요 없어서 도메인이 생생할 때 했다.

- **자세히**: ADR-054, 057 / `.github/workflows/ci.yml` / `TestcontainersConfiguration.java` / `GroupOrderConcurrencyTest.java`

### 7단계. 배포와 인프라 — ADR-063~071, 073

재료는 아래 "배포 운영(Phase 2 마무리)" 1~2번에 이미 있다. 복습은 한 요청이 지나가는 길과 코드가 서버에 올라가는 길 두 줄로 묶어 봤다(2026-10-23, 질문 없이).

- **요청의 길**: Cloudflare DNS(A 레코드 → 서버 IP, 프록시 끔) → 바깥 Nginx(443에서 TLS를 풂, HSTS 30일, 요청 id, 80은 https로 돌려보냄) → web(화면 정적 파일, `/api/`만 backend로 넘김. 그래서 `/actuator`는 backend에 닿지 않고 화면이 온다) → backend:8080 → postgres, redis. 바깥에 열린 건 바깥 Nginx뿐, 나머지는 `ports` 없이 Docker 네트워크 안에서만 서로 닿는다.
- **코드의 길**: 브랜치 → PR → CI 초록 → merge → main CI → Arm 이미지 빌드, GHCR에 커밋 태그로 → 서버에 deploy 사용자로 접속 → 배포 직전 백업 → 새 태그로 띄움 → healthy가 아니면 이전 태그로 되돌림.
- **서버 한 대에 무엇이**: OCI 오사카 A1 2 OCPU/12GB(무료 한도 안, 종량제 계정에 예산 알림). Docker Compose. 비밀값은 GitHub Secrets → 배포 때 서버의 `.env`(git에 없음, 운영 설정에 기본값 없음 → 빠지면 앱이 안 뜬다).
- **지키는 것**: 백업(매일 + 배포 직전, 빈 DB에 복구해 본 뒤에만 R2로, 신호 끊기면 메일), 인증서 자동 갱신, 보안 업데이트 자동, `bootstrap.sh` 하나로 서버 준비(다시 돌려도 됨).
- **숫자**: 복구 연습 중단 15.9초, 커널 재부팅 중단 61.1초, 덤프 약 5초.
- **쓴 사이트와 도구(2026-10-23 정리)**
  - 코드와 자동화: GitHub(저장소, PR, main 보호), GitHub Actions(CI 테스트와 화면 빌드, CD 이미지 빌드와 SSH 배포), GitHub Environments/Secrets(production 환경에만 비밀값), GHCR(이미지 보관, 커밋 SHA 태그)
  - 이미지: Docker(Dockerfile 단계 빌드), Buildx + QEMU(x86 러너에서 Arm 이미지), Docker Compose(서버에서 띄우는 설계도)
  - 서버: Oracle Cloud(OCI, 오사카 A1 2/12 무료 한도, 종량제 계정 + 예산 알림, 보안 목록으로 포트 제한), Ubuntu 24.04, unattended-upgrades(보안 패치 자동), `bootstrap.sh`(서버 준비)
  - 도메인과 HTTPS: Cloudflare Registrar(bandal.site 구매), Cloudflare DNS(레코드, 프록시 끔), Nginx(바깥 문, TLS, HSTS), Let's Encrypt + certbot(인증서 무료 발급, 자동 갱신)
  - 메일: Resend(SMTP 발송, DKIM/SPF 설정, 무료 하루 100통)
  - 백업과 감시: Cloudflare R2(백업 보관, 서버와 따로 죽는 곳), healthchecks.io(백업과 인증서 갱신이 신호를 안 보내면 메일)
  - 관측: Prometheus(숫자 긁기), Grafana(대시보드, SSH 터널로만), node-exporter(서버 CPU, 메모리), Loki + Alloy(로그 모으기, 9단계), k6(부하 테스트)

- **물어본 것 "compose로 전체를 묶어 서버가 받아 한 번에 띄우나?"**: 거의 맞다. 고칠 것 셋. ① 서버는 **소스를 받지 않는다**. 빌드는 GitHub 서버가 하고, 서버는 다 만든 이미지(GHCR)만 받는다. 서버로 가는 파일은 `compose.yml`, 스크립트 셋, `.env`뿐. compose는 "무엇을 어떻게 띄울지"의 설계도, 이미지는 완성품이다. ② 매번 전체를 새로 띄우지 않는다. `deploy.sh`는 web과 backend 이미지만 새 태그로 받고, postgres와 redis는 버전 고정이라 그대로 있다(데이터는 볼륨에 남는다). ③ 띄우고 끝이 아니라 `--wait`로 healthy까지 기다리고, 안 되면 이전 태그로 되돌린다. 로컬 `docker-compose.yml`(개발용 DB, Redis만)과 서버용 `deploy/bandal/compose.yml`은 다른 파일이다.

### 8단계. 부하 테스트와 관측 — ADR-074~078

재료는 아래 3~5-3번. 복습은 "재는 순서" 한 줄로 묶었다(2026-10-23).

1. **판정선을 먼저 정한다**: 목록 p95 300ms, 참여 p95 1초, 에러 1% 미만. 재고 나서 정하면 결과에 맞춰 선을 긋게 된다. 평균이 아니라 p95/p99(평균은 꼬리를 묻는다).
2. **운영이 아닌 같은 모양의 테스트 서버**에 운영 서버의 k6로 건다(사설 IP). 데이터는 큰 학교와 작은 학교, 지난 방까지 넣어 매번 같게.
3. **결과 숫자와 원인 숫자를 같이 본다**: 결과(p95, 에러, 처리량)는 k6, 원인(커넥션 풀 대기, 쿼리 시간, CPU, 캐시 적중)은 Prometheus + Grafana.
4. **한 번이 아니라 여러 번**: A 200명이 537~1,235ms로 흔들렸다. 전후 비교는 범위로 한다.
5. **일부러 끈다**: 캐시를 끄자 목록 p95 5초, 초당 40건 천장, Postgres CPU 100% → EXPLAIN → 개선 1(5단계). 캐시가 가리던 쿼리 비용이 드러났다.
6. **개선 2는 예상이 틀렸다**: 번호표가 필요하다고 봤는데, 순진한 미리 보기만으로 A 200명 351~589ms. 요청이 수백 ms에 퍼져 닿아서 "동시"가 아니었다. 그래서 번호표를 보류하고 재검토 조건을 적었다(3단계).
7. **관측이 놓친 것**: 10초 간격 순간값 사이로 1초짜리 몰림이 빠져 커넥션 대기 그래프가 계속 0이었다(최대값 지표로 봄).

- **도구**: k6(부하를 만들고 결과 숫자를 낸다, 운영 서버에서 CPU 1개로), 테스트 서버(운영과 같은 모양 A1 2/12, 같은 이미지), Spring Actuator + Micrometer(앱 안에서 숫자를 재서 `/actuator/prometheus`로 낸다), node-exporter(서버 CPU, 메모리), Prometheus(10초마다 긁어 쌓는다), Grafana(대시보드 "Bandal 한눈에", SSH 터널), EXPLAIN ANALYZE(느린 쿼리 속).
- **대시보드 지표**: 위 줄 "결과" = p95, p99, 처리량, 5xx 비율. 아래 줄 "원인" = 커넥션 풀(사용 중, 대기 중), 커넥션 얻기 대기 최대, 락 잡는 조회 p95, 캐시 적중률, CPU(서버 전체와 backend), JVM 힙과 GC 멈춤, 서버 남은 메모리, Tomcat 바쁜 스레드.
- **자세히**: 아래 3, 4, 5, 5-2, 5-3번 / ADR-074~078

### 9단계. 로그 — ADR-079

재료는 아래 5-4번. 복습은 "왜 → 길 → 요청 id → 깨진 것 → 확인" 순서로 봤다(2026-10-23).

1. **왜**: 로그가 컨테이너에 붙어 있어 배포하면 같이 사라졌다. 메트릭은 "언제 나빠졌나"만, 로그는 "그 요청에 무슨 일이"를 알려 준다.
2. **길**: 컨테이너 표준 출력 → Docker → docker-proxy(GET만 허용) → Alloy(수집기) → Loki(보관 30일) → Grafana Explore. Docker 소켓을 그대로 주면 컨테이너를 만들고 지울 수 있다(사실상 root)라서 읽기만 되는 문지기를 둔다.
3. **요청 id**: 바깥 Nginx가 요청마다 32자 id를 만들어 `X-Request-Id`로 넘기고 자기 접속 기록에도 `rid=`로 남긴다 → backend의 `RequestLogFilter`가 MDC에 넣고 응답 헤더로 돌려준다 → 그 요청 안의 모든 로그 줄에 같은 id. 요청 하나를 Nginx 줄과 backend 줄로 이어서 찾는다.
4. **구조화 로그**: 운영은 JSON 한 줄(method, uri, status, durationMs, userId, requestId). 글자를 정규식으로 뜯지 않고 칸으로 거른다.
5. **꼬리표와 본문**: Loki는 꼬리표(project, service, container, host, level)만 색인하고 본문은 훑는다. 꼬리표에 userId 같은 값이 많은 칸을 넣으면 색인이 폭발한다. ELK는 본문 전체를 색인해 검색이 강하지만 돌볼 것이 둘 더 는다(버림).
6. **깨진 것**: Loki 이미지에 셸도 wget도 없어 healthcheck unhealthy. docker-proxy가 네트워크 목록을 막아 Alloy가 컨테이너를 못 찾음(403).
7. **확인**: 배포 뒤 새 컨테이너의 `docker logs`는 39줄, Loki에는 배포 전 30분치 168줄. 메모리 Loki 58MB, Alloy 55MB.

### 2-2. HTTPS — ADR-070, ADR-073
- **무엇**: 바깥 Nginx에서 TLS를 푼다. Let's Encrypt 인증서를 certbot이 하루 두 번 갱신 시도한다. Cloudflare 프록시는 끈다. HSTS는 하루 → **30일 + includeSubDomains**(2026-10-21), 첫 자동 갱신(12월 중순)을 본 뒤 1년. preload는 안 한다.
- **왜**: HSTS 기간은 "https가 깨졌을 때 와 본 사람이 얼마나 못 들어오나"다. 확인한 것(발급)만큼만 믿고 단계로 올린다. 운영은 6개월 정도라 내리기 한 달 전에 max-age=0을 보낸다.
- **자세히**: ADR-070, ADR-073 / NOTES "HTTPS와 인증서", "TLS를 푸는 곳", "Cloudflare 프록시와 Flexible 함정", "인증서를 받을 때 증명하는 두 방법", "SNI", "HTTP는 막지 말고 HTTPS로 돌려보낸다. 그리고 HSTS"

### 2-3. 서버 준비와 업데이트 — ADR-063, ADR-071

## 4. Phase 4: 관측 묶음 — ADR-075

- **무엇**: backend가 `/actuator/prometheus`로 숫자를 낸다(응답 시간 히스토그램, 커넥션 풀, 리포지토리 시간, 캐시 적중 카운터). 운영 서버에 Prometheus, Grafana, node-exporter. Grafana는 SSH 터널로만. 대시보드 "Bandal 한눈에"는 git의 JSON.

### 1차 (2026-10-21, 이미지 da45139, 각 한 번씩)

읽을 것:

- C의 몰림 순간에 상관없는 요청의 p99가 7ms → 약 300ms, 커넥션 얻는 시간 최대 0.23 → 0.54초. 락을 기다리는 참여 요청이 커넥션 10개를 붙잡았다. 꼬리에서 ADR-058의 신호가 처음 보였다.

### 2차 (흔들림, 캐시 끈 목록)

**흔들림(캐시 켬, 데운 뒤):**
- A 200명 참여 p95를 네 번(1차 포함) 쟀더니 537~1,235ms. 두 번은 판정선(1초)을 넘었다. "200명이면 넘을 수도 있다"가 정확하다.
- C 안의 참여 p95는 483~624ms, 목록 p99는 99~186ms.
- 그래서 개선 전후 비교는 한 번이 아니라 여러 번 돌린 범위로 한다.

**캐시 끔:**

| 단계 | 목록 p95 | 초당 목록 | 서버 CPU | backend CPU | 커넥션 얻는 시간 최대 |
|---|---|---|---|---|---|
| 60명 | 0.5초 | 35 | 95% | 9~14% | 0.4초 |
| 120명 | 2초 | 40 | 100% | 7% | 1.8초 |
| 240명 | **5.1~5.7초** | 40 | 100% | 7% | 6.4초 |

- 캐시가 없으면 60명에서 이미 판정선을 넘고, 처리량은 초당 40건이 천장이다.
- CPU를 먹는 건 backend가 아니라 Postgres다. 커넥션 10개가 다 쿼리에 묶여 나머지는 기다린다.
- **원인(EXPLAIN ANALYZE)**: 인덱스가 아니었다. `group_order` 전체 훑기는 2ms. Postgres가 남을 방을 11개로 추정했는데 실제 375개였다(status와 deadline을 상관없다고 보고 곱해 33, 짐작 못 하는 하위 쿼리 비교에 1/3). 적게 믿고 고른 조인(Nested Loop + Join Filter)이 users 2,530 × 방 300을 하나씩 비교해 758,700번, 쿼리 한 번 101ms.
- 캐시를 켜면 97~99% 가려지지만, 참여할 때마다 캐시를 지워서 몰림 순간에는 이 비용이 드러난다(1차 C의 p99 300ms).
- 캐시 끈 C는 목록 p95 2.0초, 참여 p95 2.8초. 몰림과 목록이 같이 오면 모두 느려진다.
- **자세히**: ADR-074 "기준값 2차" / JOURNAL "캐시를 끄자 방 목록 p95가 5초가 됐다" / NOTES "EXPLAIN ANALYZE와 행 수 추정"

### 그래서 고칠 후보(같이 정할 것)

1. **목록 쿼리**: 하위 쿼리 대신 이미 있는 `participant_count` 열로. 같은 데이터에서 EXPLAIN으로 101ms → 1.8ms(조인이 방장 기본키 찾기로 바뀜). 추정은 그대로 11이라 데이터가 바뀌면 다시 볼 것. 캐시를 끈 B로 전후를 잰다.
2. **몰림이 커넥션을 묶는 것**: 같은 방 참여가 락을 기다리는 동안 커넥션을 붙잡는다. 풀 크기, 대기열, Redis 분산 락 중 무엇을 할지. C의 다른 요청 p99로 전후를 잰다.
3. 인덱스: 지금 데이터 크기에서는 효과가 작다고 실행 계획이 말한다. 데이터가 커지면 다시 본다.

## 5-2. 개선 1: 목록 정원 조건을 인원 열로 — ADR-076

**순서대로 한 일**
1. 질문: 하위 쿼리 대신 `participant_count`를 쓰면 무엇이 좋아지고, 무엇을 먼저 확인해야 하나.
2. 확인 (가) 코드: 참여 행이 생기고 없어지는 곳은 셋뿐(방 만들기 1, 참여 +1, 나가기 −1). 참여와 나가기는 방 락 안. cascade 없음.
3. 확인 (나) 데이터: 테스트 서버 4,126개 방에서 숫자 ≠ 실제 행 수인 방 0개. 200명이 동시에 참여한 방도 10 = 10.
4. 테스트 추가: 실제 API로 참여해서 꽉 차면 빠지고, 나가면 다시 나오는지(`reappearsAfterLeave`).
5. 사용자가 쿼리를 고침: `AND go.participantCount < go.capacity`.
6. **깨짐**: `hidesFullRoom`. 테스트가 참여 행만 넣고 숫자를 안 올려서, 앱에선 생길 수 없는 방(행 2, 숫자 1)을 만들고 있었다. 쿼리가 아니라 테스트를 고쳤다(`join()` 도우미). 721개 통과.
7. 실행 계획 확인 → 측정(기준값 2차와 같은 순서, 조건, 데이터).

**왜 빨라졌나(설명을 두 번 고쳤다)**
- 처음 설명 "열로 바꾸면 추정이 맞아진다"는 틀렸다. 짐작 못 하는 비교에는 하위 쿼리든 열이든 1/3이라, 추정은 그대로 11.
- 추정이 크게 틀리는 진짜 까닭은 status와 deadline을 상관없다고 보고 곱한 것(33, 실제 376).
- 계획이 바뀐 까닭은 비용 점수: 하위 쿼리 버전은 기준 76,000점에 두 조인 방식 차이 200점(0.3%)이 묻혔고, 열 버전은 197 대 407로 차이가 드러났다. Postgres는 1% 안쪽 차이를 같은 비용으로 본다(가장 그럴듯한 설명).

**전후**

| | 전 | 후 |
|---|---|---|
| 캐시 끔 목록 p95(240명) | 5,149ms | **12.0ms** |
| 캐시 끔 초당 목록 / 서버 CPU | 40건 천장 / 100% | 160건 / 47% |
| 목록 쿼리 평균 | 0.24초 | 0.002초 |
| 캐시 켬 C 목록 p99 | 99~186ms | 39~60ms |
| 캐시 켬 A 200명 참여 p95 | 537~1,235ms | 597~1,030ms (그대로, 다음 개선 대상) |

- **자세히**: ADR-076 / JOURNAL "목록 쿼리를 인원 열로 바꾸자 ... 테스트가 깨졌다", "캐시를 끄자 ... 5초"(추가 확인) / NOTES "EXPLAIN ANALYZE와 행 수 추정"

### 남은 것
- **몰림이 커넥션을 묶는 것**(A 200명 참여가 아직 판정선 근처). 5-3에서 다뤘다.

## 5-3. 개선 2: 꽉 찬 방은 락 앞에 서지 않게 — ADR-077(뒤집힘), ADR-078

**문제**: 정원 10명 방에 200명이 몰리면 191명은 결국 409인데, 그 191명도 커넥션을 하나씩 쥐고 방 락 앞에 줄을 선 뒤에야 "꽉 참"을 안다. 그동안 다른 요청도 커넥션을 기다린다.

**설계 대화(순서대로)**
1. 사용자: "비동기, 멀티스레드로 동시에 하면?" → 아니다. Tomcat 스레드 200개는 이미 동시에 돈다. 모자란 건 커넥션 10개와 락 1개다. 락은 정원을 지키려고 일부러 한 줄로 세운 것(NOTES "스레드, 커넥션, 락 대기").
2. 사용자: "participantCount로 미리 판별" → 락 없이 읽은 값은 틀릴 수 있지만, 정원은 락 안의 확인이 계속 지키니 미리 보기는 가끔 틀려도 된다(NOTES "락 전에 미리 보기").
3. "빈 방에 200명이 동시에 읽으면?" → 사용자: 다 0명을 보고 다 통과할 것. 그래서 "읽기"가 아니라 "자리를 가져가기", Redis `DECR` 번호표를 설계했다(ADR-077: 표 돌려주는 곳, 수명 30초 + SET NX, Redis가 죽으면 건너뛰기, 버린 대안: 매번 DB 값으로 덮어쓰기).
4. 순서: 먼저 순진한 미리 보기만 넣고 재고, 그다음 번호표.

**깨진 것**: 미리 보기를 `join` 트랜잭션 안에 넣자 동시성 테스트 11개 중 6개가 에러 없이 깨졌다. 정원 4명 방에 13명, 방장 취소가 "모집중"으로 되돌아감. 먼저 읽은 방이 영속성 컨텍스트에 남아 `findByIdForUpdate`가 옛 객체를 돌려줬다. ADR-058에 "잠그는 읽기는 첫 읽기여야 한다"고 적어만 둔 규칙을 처음 직접 어겨 봤다.
- 고침: 트랜잭션 없는 `ParticipationGate`를 컨트롤러와 서비스 사이에 두고 거기서 미리 본다(같은 클래스 안 호출은 프록시를 안 거쳐서 클래스를 나눴다). 고치는 중에 호출 방향이 한 번 거꾸로 됐다(서비스 → 문지기, 컴파일 에러로 멈춤). 11개, 전체 722개 통과. 꽉 찬 방 참여는 앞사람이 락을 쥔 동안에도 1,981ms → 1ms.
- **자세히**: JOURNAL "락 전에 인원을 미리 보자 정원 4명 방에 13명이 들어가고, 방장의 취소가 사라졌다"

**측정 — 예상이 틀렸다**

| | 개선 1 뒤 | 미리 보기 뒤 |
|---|---|---|
| A 200명 참여 p95 (3번) | 597~1,030ms | **351~589ms** |
| A 200명, 방 락까지 간 요청 | 200 | **약 17~29** |
| C 참여 p95 / 목록 p99 (3번) | 405~460 / 39~60ms | 316~382 / 31~57ms |
| A 500명 / 1,000명 참여 p95 | - | 1,161 / 1,112ms (락까지 간 요청 약 23 / 12) |

- "동시에"는 실제로 동시가 아니었다. 요청은 수백 ms에 퍼져 닿고 9자리는 앞의 몇십 명 안에서 찬다. 나머지는 미리 보기에서 거른다.
- 500, 1,000명에서 1초를 넘은 건 락이 아니라 커넥션 얻기(최대 0.6초, 미리 보기도 커넥션을 빌린다)와 Spring 바깥(Tomcat 스레드 대기로 추정, 직접 확인 못 함). 번호표는 커넥션 몫만 줄인다.
- **결정**: 번호표는 보류. 판정선(200명) 안에 여유 있게 들어왔고, 번호표의 복잡도(Redis와 DB 숫자 맞추기)에 비해 남은 이득이 작다. 재검토 조건: 락까지 간 요청이 수백 개로 늘거나 몰림 때 커넥션 얻기가 0.5초를 반복해서 넘을 때.
- **자세히**: ADR-078(표, 재검토 조건) / ADR-077(번호표 설계, 뒤집힘) / NOTES "Redis 원자적 카운터", "서버가 잰 시간과 k6가 잰 시간이 다를 때"

## 5-4. 로그 모니터링: Loki — ADR-079

**왜**: 로그가 컨테이너에 붙어 있어서 배포하면 이전 로그가 사라졌다(16:13 배포 뒤 backend 로그 첫 줄이 16:13). 메트릭은 "나빠졌다"만 알려 준다.

**고른 것과 버린 것**: ELK는 본문 전체를 색인해 검색이 강하지만 JVM 둘과 화면 하나를 더 돌본다. 처음엔 "메모리가 모자라다"고 했다가 재 보니 서버는 12GB 중 1.3GB만 써서 그 이유는 틀렸다. 남는 이유는 품과 화면이 하나 더 는다는 것, 로그가 적다는 것. Loki는 꼬리표만 색인하고 이미 있는 Grafana에서 본다.

**구조**
```
컨테이너들 ──(로그)── Docker ──GET만── docker-proxy ── Alloy ──push── Loki ── Grafana(Explore)
바깥 Nginx: $request_id를 만들어 X-Request-Id로 넘기고 접속 기록에 rid=로 남긴다
backend: RequestLogFilter가 그 id를 MDC와 응답 헤더에 넣고, 요청마다 JSON 한 줄(method, uri, status, durationMs, userId)
```

**한 일(순서대로)**
1. 앱: `RequestLogFilter`(가장 앞 필터), `JwtAuthenticationFilter`가 MDC에 userId, prod는 `logging.structured.format.console: logstash`. 테스트 4개(JSON 줄, id 이어받기/버리기, userId와 MDC 비우기, /actuator 제외). 전체 726개 통과.
2. 묶음: Loki 3.7.8(30일), Alloy v1.20.1, docker-proxy v0.5.0(컨테이너·네트워크 GET만). 꼬리표는 project, service, container, host, level.
3. 로컬에서 띄워 확인하다 두 번 깨졌다. Loki 이미지엔 셸도 wget도 없어 healthcheck가 unhealthy. docker-proxy가 네트워크 목록을 막아 Alloy가 컨테이너를 못 찾음(403). 둘 다 고친 뒤 줄 10개가 꼬리표대로 들어오고, 컨테이너 만들기는 403으로 막히는 것을 봤다.
4. 운영(c089780 + 바깥 Nginx 적용): 컨테이너 11종 로그 수집, Grafana에 Loki 자동 등록. 요청 하나의 id로 바깥 Nginx 줄(`rid=`, 9ms)과 backend 줄(4ms)이 같이 나왔다. 메모리 Loki 58MB, Alloy 55MB.
5. 배포 뒤에도 남는지(149e457 배포): 새 backend 컨테이너는 17:23:24에 만들어졌고 `docker logs`에는 17:23:27부터 39줄뿐. Loki에는 16:54:16 ~ 17:23:45의 backend 줄 168개가 있었다(이전 컨테이너 것 포함). 확인 스크립트는 `docker inspect`의 생성 시각, `docker logs` 첫 줄, Loki의 컨테이너별 첫·마지막 줄을 나란히 찍는다.

- **자세히**: ADR-079 / JOURNAL "Loki를 띄우자 healthcheck에서 unhealthy, Alloy는 컨테이너를 하나도 못 찾았다(403)" / NOTES "메트릭, 로그, 트레이스", "MDC", "구조화 로그", "Loki의 꼬리표와 본문, LogQL", "수집기(Alloy)와 Docker 소켓"

## 6. 포트폴리오로 말할 거리

- **복구를 실제로 해 봤다**: "백업이 있다"가 아니라 "운영 서버를 R2의 덤프로 되돌리는 데 26.5초, 사용자가 본 중단 15.9초".
- **판정선을 먼저 정하고 쟀다**: 결과에 맞춰 선을 긋지 않았다. 200명 몰림에서 참여 p95가 1초를 넘는다는 한계를 찾았다.
- **평균이 아니라 꼬리를 봤다**: p95는 멀쩡했지만 p99에서 다른 방까지 느려지는 것을 잡았다. 이게 분산 락/대기열을 검토할 근거가 된다.
- **관측 도구를 의심했다**: 그래프의 0이 "없었다"가 아니라 "못 봤다"였다(순간값과 긁는 간격). 설정 다시 읽기 "성공"이 새 설정이 아니었다(inode).
- **고치기 전에 쟀다**: 인덱스가 없다는 걸 먼저 봤지만 기준값을 남기려고 일부러 그대로 두었다.
- **한 줄로 430배**: 캐시를 끈 목록 p95 5,149ms → 12ms. 처리량 천장(초당 40건)이 사라지고 서버 CPU 100% → 47%. 고친 건 쿼리 조건 한 줄이고, 고치기 전에 그 숫자를 믿어도 되는지(코드의 모든 길, 실제 데이터)부터 확인했다.
- **테스트가 틀린 쪽을 가리킨 걸 알아챘다**: 쿼리를 바꾸자 깨진 테스트는 쿼리가 아니라 앱 규칙을 건너뛴 테스트 데이터 탓이었다.
- **짐작이 틀린 걸 실행 계획으로 확인했다**: "인덱스가 없어서 느릴 것"이라고 봤지만, 실제 원인은 행 수 추정이 34배 틀린 조인이었다. 그 까닭도 처음 설명(하위 쿼리 탓)이 틀려서, 조건을 하나씩 떼어 추정을 보고 고쳤다(두 열의 상관).
- **캐시가 가리는 것을 걷어 내고 쟀다**: 캐시를 켜면 목록 p95 8ms, 끄면 5초. 캐시 덕에 버티는 시스템과 쿼리 자체가 버티는 시스템을 나눠서 봤다.
- **재 보고 복잡한 설계를 접었다**: Redis 번호표까지 설계했지만, 순진한 미리 보기를 먼저 재 보니 A 200명 p95가 597~1,030ms → 351~589ms였고 락까지 간 요청이 200 → 20~30이었다. 생각 실험("200명이 같은 순간에")이 실제 도착 분포와 달랐다. 번호표는 재검토 조건을 붙여 보류했다.
- **적어 둔 규칙을 직접 깨 봤다**: 락 전에 같은 트랜잭션에서 방을 읽자 정원 4명 방에 13명이 들어가고 취소가 지워졌다. 에러 없이 숫자만 틀려서, 동시성 테스트가 없었으면 운영에서 알았을 것이다.
- **배포해도 로그가 남는다**: 전에는 배포하면 이전 컨테이너 로그가 같이 사라졌다(16:13 배포 뒤 첫 줄이 16:13). Loki를 붙인 뒤 배포에서는 새 컨테이너의 `docker logs`가 39줄뿐인데 Loki에는 배포 전 30분치 168줄이 남았다. 요청 id 하나로 바깥 Nginx 줄과 backend 줄을 같이 찾는다.
- **한 번 잰 숫자를 믿지 않았다**: 같은 조건 네 번에 537~1,235ms. 판정은 범위로 했다.
- **비용**: 서버 두 대 모두 무료 한도 안(4 OCPU/24GB, 부트 150GB). 예산 알림 27 SGD.
