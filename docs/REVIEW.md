## 2. 배포와 운영 (2026-10-20 ~ 21)

### 2-1. 백업과 복구 — ADR-069
- **무엇**: 매일 04:00 KST와 배포 직전에 `pg_dump`를 뜨고, 네트워크 없는 빈 Postgres에 실제로 복구해 행 수와 Flyway 버전을 비교한 뒤에만 R2에 올린다. 실패하거나 하루 넘게 신호가 없으면 healthchecks.io가 메일을 보낸다.
- **왜**: 서버 디스크와 같이 죽지 않는 곳(R2)에 둔다. 복구해 보지 않은 백업은 깨져 있어도 모른다.
- **숫자**: 정기 백업 약 5초(덤프 20,884바이트). **운영 복구 연습: 새 백업 5.5초 → R2에서 받기 1.4초 → restore.sh 19.6초, 바깥에서 본 중단 15.9초.** 복구 전후 행 수 같음, 테스트 계정 로그인 됨.
- **겪은 것**: 백업 설정이 빠졌는데 실패 알림이 안 갔다(trap 순서). 복구 연습 명령을 ssh 표준입력으로 넘겼더니 docker compose exec가 나머지 명령을 먹었다.
- **자세히**: ADR-069 / JOURNAL "백업 설정이 빠졌는데", "복구 연습 명령을 ssh 표준입력으로" / NOTES "백업은 무엇과 같이 죽는가로", "RPO", "pg_dump와 디스크 스냅샷", "복구해 보지 않은 백업은", "표준입력은 자식 명령이 물려받는다", "RTO 실측"

### 2-2. HTTPS — ADR-070, ADR-073
- **무엇**: 바깥 Nginx에서 TLS를 푼다. Let's Encrypt 인증서를 certbot이 하루 두 번 갱신 시도한다. Cloudflare 프록시는 끈다. HSTS는 하루 → **30일 + includeSubDomains**(2026-10-21), 첫 자동 갱신(12월 중순)을 본 뒤 1년. preload는 안 한다.
- **왜**: HSTS 기간은 "https가 깨졌을 때 와 본 사람이 얼마나 못 들어오나"다. 확인한 것(발급)만큼만 믿고 단계로 올린다. 운영은 6개월 정도라 내리기 한 달 전에 max-age=0을 보낸다.
- **자세히**: ADR-070, ADR-073 / NOTES "HTTPS와 인증서", "TLS를 푸는 곳", "Cloudflare 프록시와 Flexible 함정", "인증서를 받을 때 증명하는 두 방법", "SNI", "HTTP는 막지 말고 HTTPS로 돌려보낸다. 그리고 HSTS"

### 2-3. 서버 준비와 업데이트 — ADR-063, ADR-071
- **무엇**: `bootstrap.sh <IP>` 하나로 Docker, 스왑, deploy 사용자(키 restrict), SSH 잠그기, cron까지. 다시 돌려도 되게(멱등). 서버는 1/6으로 잡힌 뒤 재시도 반복으로 **2 OCPU/12GB**로 키웠다(세 번째 시도).
- **업데이트**: 자동 보안 업데이트가 보안 패치와 커널 7.0을 스스로 깔았다. Docker는 컨테이너가 다 다시 뜨므로 사람이 시점을 고른다. **커널 재부팅 중단 61.1초**, 컨테이너는 restart 정책으로 스스로 떴다.
- **겪은 것**: 진짜 서버에서 bootstrap이 관리자 키 암호 때문에 멈췄다(BatchMode), 업그레이드 뒤 `/run/sshd`가 없어 sshd 검사가 실패했다. 테스트 서버를 같은 스크립트로 준비할 때는 둘 다 다시 안 났다(고친 스크립트가 처음부터 통했다).
- **자세히**: ADR-063, ADR-071 / JOURNAL "bootstrap을 돌렸더니 10분 넘게 멈췄다", "/run/sshd가 없다며" / NOTES "docker 그룹은 사실상 root다", "다시 돌려도 되는 스크립트", "authorized_keys의 restrict", "ssh-agent와 eval"

### 2-4. 배포 파이프라인 — ADR-067
- **무엇**: main CI 초록 → Arm 이미지 빌드, GHCR → 서버에서 배포 직전 백업 → 새 태그로 띄우고 healthy 아니면 이전 태그로 되돌린다. 관측 묶음도 앱 배포 뒤에 같이 올린다.
- **겪은 것**: job의 `if`가 환경 변수를 못 봐서 배포가 초록불인 채로 건너뛰어졌다.
- **git 실수 하나**: 커밋 안 된 수정이 남은 채로 stash pop을 하다 충돌 표시(`<<<<<<<`)가 main에 merge됐다. 이후 "pull 전에 브랜치부터" 순서로 바꿨다.
- **자세히**: ADR-067 / JOURNAL "deploy job이 값을 다 넣었는데도 건너뛰어졌다", "stash pop의 충돌 표시가 그대로 커밋되어"

## 3. Phase 4: 측정 설계 — ADR-074

- **결과 숫자**: p95, p99, 에러율, 처리량. 평균은 꼬리를 묻고, 무너지는 서버는 일찍 실패해서 오히려 빨라 보이기도 한다.
- **판정선(테스트 전에 정함)**: 목록 p95 300ms, 참여 p95 1초, 에러 1% 미만.
- **원인 숫자**: 커넥션 풀(사용 중, 대기, 얻는 시간), 락 잡는 조회 시간, CPU, JVM, 캐시 적중률, Tomcat 스레드.
- **시나리오**: A 한 방에 몰림, B 목록 새로고침(큰 학교, 작은 학교), C 둘을 같이(다른 방까지 느려지나 = ADR-058 재검토 조건).
- **환경**: 운영과 같은 테스트 서버, 부하는 운영 서버의 k6(CPU 1개, 사설 IP). 운영에 직접 걸지 않는다.
- **데이터**: 학교마다 규모가 달라서 큰 학교(연세대 신촌 2,000명, 모집중 300, 지난 방 3,000)와 작은 학교(광운대 200, 20, 200)를 같이. 지난 방을 넣어야 인덱스 없는 쿼리의 비용이 드러난다. 매번 같은 데이터(1초에 넣는다).
- **자세히**: ADR-074 / NOTES "부하 테스트와 관측" 아래 전부, "k6의 기본 말들" / `loadtest/README.md`

## 4. Phase 4: 관측 묶음 — ADR-075

- **무엇**: backend가 `/actuator/prometheus`로 숫자를 낸다(응답 시간 히스토그램, 커넥션 풀, 리포지토리 시간, 캐시 적중 카운터). 운영 서버에 Prometheus, Grafana, node-exporter. Grafana는 SSH 터널로만. 대시보드 "Bandal 한눈에"는 git의 JSON.
- **왜 운영 서버에**: 테스트 서버는 테스트할 때만 켠다. **왜 터널**: 로그인 화면을 인터넷에 세우지 않는다.
- **겪은 것**: node-exporter의 rslave 마운트가 WSL에서 거부됐다. 설정 파일 하나를 붙인 Prometheus가 tar로 바뀐 새 파일을 못 보고 옛 설정을 "성공적으로" 다시 읽었다(inode). 1초짜리 몰림이 10초 간격의 순간값 사이로 빠졌다.
- **자세히**: ADR-075 / JOURNAL "node-exporter가", "Prometheus 설정을 배포했는데", "커넥션 대기 수 그래프는 계속 0" / NOTES "Actuator, Micrometer", "SSH 터널", "provisioning", "파일 하나 마운트와 inode"

## 5. Phase 4: 기준값 (고치기 전)

### 1차 (2026-10-21, 이미지 da45139, 각 한 번씩)

| 시나리오 | 부하 | 결과 | 판정 |
|---|---|---|---|
| A | 40명 → 정원 10인 방 | 참여 p95 654ms | 통과 |
| A | 100명 | 698ms | 통과 |
| A | 200명 | **1,235ms** | **넘음** |
| B | 큰 학교 최대 200명, 작은 학교 40명 | 목록 p95 7.6ms / 8.0ms | 통과 |
| C | 목록 100명 + 200명 몰림 | 목록 p95 5.1ms, 참여 580ms | 통과 |

읽을 것:
- 정원은 늘 정확했다. 에러 0%.
- 목록이 빠른 건 캐시(적중 97~99%) 덕이다.
- C의 몰림 순간에 상관없는 요청의 p99가 7ms → 약 300ms, 커넥션 얻는 시간 최대 0.23 → 0.54초. 락을 기다리는 참여 요청이 커넥션 10개를 붙잡았다. 꼬리에서 ADR-058의 신호가 처음 보였다.
- A 200(1,235ms)과 C 안의 200(580ms)이 두 배 차이 → 2차에서 반복해 흔들림을 잰다.

### 2차 (흔들림, 캐시 끈 목록)

**흔들림(캐시 켬, 데운 뒤):**
- A 200명 참여 p95를 네 번(1차 포함) 쟀더니 537~1,235ms. 두 번은 판정선(1초)을 넘었다. "200명이면 넘을 수도 있다"가 정확하다.
- C 안의 참여 p95는 483~624ms, 목록 p99는 99~186ms.
- 그래서 개선 전후 비교는 한 번이 아니라 여러 번 돌린 범위로 한다.

**캐시 끔:**

| 단계 | 목록 p95 | 초당 목록 | 서버 CPU | backend CPU | 커넥션 얻는 시간 최대 |
|---|---|---|---|---|---|
| 60명 | 0.5초 | 35 | 95% | 9~14% | 0.4초 |
| 120명 | 2초 | 40 | 100% | 7% | 1.8초 |
| 240명 | **5.1~5.7초** | 40 | 100% | 7% | 6.4초 |

- 캐시가 없으면 60명에서 이미 판정선을 넘고, 처리량은 초당 40건이 천장이다.
- CPU를 먹는 건 backend가 아니라 Postgres다. 커넥션 10개가 다 쿼리에 묶여 나머지는 기다린다.
- **원인(EXPLAIN ANALYZE)**: 인덱스가 아니었다. `group_order` 전체 훑기는 2ms. "참여 수 < 정원" 하위 쿼리 때문에 Postgres가 남을 방을 11개로 추정했는데 실제 375개였다. 적게 믿고 고른 조인(Nested Loop + Join Filter)이 users 2,530 × 방 300을 하나씩 비교해 758,700번, 쿼리 한 번 101ms.
- 캐시를 켜면 97~99% 가려지지만, 참여할 때마다 캐시를 지워서 몰림 순간에는 이 비용이 드러난다(1차 C의 p99 300ms).
- 캐시 끈 C는 목록 p95 2.0초, 참여 p95 2.8초. 몰림과 목록이 같이 오면 모두 느려진다.
- **자세히**: ADR-074 "기준값 2차" / JOURNAL "캐시를 끄자 방 목록 p95가 5초가 됐다" / NOTES "EXPLAIN ANALYZE와 행 수 추정"

### 그래서 고칠 후보(같이 정할 것)

1. **목록 쿼리**: 하위 쿼리 대신 이미 있는 `participant_count` 열로. 추정이 맞아지면 조인이 바뀔 것이다. 캐시를 끈 B로 전후를 잰다.
2. **몰림이 커넥션을 묶는 것**: 같은 방 참여가 락을 기다리는 동안 커넥션을 붙잡는다. 풀 크기, 대기열, Redis 분산 락 중 무엇을 할지. C의 다른 요청 p99로 전후를 잰다.
3. 인덱스: 지금 데이터 크기에서는 효과가 작다고 실행 계획이 말한다. 데이터가 커지면 다시 본다.

## 6. 포트폴리오로 말할 거리

- **복구를 실제로 해 봤다**: "백업이 있다"가 아니라 "운영 서버를 R2의 덤프로 되돌리는 데 26.5초, 사용자가 본 중단 15.9초".
- **판정선을 먼저 정하고 쟀다**: 결과에 맞춰 선을 긋지 않았다. 200명 몰림에서 참여 p95가 1초를 넘는다는 한계를 찾았다.
- **평균이 아니라 꼬리를 봤다**: p95는 멀쩡했지만 p99에서 다른 방까지 느려지는 것을 잡았다. 이게 분산 락/대기열을 검토할 근거가 된다.
- **관측 도구를 의심했다**: 그래프의 0이 "없었다"가 아니라 "못 봤다"였다(순간값과 긁는 간격). 설정 다시 읽기 "성공"이 새 설정이 아니었다(inode).
- **고치기 전에 쟀다**: 인덱스가 없다는 걸 먼저 봤지만 기준값을 남기려고 일부러 그대로 두었다.
- **짐작이 틀린 걸 실행 계획으로 확인했다**: "인덱스가 없어서 느릴 것"이라고 봤지만, 실제 원인은 하위 쿼리 때문에 행 수 추정이 34배 틀린 조인이었다.
- **캐시가 가리는 것을 걷어 내고 쟀다**: 캐시를 켜면 목록 p95 8ms, 끄면 5초. 캐시 덕에 버티는 시스템과 쿼리 자체가 버티는 시스템을 나눠서 봤다.
- **한 번 잰 숫자를 믿지 않았다**: 같은 조건 네 번에 537~1,235ms. 판정은 범위로 했다.
- **비용**: 서버 두 대 모두 무료 한도 안(4 OCPU/24GB, 부트 150GB). 예산 알림 27 SGD.
